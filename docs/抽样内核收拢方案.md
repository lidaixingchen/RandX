# 抽样内核收拢方案

日期：2026 年 10 月 1 日

源码基点：`e0ce50a`

状态：生产实现与验收规范；实测结果见《抽样内核收拢验收结果》。

## 1. 目标与范围

将 `RandSample` 默认引擎与显式引擎重载中重复的随机访问抽样、蓄水池抽样分别集中到内部函数模板。公开接口负责语言标准约束、类型提取及范围适配；内部内核负责现有边界处理、随机选择和结果构造；容器适配继续负责位图路由。

每个生产头文件内，一种选择算法只维护一处。两份头文件保留同构的算法正文并继续独立分发，涉及生产实现的提交同时修改 `RandX.hpp` 与 `RandX_Cpp17.hpp`。复用现有共享契约测试组织。

本次交付保持各公开路径的现有行为：可调用性、结果类型、抽样策略、阈值、输出次序、随机数消耗、分布对象生命周期、引擎获取时机、元素支持和异常时序。共同源码生成、公开 API 扩展、分布映射优化及抽样策略调优分别立项。

该结构适合当前独立双头文件与行为等价的约束。预期收益是减少维护位置、集中算法知识；运行速度、编译时间和产物大小由测量确认。

## 3. 兼容性契约

### 3.1 数量、顺序与范围访问

- 随机访问迭代器入口先按现有规则计算距离，再判断 `n <= 0` 或长度不为正并返回空结果。零量请求仍保留该入口的距离计算及其可能的异常。
- 正数量的有效随机访问范围先执行现有长度验证；`n >= size` 时按原顺序复制全部元素，引擎输出消耗为零。
- 容器入口的 `n == 0` 返回位于范围访问之前。正请求量保留向差值类型转换的截断上限规则，位图判断继续使用原始 `std::size_t n`，迭代器委托使用转换后的数量。
- 输入迭代器的 `n <= 0` 返回位于分配和遍历之前。正请求量先按现有顺序 reserve，再单遍初填；输入耗尽时返回已填元素，引擎输出消耗为零。分配和元素构造异常按现有规则传播。
- 部分抽样保持路径次序：hash-set 与位图按接受次序输出，索引数组按前缀交换结果输出，蓄水池按最终槽位顺序输出。
- 唯一性以源位置为准；源范围包含重复值时，结果允许出现相同值。源元素保持原值，复制和代理引用转换沿用现有操作。
- 逆序边界只覆盖当前能够计算出非正距离的同类型随机访问迭代器组合；哨兵范围测试使用可达终点。

### 3.2 策略、位宽与随机数消耗

| 路径 | 保持的条件或步骤 |
| --- | --- |
| 随机访问迭代器 | `nU <= (sizeU - 1) / HashSetThresholdK` 时使用 hash-set，否则使用索引数组 |
| 容器 | 按现有 `SampleBitmapThresholdK` 与 `SampleBitmapDensityDivisor` 条件选择位图，其余委托迭代器入口 |
| hash-set | 从 `[0, sizeU - 1]` 抽取索引，碰撞重抽，接受后立即复制元素 |
| 索引数组 | Fisher–Yates 前请求量步，第 `i` 步从 `[i, size - 1]` 抽取；全部交换完成后提取元素 |
| 位图 | 保留位图字数计算、位索引、碰撞重抽和接受时复制的顺序 |
| 蓄水池 | Algorithm R 第 `i` 个位置从闭区间 `[0, i]` 抽取，符合替换条件时赋值 |

继续使用已有具名阈值与除法比较，保持差值、数量、索引的类型和转换位置。测试规模从阈值、位宽和总体规模推导。

相同编译器、标准库版本、目标平台、语言标准和构建选项下，每条公开路径的选中元素、输出次序及最终引擎状态须与基点一致。容器、迭代器及 ranges 各自比较自己的基线。默认与显式入口也分别建立基线；已有工具链下二者一致的组合继续验证该一致性。

跨标准 parity 比较同一工具链下的对应入口。分布算法由标准库实现定义，验收记录标准库种类与版本。[标准依据](https://eel.is/c++draft/rand.dist.general)

### 3.3 迭代器、引擎与元素类型

公开重载继续按值接收迭代器及哨兵。内部内核引用公开重载已经持有的局部对象，避免在新增调用边界产生迭代器或哨兵的复制、移动。C++23 的 `std::input_iterator` 支持只移动类型；`istream_view::iterator` 是必须覆盖的实例。[标准依据](https://eel.is/c++draft/range.istream.iterator)

显式引擎始终按左值引用使用，保留不可复制引擎、32 位引擎、完整 64 位引擎及非零最小值合法引擎的现有支持。

元素操作要求按算法区分：随机访问与位图通过 `push_back` 复制构造元素；蓄水池初填复制构造元素，替换阶段还需要从迭代器引用向槽位赋值。含只读成员且赋值被删除的可复制构造类型覆盖随机访问和位图路径。公开 Concepts/SFINAE 及当前实例化要求保持一致。

### 3.4 引擎获取与失败时序

迭代器内核的获取器在下表对应阶段调用一次，并以显式左值引用保存结果。内核早返回阶段调用次数为零；进入部分抽样阶段调用次数为一次。显式入口的获取器只返回已有引擎引用。容器与 ranges 保留各自公开适配层的引擎访问和委托方式。

| 入口 | 引擎取得位置及随后操作 |
| --- | --- |
| 默认随机访问迭代器 | 距离、数量判断、长度验证和全量返回之后；hash-set reserve 或索引数组分配之前 |
| 默认输入迭代器 | reservoir reserve、初填和输入耗尽判断之后；Algorithm R 的后续循环条件判断及抽取之前 |
| 默认容器 | `n == 0` 返回之后；数量转换、begin/end、距离计算和长度验证之前 |
| 显式迭代器 | 内核使用已有引用；获取器的阶段与对应默认内核一致 |
| 显式容器 | 使用已有引用，保留当前范围适配与路由次序 |
| ranges | 保留 begin/end 适配和对应默认迭代器内核的取得阶段 |

“取得默认引擎”与“调用引擎生成输出”分别验证。默认容器的正数量请求即使最终返回空结果或全量结果，也保留当前默认引擎访问行为。

hash-set 的顺序为抽取、插入集合、接受时复制；位图为抽取、检查并置位、接受时复制；索引数组先完成全部抽取和交换，再 reserve 结果并复制；蓄水池先初填，随后抽取并按条件赋值。保存各分配点、比较、解引用和递增操作的现有相对位置。

引擎、迭代器操作、元素复制或赋值抛出异常时，保留已经发生的引擎推进和源遍历进度。沿用现有异常传播契约。

### 3.5 分布对象生命周期

| 路径 | 结果类型 | 构造与调用安排 |
| --- | --- | --- |
| 默认 hash-set | `std::uint64_t` | reserve 完成后构造固定区间分布，每次抽取复用该对象 |
| 显式 hash-set | `std::uint64_t` | 每次抽取时构造固定区间分布，包含碰撞重抽 |
| Fisher–Yates 的两个入口 | `std::size_t` | 每一步按 `[i, size - 1]` 构造分布 |
| 位图 | `std::uint64_t` | reserve 完成后构造固定区间分布，每次抽取复用 |
| 蓄水池的两个入口 | `std::uint64_t` | 每个剩余位置按 `[0, i]` 构造分布 |

保留构造参数、结果类型、构造阶段和抽取调用顺序。标准分布允许内部状态；参数相同不能单独证明复用对象与每次新建对象具有相同序列和消耗。[分布要求](https://eel.is/c++draft/rand.req.dist)

## 4. 内部结构

### 4.1 内核职责与传参

| 内部实现 | 输入与职责 |
| --- | --- |
| `detail::SampleRandomAccess` | `It& first`、已取得的 `Diff size`、`Diff n`、静态获取器和固定区间分布生命周期策略；集中边界、长度验证、全量构造、hash-set 与索引数组 |
| `detail::SampleReservoir` | `It& first`、`Sentinel& last`、`Diff n`、静态获取器与入口抽取策略；集中 reserve、初填、耗尽判断与 Algorithm R |
| `detail::SampleFixedIndexDistribution` | 按入口策略生成整数；hash-set 保留选择期间生命周期，索引数组与蓄水池在每一步构造区间适配 |
| `detail::SampleBitmap` | 保留当前位图算法和接口，由容器路径调用 |
| `detail::ValidateSampleSize` | 保留当前长度契约与调用位置 |

内核使用头文件内联模板。`T` 和 `Diff` 由公开重载选定后传入，`It`、`Sentinel` 和获取器类型由参数推导。C++23 使用现代类型提取，C++17 使用传统迭代器特征；公共算法正文沿用传入类型。

公开入口采用常规 `inline`。两个内核采用编译器内联标注，在公开适配层展开，保留局部迭代器和获取器的优化信息：MSVC 使用 `__forceinline`，GCC/Clang 使用 `always_inline`，其他编译器使用 `inline`。容器适配由编译器按实例决定展开。整型差值的随机访问适配层保留空请求快路径；其他差值类型直接由内核判定。标注宏在抽样区域末尾解除。通过逐项基准及消费者构建成本验证这一策略。

随机访问内核接收长度。C++23 公开适配继续使用 `std::ranges::distance`，C++17 继续使用 `std::distance`。距离仍在公共适配层取得，内核保持随后边界判断的顺序。

内部对迭代器、哨兵及引擎的引用仅在本次同步调用中使用。返回对象只拥有复制出的元素。

### 4.2 静态引擎获取器

默认迭代器入口传入返回 `Xoshiro256StarStar&` 的获取器；显式入口传入捕获现有引用、返回 `Engine&` 的获取器。获取器构造本身保持轻量，默认获取发生在调用操作中。

内核按第 3.4 节规定的位置执行一次获取，再将引用传给分布。模板参数直接保留获取器类型，并保持静态调用和内联机会。这种向算法传递函数对象的方式符合泛型算法的常见实践。[C++ 核心指南 T.40](https://isocpp.github.io/CppCoreGuidelines/CppCoreGuidelines#Rt-fo)

### 4.3 固定区间分布策略

内部使用具名枚举 `SampleDistributionLifetime`，其取值为 `Selection` 与 `Draw`。固定区间按该策略保留分布生命周期，动态区间按该策略保留入口的整数生成适配。

- `Selection`：`SampleFixedIndexDistribution` 拥有一个 `std::uniform_int_distribution<UInt>`，在原分布构造位置初始化，调用时复用。
- `Draw`：适配器只保存当前类型的上下界，每次调用时创建对应分布并立即抽取。
- 默认随机访问入口选择 `Selection`，显式随机访问入口选择 `Draw`；容器和 ranges 委托时继承目标迭代器入口的策略。
- 两种策略用编译期选择或模板特化表达。hash-set 的集合、碰撞处理及元素复制循环在每份头文件内只有一份。
- Fisher–Yates 和蓄水池区间逐步变化，每一步构造区间适配：默认入口的 `Selection` 分布在该步作用域内持有，显式入口的 `Draw` 沿用 `RandInt` 的逐次构造。位图继续使用已有固定分布。

该适配器只承担固定区间整数生成与分布生命周期。抽样策略、边界、引擎获取和结果构造仍由各自内核拥有。

### 4.4 公开重载与容器路由

随机访问公开重载保留约束、结果类型与距离计算，整型差值先处理空请求，随后调用随机访问内核。输入公开重载保留迭代器分类、哨兵约束与结果类型，随后以局部对象引用调用蓄水池内核。

容器显式重载继续负责数量转换、const 范围类型、长度取得、长度验证和位图路由。位图之外继续调用显式随机访问入口，C++23 保留 `first + size` 对非 common range 的适配。

默认容器入口和默认 ranges 入口保持第 3.4 节的现有委托方式。公开重载保留语言标准差异；选择循环分别归随机访问、位图和蓄水池内核所有。

不可赋值元素测试须分别命中 hash-set、索引数组、位图和全量复制，检查复制次数与源值。蓄水池使用可赋值元素，覆盖初填复制及替换赋值。

重复值案例通过携带源位置标识的记录验证位置唯一性，另用重复标量验证允许相同值出现。比较有序输出，保持原始次序。

### 5.3 状态、获取时机与异常测试

- 每个默认入口测试使用具名种子独立播种；显式入口建立独立引擎。连续调用测试记录每次调用后的完整状态。
- 获取器测试用可记录阶段的静态测试对象：核对早返回零次调用、部分抽样一次调用，以及相对于初填、源比较和复制的调用阶段。
- `Reseed` 会访问默认引擎。播种后的状态比较用于验证输出消耗；默认公开薄层另行核对其获取器构造和委托位置。
- 分配点及其与获取、抽取、复制的次序逐语句核对。可稳定复现的容量拒绝案例同时记录异常和源操作进度。
- 对 hash-set、位图和全量路径注入受控复制异常；索引数组检查复制失败前已完成选择阶段；蓄水池分别覆盖初填复制与替换赋值异常。
- 引擎异常按受控调用位置触发，记录已发生的调用及源操作。位置和规模使用具名参数。
- 分布拒绝和抽样碰撞会增加引擎调用次数。验证前后状态与调用记录，而非用请求量推断调用次数。

新增测试按现有迁移清单规则登记。公共测试在两个目标中注册一致，标准与平台专属测试进入对应分组，保留固定随机顺序执行与注册清单检查。

## 6. 前后比较与跨标准验收

### 6.1 可重复执行的比较入口

扩展 `gen_parity_sequences.cpp`，提供 `--sampling-only` 模式。该模式使用公开入口，输出案例标识、参数、具名种子、有序样本、完整可序列化状态或受控引擎的完整可记录状态、调用记录，以及异常类别与源进度。元数据单独保存。

新增 `tools/compare_sampling.py`，使用 Python 标准库。其输入为 `--baseline-ref`、`--candidate-root`、`--compiler`、`--compiler-family`、`--standard`、`--build-mode` 和 `--output-dir`；编译器路径、基点及输出路径均由参数传入。本地 Python 解释器由现有 Miniconda 环境选择。

比较流程：

1. 在输出目录中建立基点头文件、候选头文件和公共源码三个独立子目录。从指定基点提取两个生产头文件，将指定工作目录中的候选头文件复制到候选子目录。
2. 将同一份候选生成程序及其必需支持文件复制到公共源码子目录，保持支持文件的相对路径。通过显式包含路径选择基点或候选头文件，公共源码目录只存放生成程序和测试支持文件。
3. 分别用完全相同的编译器、标准库、语言标准、构建选项及平台链接选项编译。C++17/C++20 使用兼容头文件选择，C++23 使用主头文件选择。
4. 运行两个生成程序的 `--sampling-only` 模式，保存完整明文输出和各自执行结果。
5. 校验两组输出都包含观察案例，覆盖全部共同必需案例；C++23 还须包含独立哨兵、只移动输入及 ranges 必需案例。随后逐字节比较输出，按案例显示首个差异及相关上下文；每个比较组合的案例集合须一致。宽差值专属案例按平台能力注册。
6. 保存构建命令、基点、候选路径、生成程序副本、编译器与标准库版本、平台、语言标准、构建模式、源参数及比较结论。

工具将参数作为独立进程参数传递。相同源码及包含路径隔离用于保证两组测量只替换生产头文件。临时结果保存在指定目录，供复查。

语言标准选择沿用现有生成器的 `RANDX_PARITY_CPP17` 开关：C++17/C++20 构建启用该开关，C++23 构建选择主头文件。MSVC 的 C++23 构建使用 `/std:c++23preview` 和 `/utf-8`；MSVC 比较构建启用 `/Zc:__cplusplus`，让标准专属观测按实际标准注册，并核对 C++23 案例确实出现在输出中。debug/release 编译选项按对应 CI 组合设置。Windows 链接 bcrypt，macOS 链接 Security framework，Linux 沿用现有链接方式。

退出行为：比较通过返回成功；行为差异返回失败；构建、运行、输入参数或观察结果错误返回独立失败状态。空输出、没有案例标识及缺少必需案例属于观察结果错误，保存原始输出和失败元数据。单元测试覆盖头文件选择、平台参数、完整输出差异、共同缺失案例、C++23 必需案例、异常记录差异和子进程失败传播。

完整状态可记录的引擎直接比较状态；后续输出作为补充观察。确定性前后比较使用可重复播种的 PRNG 和受控测试引擎。ChaCha20 的现有行为测试继续覆盖其可调用性和抽样不变量。

### 6.2 基线案例与标准库覆盖

基线包含默认与显式随机访问、默认与显式蓄水池、默认与显式容器，以及 C++23 默认 ranges。对每条路径覆盖策略内部、阈值邻接、零量、空范围、全量、超量、连续调用和可控失败。

测试规模、边界和种子在同一生成程序中由具名常量及已有阈值推导。长度拒绝与只移动迭代器等平台或标准专属案例，在相同能力的前后构建中比较。

在 GCC、Clang 和 MSVC 的现有 CI 构建组合中分别执行前后比较，记录实际标准库。Clang 的默认库由构建环境确定；标准库覆盖按记录的库种类与版本报告。

### 6.3 跨标准一致性与持续集成

既有 parity 继续执行 C++17/C++23 对应入口的逐字节比较，并增加默认迭代器、策略邻接与完整状态输出。C++23 专属案例进入对应标准的前后比较模式，公共 parity 输出只包含双标准共同案例。

在 `.github/workflows/ci.yml` 的编译器矩阵中接入前后比较，并在 Python 测试阶段执行比较工具单元测试。CI 显式提供源码基点；比较所需的提交对象在构建前准备完成。失败时上传明文结果、差异和构建元数据。

前后比较、跨标准 parity、公开契约测试和统计测试分别提供独立证据，全部纳入验收。

## 7. 性能与构建成本

### 7.1 测量覆盖

保留现有策略复杂度：稀疏 hash-set 的期望选择开销与样本量相关；索引数组初始化与辅助存储与总体长度相关；位图按总体长度分配位存储并碰撞重抽；蓄水池单遍遍历总体，结果存储与请求量相关。

扩展 `benchmark_gbench.cpp` 的抽样组，形成以下具名参数组合：

| 维度 | 必须测量的组合 |
| --- | --- |
| 入口 | 默认与显式随机访问、容器和蓄水池 |
| 规模 | 小范围与现有大范围；容器额外覆盖位图字对齐长度及其两侧邻接长度 |
| 密度 | 稀疏样本、各阈值邻接、中等密度、半数邻接、高密度、全量 |
| 早返回 | 零量、空范围、单元素全量、超量 |
| 引擎 | 默认 Xoshiro256StarStar，显式 64 位与 32 位引擎 |
| 标准 | C++17 兼容头与 C++23 主头的抽样组 |

数据构造、播种和默认引擎预热放在计时区间外。两组测量使用同一数据、种子、引擎初态、迭代安排、编译器、标准库、机器和优化选项。单遍输入案例在计时循环中按相同方式建立新的输入位置。源容器保持不变。

计时循环通过 `DoNotOptimize` 约束请求数量和输出指针，有元素时以 `ClobberMemory` 观察缓冲区写入，保证测量实际的运行时调用路径；各轮的实际请求值仍由同一参数表确定。

阈值邻接、位图密度和字边界从现有具名常量推导。容器字边界范围以 `SampleBitmapWordBits` 的具名倍数为对齐点，覆盖对齐长度及其前后相邻长度；请求量由 `SampleBitmapDensityDivisor` 推导并实际进入位图路径。蓄水池复杂度按 Algorithm R 记录，参数扫描包括不同请求密度。

### 7.2 同一基准程序与比较

批次 A 先完成新抽样测量项。验收时，将同一份扩展后的基准源及构建依赖分别与基点、候选头文件构建，使用与前后序列比较相同的包含路径隔离原则。

两边使用相同版本的 Google Benchmark、重复次数、测量项名称及参数列表，保存原始结果与 median 聚合结果。逐轮交替执行两组单次测量，并在偶数轮反转双边顺序；`tools/merge_benchmark_repetitions.py` 汇总各轮，保留原始记录并生成 median。所有新抽样项必须在两组输出中出现。使用 `tools/compare_benchmark.py` 执行项目现有门禁容差比较，并单独核对测量项集合。时间参数采用 Google Benchmark 的秒单位格式，全量初测使用具名配置 `0.1s`。

初测超过 25% 的项由 `tools/confirm_sampling_benchmark.py` 执行一次固定确认。确认集合包括超门槛项、同入口同范围内请求数量的相邻项；空范围还包含该入口最近的非空范围。双边各执行具名配置的六轮独立进程测量，每项至少 `1s`，先后顺序各占三轮，并固定到初测使用的逻辑处理器。确认集合及全部命令在运行前确定，测量完成后只替换该集合的双边结果，保留完整 243 项参与原有 25% 门禁。初测、确认原始记录和元数据分别保留；确认项缺失、进程失败或最终比较超门槛均使验收失败。

在 CMake 中增加能够明确选择 C++17 与 C++23 抽样构建的验收入口，保留现有 C++23 基准目标。每个目标使用同一扩展基准源，分别选择兼容头文件与主头文件；计时报告只比较同一标准的前后结果。抽样基准的标准选择及头文件选择在实际编译命令中记录。

双边固定到同一个可用逻辑处理器，记录处理器编号和调度优先级。相同配置下重复运行同一基点，记录测量波动；随后交替运行基点与候选，保存逐次测量及聚合结果。重复次数沿用项目现有具名配置，并在双边运行中保持一致。

现有性能 CI 会按两个提交各自的基准源构建。本任务的 `.github/workflows/benchmark.yml` 验收步骤须让新增抽样项在两组头文件上使用同一份扩展后的基准源测量，并记录实际基点。保留既有项目性能门禁。

### 7.3 验收判断

项目现有 25% 容差作为性能门禁。另逐项报告抽样组的变化量和重复测量波动；位于容差内但可重复、超过测量波动的回归仍须定位并消除后验收。

保持分配规模、分配位置、元素复制方式和引擎抽取安排。检查优化构建中的内联结果；若出现稳定回归，结合生成代码及分配记录分析原因。

保存同一代表性消费者构建的编译耗时与产物大小。源码循环收拢与模板实例化数量分别观察，构建成本出现明显变化时须解释并处理。
