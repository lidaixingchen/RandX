## 1. 目标与交付范围

让 `RandX.hpp` 与 `RandX_Cpp17.hpp` 的公共行为由同一份测试源码验证。保留两个独立测试入口，分别选择被测头文件；公共测试正文以 C++17 语法编写，在两个测试目标中各编译、运行一次。

## 3. 推荐结构

### 3.1 两个入口与一份公共正文

`test_randx.cpp` 和 `test_randx_cpp17.cpp` 保留原路径和目标名称，最终只负责：

1. 定义当前可执行文件的 doctest main。
2. 包含对应生产头文件。
3. 包含公共契约汇总文件。
4. 包含当前版本的专属测试及相关内部检查。

每个可执行文件继续由一个测试翻译单元构成。共享测试文件以头文件形式被包含，里面直接注册 doctest 用例；每个入口只包含一次汇总文件，共享文件具备正常的包含保护。

两个头文件提供相同的公共接口。入口在编译期选择头文件，公共测试直接使用 `RandX::` 名称。

### 3.2 文件职责

已实施的目录按以下职责组织。

| 文件 | 职责 |
| --- | --- |
| `tests/common/contracts.hpp` | 按明确顺序包含所有公共行为测试 |
| `tests/common/fixtures.hpp` | 公用的受控引擎、SeedSequence、元素类型和具名测试常量 |
| `tests/common/engine_contracts.hpp` | 七种 PRNG 的 KAT、种子、复制、状态与步进行为 |
| `tests/common/serialization_contracts.hpp` | 状态往返、文本流输入输出、失败状态和格式恢复 |
| `tests/common/sampling_contracts.hpp` | 元素选择、抽样、洗牌、排列与容器行为 |
| `tests/common/distribution_contracts.hpp` | 数值区间、参数错误、退化输入、权重及分布边界 |
| `tests/common/convenience_contracts.hpp` | 位、字符、字符串、UUID、填充和向量等公共行为 |
| `tests/common/security_contracts.hpp` | ChaCha20 KAT、生命周期、确定性模式和现有 OS 熵源行为 |
| `tests/common/statistical_contracts.hpp` | 现有统计特征与频率检验，集中样本数和容差依据 |
| `tests/specific/cpp23_contracts.hpp` | ranges、哨兵、编译期随机及 Concepts 专属诊断 |

| `tests/implementation/contracts.hpp` | 确实需要访问内部类型、常量或 helper 的现有检查 |
| `tests/implementation/cpp17_contracts.hpp`、`cpp23_contracts.hpp` | 两版本各自的内部约束检查 |

按领域行为聚合测试，一种行为归属一个文件。仅被单个文件使用的 fixture 就近定义；确实被多处使用时才进入 `fixtures.hpp`。涉及平台的编译条件放在对应测试附近。

### 3.3 编写约定

- 公共文件自包含所需的标准库头文件，使用 C++17 可用语法；`RandX` 名称显式限定，消除入口中的 `using namespace` 依赖。
- fixture 放入具名测试命名空间，避免同名受控引擎在合并后产生碰撞。
- main 宏仅由两个入口定义；共同文件不选择生产头文件，也不产生独立 main。
- 测试直接调用公开函数或引擎方法，不建立覆盖全部随机函数的转发 interface。
- 测试套件采用中文领域名称。基础公共套件使用 `公共/基础/` 前缀，条件公共套件使用 `公共/条件/<能力>/` 前缀，后接领域名称；标准专属与内部检查分别使用 `专属/`、`内部/` 前缀。同一公共用例在满足其能力条件的目标中使用相同套件名与用例名。
- KAT 中的种子与预期序列作为有来源的测试向量维护；样本数、重复次数、统计容差和策略规模使用具名常量，并说明数学或测试目的。
- 用例自行初始化随机状态。默认引擎测试显式设置起始状态，保留现有播种与恢复语义；任何用例都不能依赖前一个用例的消费次数。测试执行顺序种子与被测引擎种子分别命名、管理，前者只控制 doctest 的用例排序。
- 注释只说明当前契约和必要边界条件。迁移记录属于提交或 PR 描述。

## 4. 共享与专属测试的分类规则

| 测试类型 | 归属 | 处理方式 |
| --- | --- | --- |
| 两版本拥有相同公开行为 | 公共契约 | 合并输入与可观察断言；只保留一份正文 |
| 仅某一版本已有测试，但行为在两版本均适用 | 公共契约 | 迁移后由两个目标执行，补齐另一版本覆盖 |
| 只依赖 C++17 的公开类型、构造和调用结果检测 | 公共契约 | 保留 `static_assert`，与运行期契约共同编译 |
| Concepts、ranges、非 common range、constexpr 随机 | C++23 专属 | 保留语言特性和专属行为验证 |
| 兼容头文件的 SFINAE 检测方法 | C++17 专属 | 在兼容目标中验证替换失败与合法调用 |
| `char8_t` 公开行为 | 条件公共契约 | 使用现有特性检测，在 C++20/C++23 下启用；在支持该能力的矩阵配置之间比较清单 |
| 长双精度扩展、`__int128`、libstdc++ 特有场景 | 对应行为文件中的条件公共契约 | 保留局部平台能力判断；同一能力条件下两个目标使用相同断言并比较清单 |
| 内部 helper、内部特征类型和策略阈值 | 内部检查 | 集中到 implementation module，保持现有验证能力 |
| 统计频率与分布特征 | 公共统计契约 | 保留现有固定种子、样本规模和容差依据 |

公共契约以行为相等为判断依据。相同测试名不保证正文等价，不同测试名也可能验证同一行为；迁移清单必须逐项核对输入、断言、类型、条件编译和副作用。

基础公共契约只依赖两个版本均支持的 C++17 能力，其注册清单在两个目标中完全一致。条件公共契约继续与对应领域的基础用例放在同一文件中，使用独立套件前缀标识能力，并在用例附近保留条件编译。迁移清单登记每个条件套件的能力表达式与适用矩阵配置；同一工具链、平台和能力条件下核对注册内容。条件尚未满足的配置按登记规则核对该套件的缺席，不将其计为基础清单差异。

对于混合用例，把公开行为断言放入公共契约，专属约束断言放入对应专属文件。涉及内部抽样阈值的分支覆盖继续保留在内部检查中；公共抽样测试验证数量、成员关系、唯一性、值类型与引擎状态。

## 5. 首批试点：引擎种子与状态契约

1. 固定种子 KAT，保留已有期望值与输出顺序。

3. `serialize()` 与状态构造、`deserialize()` 的恢复行为。
4. `discard()` 与逐次调用的等价性。

6. 各引擎现有的全零状态策略。

`ChaCha20` 的生命周期和安全模式归入安全契约，其能力与可序列化 PRNG 分别组织。`SFC64` 的合法全零快照与吸收态引擎的处理规则保持各自语义。

将 `VerifyEngineSeedSeqContracts` 移到公共正文时，同时迁移它依赖的 fixture 和调用点。公共用例在两个目标中注册一次；原位置的对应测试正文在同一批次中移除，确保终态只有一个行为来源。

### 7.3 序列一致性与覆盖率

保留 `gen_parity_sequences.cpp` 与现有 parity job：共同契约证明两个版本满足相同可观察行为，parity 验证既定抽样序列，两者互补。分布确定性对比沿用同一工具链下的现有约定。

在 coverage job 的采集阶段显式选择 `RandX.hpp` 与 `RandX_Cpp17.hpp`，使统计对象集中于生产源码。保持现有 80% 行覆盖率门禁，同时列出两份生产头文件各自的行与分支覆盖率明细；分支数据用于迁移前后比较，此方案不增加分支百分比或按单头文件分别达标的额外门禁。

迁移前按这一相同统计口径记录生产头文件基线，迁移后比较覆盖行与分支，避免用源码路径变化或测试自身覆盖掩盖回归。明确保留两个目标产生的覆盖数据并聚合，同时逐头文件核对覆盖丢失。

基线与迁移后的采集统一使用 GCC 14、gcov-14、LCOV 2.5、`-O0 -g --coverage` 编译选项及相同源码范围。根据 [LCOV 官方文档](https://github.com/linux-test-project/lcov/blob/master/docs/man/geninfo.rst)，LCOV 默认不采集分支数据，因此在采集与报告输出时均显式启用 `--branch-coverage`，使分支记录在整个处理链中得到保留。采集与报告命令采用以下形式：

```bash
lcov --capture --directory . --output-file coverage.info --gcov-tool gcov-14 --branch-coverage \
  --include "$PWD/RandX.hpp" --include "$PWD/RandX_Cpp17.hpp"
lcov --list coverage.info --branch-coverage
lcov --summary coverage.info --branch-coverage
```

检查报告中的源码文件范围，并确认两份生产头文件均包含行与分支记录；对缺失的数据先查明原因，再进行覆盖率比较。分别保存迁移前后的报告，比较同一生产源码行和分支的命中情况。

## 8. 验收标准

### 8.1 源码与注册

- 公共行为测试只有一份正文，两个目标的基础公共套件与用例注册清单完全一致；条件公共清单符合能力登记，支持同一能力的配置使用相同套件名与用例名。
- 原有用例按“公共、标准专属、平台条件、内部检查”登记归属；两份原始清单中的每一项都能追溯到终态测试。
- 合并重复用例可以减少总用例数，但原有可观察断言的覆盖范围必须保留。测试数量单独不作为覆盖等价的证明。
- 每个目标只定义一次 doctest main，每个适用的公共用例注册一次，以“套件名＋用例名”的出现次数核对。
- 公共正文通过 C++17 编译；C++23 特性在专属正文中编译；C++20 的条件能力验证继续执行。

### 8.2 行为与回归

- 完整 CMake/CTest 测试通过；各批次先运行迁移的套件，再运行两个目标的完整测试。
- 现有 GCC、Clang、MSVC 矩阵和已有 debug/release 执行路径通过。
- 七种 PRNG KAT、ChaCha20 RFC KAT 和跨标准 parity 通过。
- 生产源码按统一口径满足现有行覆盖率门禁；两份头文件的行与分支数据完整，覆盖丢失逐项解释并补齐。
- 用例在独立执行与完整套件执行时结果一致；默认引擎测试的状态不依赖执行顺序。

### 8.3 注册清单与顺序独立性检查

`tools/check_test_contracts.py` 为每个矩阵配置保存测试清单及其编译器、标准、平台和构建模式。工具执行 `--reporters=xml --list-test-cases`，直接从 XML 中读取套件名与用例名，建立“套件名＋用例名＋出现次数”的明文清单。命令选项参照 [doctest 官方文档](https://github.com/doctest/doctest/blob/master/doc/markdown/commandline.md)。比较时忽略输出顺序、源码路径和行号，保留名称与出现次数，并要求每个适用的公共用例恰好出现一次。

命令行工具的标准输出、标准错误及清单文件统一使用 UTF-8。

基础公共清单按相同工具链、平台与构建模式比较两个版本；条件公共清单按第 4 节的能力登记核对适用配置。比较使用明文记录，不使用哈希校验。迁移映射同时保留原有用例到终态断言的对应关系，注册清单负责验证用例装配，断言映射负责验证行为覆盖。

CI 各编译任务上传清单，由 `test-contracts` 任务运行清单工具单测并汇总核对。CI 通过可重复的 `--expected-group <编译器> <平台> <构建模式>` 参数声明 GCC、Clang、MSVC 的六个调试与发布分组，要求实际分组与预期完全一致，再核对每组的标准与注册内容。本地可省略该参数比较已有子矩阵，也可显式声明本次构建的分组。MSVC 的现有发布配置仅包含 C++17/C++23，`char8_t` 比较由其三个标准的调试配置完成。CMake 在找到 Python 3.10 或更新版本时注册清单检查；默认顺序与固定种子随机顺序检查始终注册。

每批迁移完成后，在两个目标中依次完成以下检查：

1. 用 `--test-suite=<套件名>` 单独运行迁移套件；对使用默认引擎状态的用例，再用 `--test-suite=<套件名> --test-case=<用例名>` 单独运行。
2. 按默认顺序运行完整测试程序。
3. 用 `--order-by=rand --rand-seed=<执行顺序种子>` 运行完整测试程序。执行顺序种子作为有说明的具名测试参数维护，在两个目标中使用相同值，并随验收结果保存以便复现。

三种执行方式均须通过。用例自行建立被测引擎状态；OS 熵源用例继续使用其平台条件与安全契约。以上检查复用现有测试程序。

Windows 命令行按中文名称筛选时需要与测试程序采用相同编码。独立用例验收也可使用 `--order-by=name --first=<序号> --last=<序号>`，并从 XML 确认实际执行一个用例；文件筛选可使用 ASCII 文件名，例如 `--source-file=*engine_contracts.hpp`。

在迁移后的试点阶段，做一次受控的检测验证：在临时测试编辑中将一个公共 KAT 期望值改为错误值，分别确认两个目标中的对应套件都失败；恢复正确值后重新通过。该检查验证共同正文确实进入两个目标，交付源码保留正确期望值。

## 9. 风险与处理

| 风险 | 处理 |
| --- | --- |
| C++23 语法随公共用例进入兼容目标 | 每批先编译 C++17；专属表达移到对应文件 |
| 合并时丢失某一版本额外断言 | 迁移映射以两版本原始测试的并集为依据 |
| 条件能力造成公共清单差异 | 基础清单严格一致，条件清单按能力表达式与适用矩阵配置核对 |
| helper、fixture 或套件注册发生名称碰撞 | 具名测试命名空间、包含保护及一次汇总包含 |
| 清单去重掩盖重复注册 | 按套件名与用例名记录出现次数，每个适用公共用例恰好出现一次 |
| CI 矩阵清单整组缺失 | 工作流显式声明六个预期分组，比较器核对实际与预期分组完全一致 |
| 公共测试为了复用而产生复杂转发 | 直接调用 `RandX` 公开 interface，复用输入和断言知识 |
| 内部检查被公共化后限制后续实现调整 | 保留独立 implementation 归属，并继续验证公开行为 |
| 默认引擎或 OS 熵源测试依赖全局顺序 | 用例自行建立状态；执行单独、完整及固定种子随机排序检查；沿用现有平台可用性条件和安全契约 |
| 统计迁移造成执行规模与容差变化 | 保留原有采样参数，集中具名常量及其依据 |
| 新目录变化没有触发 CI | 批次 A 同步更新两个事件的 `tests/**` 过滤 |
| 覆盖率分母随着源码迁移变化 | 迁移前后使用同一生产源码统计口径 |
| 分支记录在采集或处理中缺失 | 在 LCOV 处理链中显式启用分支覆盖率，核对两份头文件的数据完整性 |
