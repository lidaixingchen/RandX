# 开发与验证

本指南面向维护者，记录共同源码生成、构建、测试及诊断入口。用户安装与使用方式见 [README](../README.md)，发布操作见[发布流程](RELEASING.md)。以下命令从仓库根目录执行。

## 工具环境

使用支持目标语言标准的 C++ 编译器和 CMake；CMake 最低版本由根目录 `CMakeLists.txt` 声明。Python 维护工具使用 Miniconda 提供的 Python 3.12 或以上版本。示例中的 `conda run` 使用当前选定的 conda 环境，先确认 `conda run python --version` 满足要求。

Windows 使用已配置编译器及 CMake 的 PowerShell／开发者终端；MSVC 需支持项目当前 C++23 预览模式。MinGW 与 MSVC 使用不同构建目录。Ninja 单配置构建通过 `CMAKE_BUILD_TYPE` 选择模式，Visual Studio 等多配置构建通过 `--config` 和 CTest 的 `-C` 选择模式。

消费者只需头文件和对应平台链接依赖。维护工具与测试依赖不传播给消费者。启用 `RANDX_BUILD_BENCHMARK` 会获取 Google Benchmark，普通开发构建按任务需要启用该选项。

## 共同源码生成

维护入口是 `src/header_sources/targets.json`：共同定义在 `common/`，标准声明、约束与适配在 `cpp17/`、`cpp23/`。归属及展开上下文见[共同源码迁移清单](共同源码迁移清单.md)。

```powershell
conda run --no-capture-output python -X utf8 tools/generate_headers.py --write
conda run --no-capture-output python -X utf8 -m unittest discover -s tools -p 'test_*header*.py' -v
conda run --no-capture-output python -X utf8 tools/generate_headers.py --check
```

`--write` 用于来源修改后的产物更新；检查已有产物时直接执行单元测试与 `--check`。源码、生成器及两头文件改动在同一逻辑提交中交付。

定位生成头文件编译诊断时，输出逐行来源映射：

```powershell
conda run --no-capture-output python -X utf8 tools/generate_headers.py --map-dir build/header-maps
```

每个目标的映射记录目标与来源行区间，同一来源可能展开到两个目标。修改生成或映射机制时，按[发布流程中的维护演练](RELEASING.md#共同源码维护与发布检查)检查真实编译诊断。CMake 的 `RANDX_ENABLE_HEADER_TOOLS` 提供 `randx_generate_headers`、`randx_check_headers` 目标；默认关闭。

## 构建与测试

### Ninja 单配置构建

以下 PowerShell 命令使用当前工具链。激活 MSVC 开发者环境后可使用 MSVC；使用 MinGW／GCC 时应保证相应编译器在 PATH 中或在配置时指定 `CMAKE_CXX_COMPILER`。

```powershell
$taskPython = (conda run python -c 'import sys; print(sys.executable)').Trim()
cmake -S . -B build/dev-release -G Ninja -DCMAKE_BUILD_TYPE=Release -DRANDX_BUILD_TESTS=ON -DRANDX_BUILD_EXAMPLES=ON -DRANDX_ENABLE_HEADER_TOOLS=ON "-DPython3_EXECUTABLE=$taskPython"
cmake --build build/dev-release --target randx_check_headers
cmake --build build/dev-release
ctest --test-dir build/dev-release --output-on-failure
```

Debug 使用独立目录 `build/dev-debug` 和 `-DCMAKE_BUILD_TYPE=Debug`，其余选项及测试命令相同。Python 解释器显式传给 CMake，以便注册契约核对测试。

### Visual Studio 多配置构建

在支持项目当前 C++23 预览模式的 Visual Studio 开发者环境中运行；若安装了多个生成器，在首次配置时使用本机 `cmake --help` 列出的对应生成器。

```powershell
$taskPython = (conda run python -c 'import sys; print(sys.executable)').Trim()
cmake -S . -B build/dev-msvc -DRANDX_BUILD_TESTS=ON -DRANDX_BUILD_EXAMPLES=ON -DRANDX_ENABLE_HEADER_TOOLS=ON "-DPython3_EXECUTABLE=$taskPython"
cmake --build build/dev-msvc --config Debug --target randx_check_headers
cmake --build build/dev-msvc --config Debug
ctest --test-dir build/dev-msvc -C Debug --output-on-failure
cmake --build build/dev-msvc --config Release
ctest --test-dir build/dev-msvc -C Release --output-on-failure
```

此段采用 Visual Studio 生成器；如果环境变量指定了其他生成器，应在配置时显式选择 Visual Studio。项目测试配置负责 MSVC 的 `/std:c++23preview`，安装消费者按使用的头文件配置标准模式。

### 测试归属与完成条件

| 内容 | 维护位置 |
| --- | --- |
| 两标准共同公开行为 | `tests/common/` |
| 标准专属行为 | `tests/specific/` |
| 内部算法与能力约束 | `tests/implementation/` |
| 可复用材料及熵源脚本 | `tests/common/fixtures.hpp`、`tests/fixtures/` |
| 故障配置入口与跨翻译单元验证 | `tests/entropy/` |
| 生产默认引擎入口与共同跨翻译单元桥接 | `tests/default_engine/` |

`test_randx.cpp` 与 `test_randx_cpp17.cpp` 装配相应套件，公共测试写在共享正文中。修改前按[共享契约测试迁移清单](共享契约测试迁移清单.md)确定归属及条件能力守卫。

启用测试后，CTest 包含两标准普通测试、生产默认引擎测试、熵源故障测试及各自固定顺序重排；找到 Python 时还包含公共契约、默认引擎双标准、默认引擎生产／hook 配置及故障套件的注册核对。使用 `ctest --test-dir build/dev-release -N` 核对实际注册项。只直接编译两个普通入口不能替代这套验证。

统计测试按已定义的样本、容差及随机种子验证；修改算法时核对参数边界、输出范围和引擎消耗。涉及序列变化时编译 `gen_parity_sequences.cpp` 的两标准变体，按照 [CI 的 parity 任务](../.github/workflows/ci.yml)比较全部观测结果。

### 单独编译普通测试

以下为 Windows MinGW 的单入口调试命令：

```powershell
g++ -std=c++23 -O2 -Wall -Wextra -I third_party test_randx.cpp -o test_randx.exe -lbcrypt
./test_randx.exe
g++ -std=c++17 -O2 -Wall -Wextra -I third_party test_randx_cpp17.cpp -o test_randx_cpp17.exe -lbcrypt
./test_randx_cpp17.exe
```

Linux GCC／Clang 使用对应标准参数并省去 `-lbcrypt`；macOS 使用 `-framework Security`。CMake 自动传播平台链接依赖。

## 熵源测试与覆盖率

普通安全接口测试验证真实 OS 熵源。独立故障目标 `test_entropy_cpp17`、`test_entropy_cpp23` 通过私有测试宏制造失败、短读、中断及部分填充，覆盖同一填充实现和公开调用契约。CMake 为故障目标全部翻译单元配置一致的宏及线程依赖。

生产目标保持默认配置，故障宏只用于独立测试目标。实现与注入机制见[熵源失败测试方案](熵源失败测试方案.md)，实际平台验收见[验收结果](熵源失败测试验收结果.md)。

`test_default_engine_cpp17` 和 `test_default_engine_cpp23` 使用生产配置，验证默认引擎首次访问、播种、线程隔离和跨翻译单元实体。相同正文也进入两个故障目标。启用覆盖率时生产默认引擎目标进入生产采集目录，故障目标进入独立故障报告；全部翻译单元的 hook 宏保持一致。

修改熵源时，还需验证生产预处理产物和预处理检查工具：

```powershell
conda run --no-capture-output python -X utf8 -m unittest discover -s tools -p 'test_check_entropy_preprocessor.py' -v
conda run --no-capture-output python -X utf8 tools/check_entropy_preprocessor.py --compiler g++ --standard c++17 --header RandX_Cpp17.hpp --output build/entropy-production-cpp17.i
conda run --no-capture-output python -X utf8 tools/check_entropy_preprocessor.py --compiler g++ --standard c++23 --header RandX.hpp --output build/entropy-production-cpp23.i
```

覆盖率门禁以 [CI 的 coverage 任务](../.github/workflows/ci.yml)为权威流程：生产与故障程序分别构建、采集，并将生产头文件覆盖率作为门禁依据；故障报告独立记录熵源分支。`tools/inspect_entropy_coverage.py` 判断报告是否可合并并保留证据，合并结果用于辅助观测。

本地探索可启用 `RANDX_ENABLE_COVERAGE=ON`，使用 GCC／Clang 支持的覆盖率工具。`gcov` 必须匹配实际编译器版本；采集仅保留两份生产头文件。CMake 同时插桩普通与故障目标，因此直接扫描整个构建目录得到的汇总不能替代分离的生产门禁报告。正式验收采用工作流的分离目录、报告范围和阈值。

## 性能验证

普通测试构建保持基准选项关闭。需要测量时使用独立 Release 目录：

```powershell
cmake -S . -B build/benchmark-release -G Ninja -DCMAKE_BUILD_TYPE=Release -DRANDX_BUILD_BENCHMARK=ON
cmake --build build/benchmark-release --target benchmark_quick benchmark_gbench benchmark_gbench_default_cpp17 benchmark_gbench_sampling_cpp17 benchmark_gbench_sampling_cpp23
./build/benchmark-release/benchmark_quick.exe
./build/benchmark-release/benchmark_gbench.exe --benchmark_list_tests=true
```

多配置构建在构建命令中指定 `--config Release`，二进制通常位于其 `Release/` 子目录；Linux／macOS 路径省去 `.exe`。

正式回归比较以 `tools/benchmark_policy.json` 的组、轮数、计时和容差为准，由 `tools/benchmark_gate.py` 生成计划并求值，[Benchmark 工作流](../.github/workflows/benchmark.yml)通过适配层执行与发布结果。每组基线和候选在同一 runner、编译器及构建配置下测量；抽样组按既定规则完成确认运行。具体协议见[性能门禁策略](性能门禁策略集中方案.md)。

四个必需组为 `general`、`default_cpp17`、`sampling_cpp17`、`sampling_cpp23`。共同默认接口基准位于 `benchmarks/common/default_api_benchmarks.hpp`；C++23 装配到 general，C++17 装配到专用目标。C++17 组使用当前基准源码及历史基线的发布头文件在同一 runner 构建，首次接入即核对完整用例集合。

### 默认接口成对验收

使用当前同一份基准源码分别构建 C++17 和 C++23。两份头文件快照、MinGW 编译器与 CMake 路径解析、Miniconda Python 运行方式及完整重放命令见[整数生成性能修复验收结果的重放步骤](整数生成性能修复验收结果.md#重放成对验收)。

工具读取 general 的轮数、时长和容差，交替双边先后顺序，核对四个可执行文件及每轮完整名称集合，保留原始 JSON、编译命令、头文件来源、反汇编及中文报告。额外构建参数通过重复的 `--baseline-cmake-arg` 与 `--candidate-cmake-arg` 传入，两侧必须一致。退出码 0 表示比较通过，1 表示回归，2 表示数据或执行错误。新增用例第一次进入 general 时还没有历史数据，这份成对结果是独立验收材料。

初始化成本使用独立目标 `benchmark_gbench_initialization_cpp17`、`benchmark_gbench_initialization_cpp23` 观察：

```powershell
cmake --build build/benchmark-release --target benchmark_gbench_initialization_cpp17 benchmark_gbench_initialization_cpp23
./build/benchmark-release/benchmark_gbench_initialization_cpp17.exe --benchmark_out=build/initialization-cpp17.json --benchmark_out_format=json
./build/benchmark-release/benchmark_gbench_initialization_cpp23.exe --benchmark_out=build/initialization-cpp23.json --benchmark_out_format=json
```

观察在新线程到达同步点后测量首次默认引擎访问。JSON 的 `real_time` 记录手工计时的访问延迟，`thread_startup_ns` 与 `thread_gate_ns` 分别记录线程准备及唤醒开销。初始化目标独立于四组稳态回归门禁。

修改 Python 基准工具时运行相关单元测试，修改门禁或适配层时包含接线检查：

```powershell
conda run --no-capture-output python -X utf8 -m unittest discover -s tools -p 'test_*benchmark*.py' -v
conda run --no-capture-output python -X utf8 -m unittest discover -s tools -p 'test_compare_sampling.py' -v
conda run --no-capture-output python -X utf8 -m unittest discover -s tools -p 'test_confirm_sampling_benchmark.py' -v
node --test tools/test_benchmark_issue.cjs
```

测量报告保留完整套件、原始结果、配置及基线来源。不同架构分别比较，性能趋势展示读取现有报告。基准策略调整属于单独的设计与验证事项。

## CI 与按改动选择验证

| 改动范围 | 应覆盖的验证 |
| --- | --- |
| 生产来源、引擎、分布、抽样 | 生成检查、两标准 Debug／Release、相关契约及固定重排、注册核对；涉及序列时 parity，涉及性能时基准 |
| 熵源、ChaCha20 生命周期 | 普通与独立故障测试、生产预处理检查、跨翻译单元验证、平台路径与分离覆盖率 |
| 生成器、来源组织 | 生成器及归属测试、`--check`、诊断映射演练、独立头文件消费 |
| 测试正文与装配 | 对应标准测试、固定重排、公共及条件能力注册核对 |
| 基准工具、策略与工作流 | 对应工具测试、接线检查；影响测量协议时完整远端基准验收 |
| CMake、安装与包配置 | 相关构建、两标准消费者、安装消费及打包预演 |
| Markdown 文档 | 相对链接、标题锚点、示例与现有契约核对；修改可运行示例时编译验证 |

CI 的主矩阵包含 GCC、Clang、MSVC 及对应标准、构建模式；另有生成、工具测试、契约核对、parity、示例、覆盖率及 macOS 熵源任务。具体工具链版本、条件能力和触发路径直接查阅 [ci.yml](../.github/workflows/ci.yml)。统计质量、文档部署与打包预演分别查阅 [PractRand](../.github/workflows/practrand-nightly.yml)、[Docs](../.github/workflows/docs.yml)、[Packaging](../.github/workflows/packaging-validation.yml)。

验证汇报记录实际平台、标准、配置、运行命令与结果，区分本地检查和远端验收。文档改动本身不会保证全部工作流触发；判断依据为各工作流的实际路径过滤。
