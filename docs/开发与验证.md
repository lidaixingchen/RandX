# 开发与验证

本指南面向维护者，记录共同源码生成、构建、测试及诊断入口。用户安装与使用方式见 [README](../README.md)，发布操作见[发布流程](RELEASING.md)。以下命令从仓库根目录执行。

## 工具环境

使用支持目标语言标准的 C++ 编译器和 CMake；CMake 最低版本由根目录 `CMakeLists.txt` 声明。Python 维护工具使用 Miniconda 提供的 Python 3.12 或以上版本。示例中的 `conda run` 使用当前选定的 conda 环境，先确认 `conda run python --version` 满足要求。

Windows 的维护终端先设置 `$env:PYTHONUTF8 = '1'`，使 Python 工具启动的子进程也使用 UTF-8。Windows 使用已配置编译器及 CMake 的 PowerShell／开发者终端；MSVC 需支持项目当前 C++23 预览模式。MinGW 与 MSVC 使用不同构建目录。Ninja 单配置构建通过 `CMAKE_BUILD_TYPE` 选择模式，Visual Studio 等多配置构建通过 `--config` 和 CTest 的 `-C` 选择模式。

消费者只需头文件和对应平台链接依赖。维护工具与测试依赖不传播给消费者。启用 `RANDX_BUILD_BENCHMARK` 会获取 Google Benchmark，普通开发构建按任务需要启用该选项。

## 共同源码生成

维护入口是 `src/header_sources/targets.json`：共同定义在 `common/`，标准声明、约束与适配在 `cpp17/`、`cpp23/`。归属及展开上下文见[共同源码迁移清单](共同源码迁移清单.md)。

```powershell
conda run --no-capture-output python -X utf8 tools/generate_headers.py --write
conda run --no-capture-output python -X utf8 -m unittest discover -s tools -p 'test_*header*.py' -v
conda run --no-capture-output python -X utf8 tools/generate_headers.py --check
```

`--write` 用于来源修改后的产物更新；检查已有产物时直接执行单元测试与 `--check`。源码、生成器及两头文件改动在同一逻辑提交中交付。

定位生成头文件编译诊断时，输出逐行来源映射：

```powershell
conda run --no-capture-output python -X utf8 tools/generate_headers.py --map-dir build/header-maps
```

每个目标的映射记录目标与来源行区间，同一来源可能展开到两个目标。修改生成或映射机制时，按[发布流程中的维护演练](RELEASING.md#共同源码维护与发布检查)检查真实编译诊断。CMake 的 `RANDX_ENABLE_HEADER_TOOLS` 提供 `randx_generate_headers`、`randx_check_headers` 目标；默认关闭。

## 构建与测试

### Ninja 单配置构建

以下 PowerShell 命令使用当前工具链。激活 MSVC 开发者环境后可使用 MSVC；使用 MinGW／GCC 时应保证相应编译器在 PATH 中或在配置时指定 `CMAKE_CXX_COMPILER`。

```powershell
$taskPython = (conda run python -c 'import sys; print(sys.executable)').Trim()
cmake -S . -B build/dev-release -G Ninja -DCMAKE_BUILD_TYPE=Release -DRANDX_BUILD_TESTS=ON -DRANDX_BUILD_EXAMPLES=ON -DRANDX_ENABLE_HEADER_TOOLS=ON "-DPython3_EXECUTABLE=$taskPython"
cmake --build build/dev-release --target randx_check_headers
cmake --build build/dev-release
ctest --test-dir build/dev-release --output-on-failure
```

Debug 使用独立目录 `build/dev-debug` 和 `-DCMAKE_BUILD_TYPE=Debug`，其余选项及测试命令相同。Python 解释器显式传给 CMake，以便注册契约核对测试。

### Visual Studio 多配置构建

在支持项目当前 C++23 预览模式的 Visual Studio 开发者环境中运行；若安装了多个生成器，在首次配置时使用本机 `cmake --help` 列出的对应生成器。

```powershell
$taskPython = (conda run python -c 'import sys; print(sys.executable)').Trim()
cmake -S . -B build/dev-msvc -DRANDX_BUILD_TESTS=ON -DRANDX_BUILD_EXAMPLES=ON -DRANDX_ENABLE_HEADER_TOOLS=ON "-DPython3_EXECUTABLE=$taskPython"
cmake --build build/dev-msvc --config Debug --target randx_check_headers
cmake --build build/dev-msvc --config Debug
ctest --test-dir build/dev-msvc -C Debug --output-on-failure
cmake --build build/dev-msvc --config Release
ctest --test-dir build/dev-msvc -C Release --output-on-failure
```

此段采用 Visual Studio 生成器；如果环境变量指定了其他生成器，应在配置时显式选择 Visual Studio。项目测试配置负责 MSVC 的 `/std:c++23preview`，安装消费者按使用的头文件配置标准模式。

### 测试归属与完成条件

| 内容 | 维护位置 |
| --- | --- |
| 两标准共同公开行为 | `tests/common/` |
| 标准专属行为 | `tests/specific/` |
| 内部算法与能力约束 | `tests/implementation/` |
| 可复用材料及熵源脚本 | `tests/common/fixtures.hpp`、`tests/fixtures/` |
| 故障配置入口与跨翻译单元验证 | `tests/entropy/` |
| 生产默认引擎入口与共同跨翻译单元桥接 | `tests/default_engine/` |
| 安全擦除后端能力与跨翻译单元验证 | `tests/security/` |

`test_randx.cpp` 与 `test_randx_cpp17.cpp` 装配相应套件，公共测试写在共享正文中。修改前按[共享契约测试迁移清单](共享契约测试迁移清单.md)确定归属及条件能力守卫。

启用测试后，CTest 包含两标准普通测试、生产默认引擎测试、熵源故障测试、安全擦除能力测试及各自固定顺序重排；找到 Python 时还包含公共契约、默认引擎双标准、默认引擎生产／hook 配置及故障套件的注册核对。使用 `ctest --test-dir build/dev-release -N` 核对实际注册项。只直接编译两个普通入口不能替代这套验证。

找到 Python 时，CTest 还会注册 `test_build_tree_consumers` 和 `test_installed_consumers`。两项均用隔离的 CMake 消费者目录构建并运行 C++17、C++23 程序；安装树测试先安装到单独前缀，再从该前缀加载 `RandXConfig.cmake`，检查实际 `RandX_CONFIG`、导出目标的头文件归属及平台链接依赖。另一 RandX 构建树作为干扰前缀同时存在，缺少所选配置的负向探针必须在配置阶段失败。消费者调用普通分布、OS 熵初始化的 `ChaCha20` 和 `SecureSeed()`，确保 Windows bcrypt 与 macOS Security 能进入真实链接和运行验收。

```powershell
ctest --test-dir build/dev-release -R '^test_(build_tree|installed)_consumers$' --output-on-failure
conda run --no-capture-output python -X utf8 -m unittest discover -s tools -p 'test_validate_installed_consumers.py' -v
```

Visual Studio 多配置构建使用 `ctest --test-dir build/dev-msvc -C Debug -R '^test_(build_tree|installed)_consumers$' --output-on-failure`。主 CI 的消费者矩阵覆盖 Ubuntu、Windows 和 macOS；[打包验证工作流](../.github/workflows/packaging-validation.yml)对 vcpkg 的实际安装前缀及 toolchain 执行 CMake 消费者，对 xmake 则通过所安装的 package dependency 构建并运行，不要求 xmake 包导出 CMake 配置。

消费者继承父构建选择的生成器、编译器与构建程序；Windows 同时传递已解析的资源编译器和 manifest 工具路径。MSVC 消费者与示例采用 `/utf-8`；xmake 验收工程使用 2.8.2 起提供的 [`set_encodings("utf-8")`](https://xmake.io/zh/api/description/project-target.html#set-encodings) 配置。

消费者运行由 CTest 的目标测试完成，工具支持 `--ctest` 指定程序；默认优先选择 CMake 同目录的 CTest。交叉编译使用工具链中的 `CMAKE_CROSSCOMPILING_EMULATOR`，也可通过 `--crosscompiling-emulator` 传入 CMake 命令列表。父构建中的显式模拟器配置会传给子构建；模拟器在命名目标的 `add_test` 接线中生效。

统计测试按已定义的样本、容差及随机种子验证；修改算法时核对参数边界、输出范围和引擎消耗。涉及序列变化时编译 `gen_parity_sequences.cpp` 的两标准变体，按照 [CI 的 parity 任务](../.github/workflows/ci.yml)比较全部观测结果。

### 单独编译普通测试

以下为 Windows MinGW 的单入口调试命令：

```powershell
g++ -std=c++23 -O2 -Wall -Wextra -I third_party test_randx.cpp -o test_randx.exe -lbcrypt
./test_randx.exe
g++ -std=c++17 -O2 -Wall -Wextra -I third_party test_randx_cpp17.cpp -o test_randx_cpp17.exe -lbcrypt
```

## 流定位与整数分布类型验证

完整测试入口装配公共类型、实际实例化、自定义跳跃与大编号 `constexpr` 契约。GNU 编译器额外注册两标准扩展整数探针；根据 `__SIZEOF_INT128__` 判断该扩展能力。维护流定位材料时执行：

```powershell
conda run --no-capture-output python -X utf8 -m unittest discover -s tools -p 'test_generate_stream_jump_powers.py' -v
conda run --no-capture-output python -X utf8 tools/generate_stream_jump_powers.py --check
```

定位性能使用独立观察目标，测量轮次与最短时间读取集中策略的 `general` 组：

```powershell
cmake -S . -B build/stream-benchmark -DRANDX_BUILD_BENCHMARK=ON -DCMAKE_BUILD_TYPE=Release
cmake --build build/stream-benchmark --target randx_stream_initialization_benchmarks --parallel 2
conda run --no-capture-output python -X utf8 tools/observe_stream_initialization.py --binary build/stream-benchmark/randx_stream_initialization_benchmarks_cpp17.exe --output-dir build/stream-observations/cpp17
conda run --no-capture-output python -X utf8 tools/observe_stream_initialization.py --binary build/stream-benchmark/randx_stream_initialization_benchmarks_cpp23.exe --output-dir build/stream-observations/cpp23
```

观察记录包含编号位数、置位数、播种、连续建流、可执行文件大小，以及每次新进程中的首次调用。首次调用计时包含计时器开销，不包含进程启动时间，也不保证操作系统页面缓存冷态；小编号的纳秒级数据按该精度边界解释。Benchmark 工作流独立交付编译、链接时间和原始观察产物。现有性能组继续按原门禁执行。

## PractRand 计划与结果验证

目标长度、最早检查点和单引擎超时由 `tools/pract_rand/practrand_policy.json` 管理。quick 与默认 nightly 的目标均为 4 GiB，状态为 `runner_verified`；八个引擎的完整远端运行均已通过，运行器与时间预算证据见[项目功能改进方案](项目功能改进方案.md#114-远端验收)。该状态表示已登记规模的运行器可完成性，统计结论限于对应报告的引擎、种子策略、参数和检查长度。

```powershell
conda run --no-capture-output python -X utf8 -m unittest discover -s tools/pract_rand/tests -p 'test_*.py' -v
conda run --no-capture-output python -X utf8 tools/pract_rand/run_practrand.py --profile quick --plan-output build/practrand-plan.json
conda run --no-capture-output python -X utf8 tools/pract_rand/run_practrand.py --profile quick --engine sfc64 --output-json build/practrand-sfc64.json
```

计划冻结引擎、提交、位宽、种子策略与值、检查点、目标、超时和实际测试参数。GitHub Actions 矩阵只传引擎名，各任务下载冻结计划 JSON 并由 Python 读取对应项，保持 64 位整数种子精度。报告记录当前 RandX 提交，以及二进制同目录 `practrand-commit.txt` 的构建来源；缺少来源记录的外部二进制不能通过完整身份核对。构建脚本和工作流缓存共同交付该记录。

旧 `suspicious_count` 保持完整检查点中的最大单点计数；全程累计由 `run_suspicious_count` 和各检查点明细表达，截断尾部也保留可疑证据及日志位置。运行阶段与最终阶段均保存报告；超时、取消、缺少项目或身份差异在汇总中保留自身状态。Nightly 汇总产物与项目日志始终尝试上传，计划为空和汇总异常产生环境异常状态。

## 熵源测试与覆盖率

普通安全接口测试验证真实 OS 熵源。独立故障目标 `test_entropy_cpp17`、`test_entropy_cpp23` 通过私有测试宏制造失败、短读、中断及部分填充，覆盖同一填充实现和公开调用契约。CMake 为故障目标全部翻译单元配置一致的宏及线程依赖。

生产目标保持默认配置，故障宏只用于独立测试目标。实现与注入机制见[熵源失败测试方案](熵源失败测试方案.md)，实际平台验收见[验收结果](熵源失败测试验收结果.md)。

`test_default_engine_cpp17` 和 `test_default_engine_cpp23` 使用生产配置，验证默认引擎首次访问、播种、线程隔离和跨翻译单元实体。相同正文也进入两个故障目标。启用覆盖率时生产默认引擎目标进入生产采集目录，故障目标进入独立故障报告；全部翻译单元的 hook 宏保持一致。

修改熵源时，还需验证生产预处理产物和预处理检查工具：

```powershell
conda run --no-capture-output python -X utf8 -m unittest discover -s tools -p 'test_check_entropy_preprocessor.py' -v
conda run --no-capture-output python -X utf8 tools/check_entropy_preprocessor.py --compiler g++ --standard c++17 --header RandX_Cpp17.hpp --output build/entropy-production-cpp17.i
conda run --no-capture-output python -X utf8 tools/check_entropy_preprocessor.py --compiler g++ --standard c++23 --header RandX.hpp --output build/entropy-production-cpp23.i
```

覆盖率门禁以 [CI 的 coverage 任务](../.github/workflows/ci.yml)为权威流程：生产与故障程序分别构建、采集，并将生产头文件覆盖率作为门禁依据；故障报告独立记录熵源分支。`tools/inspect_entropy_coverage.py` 判断报告是否可合并并保留证据，合并结果用于辅助观测。

LCOV 的采集、列出、汇总及兼容合并命令统一采用 `--ignore-errors inconsistent`，将编译器行／分支命中记录的一致性诊断保留为日志警告，继续处理完整计数。生产行覆盖率仍由独立生产报告计算，并执行既定 80% 门禁；故障报告保持独立。诊断选项语义见 [LCOV 文档](https://github.com/linux-test-project/lcov/blob/master/docs/man/geninfo.rst)。

本地探索可启用 `RANDX_ENABLE_COVERAGE=ON`，使用 GCC／Clang 支持的覆盖率工具。`gcov` 必须匹配实际编译器版本；采集仅保留两份生产头文件。CMake 同时插桩普通与故障目标，因此直接扫描整个构建目录得到的汇总不能替代分离的生产门禁报告。正式验收采用工作流的分离目录、报告范围和阈值。

## 安全擦除配置与审计

生产构建默认按平台选择安全擦除后端。`RANDX_USE_PORTABLE_SECURE_WIPE=ON` 统一选择兼容实现；Apple 构建可通过 `RANDX_USE_APPLE_MEMSET_S=ON` 请求 `memset_s`。CMake 将启用的宏传播到 `RandX`、`RandX_Cpp17` 与 `RandX_Cpp23` 三个 INTERFACE 目标；Apple 选项还统一定义 `__STDC_WANT_LIB_EXT1__=1`。同一程序中所有包含 RandX 的翻译单元、静态库和预编译头都须采用相同配置。直接包含头文件时，应以目标级或全局编译选项统一设置宏，并确保 Apple 扩展声明在系统头之前生效。

CTest 的 `test_secure_wipe_capabilities_cpp17_*` 与 `test_secure_wipe_capabilities_cpp23_*` 目标编译 `tests/security/secure_wipe_capabilities.cpp` 和 `secure_wipe_cross_translation_unit.cpp`。每个程序都核对零长度、非对齐范围、区间外字节及跨翻译单元生命周期，并输出实际后端名称。C++17 目标统一定义 `RANDX_SECURITY_CPP17`；交叉翻译单元源单独预包含系统头，验证另一翻译单元的包含顺序。Linux 构建的 native 目标启用 glibc 扩展声明；另有显式 portable 目标。Apple 构建另设默认与 `memset_s` opt-in 目标。

优化审计使用 `tests/security/secure_wipe_codegen.cpp` 的运行时探针，审阅 Release 与 LTO 最终链接产物及反汇编，覆盖直接擦除、局部守卫、ChaCha20 生成区块、重播种、移动和析构。工具实现位于 `tools/check_secure_wipe_codegen.py`；应按其实际 CLI 执行两种标准与各登记后端配置，并保留编译器诊断、链接产物、反汇编、探针映射和失败日志。CI 工具单测和审计矩阵是本任务接线的一部分，具体调用方式随脚本接口维护。

## 性能验证

普通测试构建保持基准选项关闭。需要测量时使用独立 Release 目录：

```powershell
cmake -S . -B build/benchmark-release -G Ninja -DCMAKE_BUILD_TYPE=Release -DRANDX_BUILD_BENCHMARK=ON
cmake --build build/benchmark-release --target benchmark_quick benchmark_gbench benchmark_gbench_default_cpp17 benchmark_gbench_sampling_cpp17 benchmark_gbench_sampling_cpp23 benchmark_gbench_triangular_cpp17 benchmark_gbench_triangular_cpp23
./build/benchmark-release/benchmark_quick.exe
./build/benchmark-release/benchmark_gbench.exe --benchmark_list_tests=true
./build/benchmark-release/benchmark_gbench_triangular_cpp17.exe --benchmark_out=build/triangular-cpp17.json --benchmark_out_format=json
./build/benchmark-release/benchmark_gbench_triangular_cpp23.exe --benchmark_out=build/triangular-cpp23.json --benchmark_out_format=json
```

多配置构建在构建命令中指定 `--config Release`，二进制通常位于其 `Release/` 子目录；Linux／macOS 路径省去 `.exe`。

正式回归比较以 `tools/benchmark_policy.json` 的组、轮数、计时和容差为准，由 `tools/benchmark_gate.py` 生成计划并求值，[Benchmark 工作流](../.github/workflows/benchmark.yml)通过适配层执行与发布结果。每组基线和候选在同一 runner、编译器及构建配置下测量；抽样组按既定规则完成确认运行。具体协议见[性能门禁策略](性能门禁策略集中方案.md)。

当前水库基线为 `c359538af33d222ef7a85a62affa9f38a77e4cc2`：按实际输入增长容量，使用独立 64 位计数。CI 的固定抽样行为参照与性能策略的初始抽样回退参照均指向该提交。性能测量优先使用成功发布的 `benchmark-baseline` 产物所对应的提交，并通过目标分支上 `force_update_baseline=true` 的手动 Benchmark 运行刷新产物；刷新完成后再以普通模式核对四组比较及其基线来源。轮数、计时、确认规则和 25% 容差保持集中策略配置。

四个必需组为 `general`、`default_cpp17`、`sampling_cpp17`、`sampling_cpp23`。共同默认接口基准位于 `benchmarks/common/default_api_benchmarks.hpp`；C++23 通过独立编译单元装配到 general，C++17 装配到专用目标。general 与 C++17 默认接口组使用当前基准源码及各自历史基线的发布头文件在同一 runner 构建，首次接入即核对完整用例集合。

三角分布性能使用单独的 `benchmark_gbench_triangular_cpp17` 与 `benchmark_gbench_triangular_cpp23` 目标，分别编译两份发布头文件。用例覆盖对称、左右偏斜、两端点众数和退化路径，以 float／double 搭配 32／64 位引擎；三个参数作为完整数组在计时前观察，结果通过可写局部变量观察。JSON 中的 `engine_calls_per_sample` 记录每个样本实际取得的引擎输出次数，基准同时核对实际消耗。测量后运行 `tools/check_triangular_benchmark.py <结果.json> --repetitions <策略轮数>`，核对全部 24 个场景、重复集合及消耗，并拒绝测量错误。此新功能没有历史值，单独报告首轮结果；现有四组回归门禁及其历史基线范围保持原策略。

链表抽样输入使用共同的标准库 PMR 夹具：容量由实际标准库分配请求推导，百万节点在连续内存资源中构建，播种与输入构建均在计时外完成。general 和两标准 sampling 组复用该夹具，基线与候选使用相同基准源码、输入规模和固定种子。

抽样基准逐轮通过可写局部变量观察返回长度和元素存储指针；非空结果在观察指针后执行 `ClobberMemory()`，使元素写入对编译器可见。请求数量在一次测量期间固定，在计时前通过可写变量的 `DoNotOptimize()` 观察；容器析构包含在每轮计时迭代内。双边使用相同基准正文和构建配置，保留空请求及全部正样本用例。屏障语义见 [Google Benchmark v1.8.5 官方指南](https://github.com/google/benchmark/blob/v1.8.5/docs/user_guide.md#preventing-optimization)。

### 默认接口成对验收

使用当前同一份基准源码分别构建 C++17 和 C++23。两份头文件快照、MinGW 编译器与 CMake 路径解析、Miniconda Python 运行方式及完整重放命令见[整数生成性能修复验收结果的重放步骤](整数生成性能修复验收结果.md#重放成对验收)。

工具读取 general 的轮数、时长和容差，交替双边先后顺序，核对四个可执行文件及每轮完整名称集合，保留原始 JSON、编译命令、头文件来源、反汇编及中文报告。额外构建参数通过重复的 `--baseline-cmake-arg` 与 `--candidate-cmake-arg` 传入，两侧必须一致。退出码 0 表示比较通过，1 表示回归，2 表示数据或执行错误。新增用例第一次进入 general 时还没有历史数据，这份成对结果是独立验收材料。

初始化成本使用独立目标 `benchmark_gbench_initialization_cpp17`、`benchmark_gbench_initialization_cpp23` 观察：

```powershell
cmake --build build/benchmark-release --target benchmark_gbench_initialization_cpp17 benchmark_gbench_initialization_cpp23
./build/benchmark-release/benchmark_gbench_initialization_cpp17.exe --benchmark_out=build/initialization-cpp17.json --benchmark_out_format=json
./build/benchmark-release/benchmark_gbench_initialization_cpp23.exe --benchmark_out=build/initialization-cpp23.json --benchmark_out_format=json
```

观察在新线程到达同步点后测量首次默认引擎访问。JSON 的 `real_time` 记录手工计时的访问延迟，`thread_startup_ns` 与 `thread_gate_ns` 分别记录线程准备及唤醒开销。初始化目标独立于四组稳态回归门禁。

修改 Python 基准工具时运行相关单元测试，修改门禁或适配层时包含接线检查：

```powershell
conda run --no-capture-output python -X utf8 -m unittest discover -s tools -p 'test_*benchmark*.py' -v
conda run --no-capture-output python -X utf8 -m unittest discover -s tools -p 'test_compare_sampling.py' -v
conda run --no-capture-output python -X utf8 -m unittest discover -s tools -p 'test_confirm_sampling_benchmark.py' -v
node --test tools/test_benchmark_issue.cjs
```

测量报告保留完整套件、原始结果、配置及基线来源。不同架构分别比较，性能趋势展示读取现有报告。基准策略调整属于单独的设计与验证事项。

## 三角分布数值验证

增量验证复用完整入口中的契约正文，并以较小编译单元执行：

```powershell
cmake --build build/dev-release --target test_triangular_cpp17 test_triangular_cpp23 gen_triangular_cpp17 gen_triangular_cpp23 --parallel 1
ctest --test-dir build/dev-release -R '^test_triangular_' --output-on-failure
conda run --no-capture-output python -X utf8 tools/generate_triangular_reference.py --check
conda run --no-capture-output python -X utf8 -m unittest discover -s tools -p 'test_generate_triangular_reference.py' -v
```

参考生成器使用 Python 标准库 Decimal 与精确 Fraction，从参数的实际二进制值生成参考，逐级增加精度并用独立 CDF 回代核对。生成后先施加返回类型舍入和半开上界纠正。普通区间按 ULP 检查；宽度达到最小正规数的跨零区间按宽度归一化绝对误差检查，同号极端端点众数按局部 ULP 检查；次正规宽度限制为一个实际量化间距，相邻端点要求离散结果一致。边界及单调性独立断言。

统计样本量为每组 65,536，16 个等宽分箱，三类型、两引擎、五个众数共 540 项比较。整体误报参数为 `1e-6`，使用 Bernstein 界与 union bound；二阶矩偏差界使用独立解析四阶矩。均匀网格与输出舍入偏差分别计入阈值，阈值不随测试结果调整。

擦除最终产物审计：

```powershell
conda run --no-capture-output python -X utf8 tools/check_secure_wipe_codegen.py --compiler g++ --disassembler objdump --standard both --optimization both --backend both --verify-mutations
conda run --no-capture-output python -X utf8 -m unittest discover -s tools -p 'test_check_secure_wipe_codegen.py' -v
```

当前已登记规则为 Windows x64 MinGW GCC 16.1.0。退出码 0 为通过，1 为失败，2 为无法判定；其他编译器、ABI 或版本须完成对应机器码规则及变异确认，不能因功能测试通过登记为优化擦除通过。证据目录保留编译命令、编译器信息、执行日志、最终反汇编、PE 异常表、DWARF 数组存储位置及逐项路径判断。运行脚本只启动一个编译器进程。

`RandTriangular` 的公开契约在两标准普通测试中共同注册；纯数值辅助函数的边界与参考值测试放入内部契约。固定种子 parity 在 GCC 14 的 C++17／C++23 两个构建中逐字节比较 float／double 样本和调用后的完整引擎状态，覆盖 32／64 位引擎、对称与偏斜、端点众数及退化区间。其他工具链分别运行独立的数值契约，使用预先冻结的高精度参考与容差；long double 按平台有效精度登记，不跨不同浮点格式逐字节比较。

精度验收采用舍入到最近值及渐进下溢，编译使用 GCC／Clang 的标准浮点选项或 MSVC `/fp:precise`。`fast-math`、FTZ／DAZ 和其他舍入模式不属于本次数值精度验收条件。非法参数及退化输入须确认引擎调用次数为零；正常采样调用一次 `RandCanonical<T>`，其实际引擎输出数依类型和引擎位宽而定。

## 分布复用示例验证

启用 `RANDX_BUILD_EXAMPLES` 后，同一 `examples/distribution_generation.cpp` 来源生成 `example_distribution_generation_cpp17` 和 `example_distribution_generation_cpp23`，分别包含对应版本的发布头文件。示例覆盖分布引用复用、连续分批、输出迭代器、具名分布函数及默认引擎获取位置。

```powershell
cmake -S . -B build/distribution-examples-release -G Ninja -DCMAKE_BUILD_TYPE=Release -DRANDX_BUILD_EXAMPLES=ON
cmake --build build/distribution-examples-release --target example_distribution_generation_cpp17 example_distribution_generation_cpp23
& ./build/distribution-examples-release/example_distribution_generation_cpp17.exe
& ./build/distribution-examples-release/example_distribution_generation_cpp23.exe
```

Debug 使用独立目录 `build/distribution-examples-debug` 和 `-DCMAKE_BUILD_TYPE=Debug`。在已配置的编译器环境中执行；Visual Studio 构建采用相应 `--config` 及配置子目录，Linux 可执行文件省略 `.exe`。

两版本的固定种子输出应一致。示例对随机播种的默认引擎仅报告输出数量。CI 的示例任务在构建后运行两个目标；本地结果与远端矩阵结果分别登记。参数与状态规则见 [API](API.md#分布复用与标准库批量生成)，范围与验收见[方案](分布扩展与批量生成改进方案.md)。
