# 整数生成性能修复方案

日期：2026 年 10 月 4 日

源码审阅基点：`a773584`。实验基点、编译配置与原始数据见[整数生成性能研究](整数生成性能研究.md)。实施前保存当时的头文件快照，并在相同工具链下重新建立比较基线。

状态：生产实现、共享契约、基准与工作流接线已完成；实际验证范围和数据见[整数生成性能修复验收结果](整数生成性能修复验收结果.md)。

## 1. 目标与明确判断

将默认引擎首次播种和状态构造集中到一个内部辅助函数，限制初始化代码进入常用接口的展开规模，使普通业务包装函数更容易被编译器内联。同时补齐两标准默认整数入口的持续性能门禁，以及生产配置和熵源 hook 配置下的默认引擎跨翻译单元契约测试。

本次已经证实的主要问题，是 GCC 在特定调用形态下保留了逐次抽样的函数调用。`DefaultEngine()` 中的首次构造代码影响内联成本判断，进而增加热循环的调用、寄存器保存恢复及状态访问成本。内联还允许优化器将引擎状态保留在寄存器中，减少逐次 TLS 状态读写；实测收益包含这些连带优化。修复的直接对象是这条因果链。

当前证据支持局部调整默认引擎的初始化边界。`RandInt` 的公开签名、默认引擎、整数分布算法及引擎输出消费规则继续沿用现有实现。调用者仍直接包含对应语言标准的一份发布头文件；修复不增加消费者的下载、编译配置或初始化步骤。

产品比较继续分别使用 RandX 和 effolkronium/random 各自的默认接口与默认引擎。`random_static` 和 `random_thread_local` 分别列出，其共享状态语义与线程局部状态语义影响适用条件。将另一库接到 RandX 引擎上的组合，仅能用于拆分引擎和接口成本，不作为独立产品比较的结论。

## 2. 根因与证据强度

### 2.1 从实际执行成本出发

一次整数生成的热路径包含引擎取值、无偏区间映射、最终结果构造，以及未被优化掉的入口访问成本。首次调用还需要取得种子并构造引擎状态。即使计时前已经完成初始化，编译器在决定是否内联时，仍可能把首次初始化分支纳入函数大小估算。

研究基准中的普通业务函数 `Dice()` 调用默认 `RandInt(1,6)`。GCC 的拒绝内联诊断为 `max-inline-insns-auto limit reached`，其热循环仍包含 `call Dice`。相同测试框架中的对照库包装函数已被内联。

`RandomSeed()` 已采用平台对应的不可内联属性，但是它只隔离了种子获取。返回种子之后，xoshiro256 的四字状态扩展仍可展开进 `DefaultEngine()` 和上层调用者。因此本次设计覆盖完整的引擎构造，而不是只继续压缩熵源获取函数。

### 2.2 单因素实验支持的修复方向

同一台 Ryzen 7 5800H、MinGW GCC 16.1.0、C++23、`-O3 -DNDEBUG`，九轮测量：

| 调用形态 | 中位数 ns/次 | 最小–最大 ns/次 | 已验证事实 |
| --- | ---: | ---: | --- |
| 原版普通业务包装函数 | 3.206 | 3.128–3.369 | 热循环保留逐次 `call Dice` |
| 仅对研究包装函数施加内联属性 | 1.108 | 1.096–1.125 | 内联决策足以解释主要差距 |
| 仅隔离完整首次引擎构造的原型 | 1.108 | 1.091–1.179 | 普通包装函数获得内联，算法保持原样 |
| 对照库默认静态入口 | 1.903 | 1.879–2.004 | 独立产品对照 |

冷路径隔离原型的耗时降低约 65.4%，吞吐约为原来的 2.89 倍。这是指定机器和构建配置的实测结果；正式实现必须重新测量。该独立产品对照程序在 GCC 14、Clang 和 MSVC 下的收益幅度尚未测量；持续门禁的实际平台与结果见验收记录。

同一工具链和固定种子下，原型与原版前 20,000 个骰子结果以及最终序列化状态逐项相同。这项检查支持本次代码组织调整的序列保持，完整契约验收见第 5 节。

### 2.3 整数映射的定位

本机 libstdc++ 对满范围 64 位引擎已经采用 Lemire 乘积映射与拒绝采样。骰子区间的拒绝概率为 `4 / 2^64`，内联后的热循环没有常规整数除法，拒绝概率无法解释原来约 2 ns 的差距。

独立热循环中，默认整数入口为 1.126 ns/次，局部引擎加标准库分布为 1.196 ns/次，等价手写 Lemire 为 1.137 ns/次。运行时上界的默认入口为 1.712 ns/次。这些数据说明调用形态与端点可见性需要分别测量；现有证据尚不能把动态端点的全部差距归于某一项检查或某一条指令。

无偏映射原理见 [Lemire 原论文](https://arxiv.org/abs/1805.10941)，概率与端点契约见 [C++ 工作草案](https://eel.is/c++draft/rand.dist.uni.int)。具体 libstdc++ 分支与汇编摘录已保存在研究材料中。

## 3. 修复设计

### 3.1 内部构造边界

新增 `RandX::detail::CreateDefaultEngine()`，返回 `Xoshiro256StarStar` 值。函数内部执行一次 `RandomSeed()`，用所得种子直接构造返回对象。函数使用 `inline` 保持纯头文件的多翻译单元定义规则，并使用平台对应的不可内联属性隔离完整构造过程。

`DefaultEngine()` 继续持有原有的函数局部 `thread_local Xoshiro256StarStar`。其初始化表达式改为调用内部构造函数，随后继续返回该对象的左值引用。热入口保持普通 `inline`，让优化器根据调用现场决定展开方式。

C++ 的 `inline` 多重定义规则与编译器是否展开函数是两个层面的约束；二者可以同时采用。[C++ 工作草案 inline 规则](https://eel.is/c++draft/dcl.inline)明确允许对应实体在多个翻译单元定义，并保留函数体内静态对象的实体一致性。平台属性负责控制代码生成，不改变这个实体规则。

构造函数本身不持有 TLS 对象或额外缓存。返回值采用直接构造的同类型纯右值，适配 C++17 与 C++23。实现继续使用现有异常规格，使对象初始化完成时机和初始化异常的传播规则沿用当前契约。[局部静态及线程局部初始化规则](https://eel.is/c++draft/stmt.dcl)

### 3.2 编译器适配

沿用当前 `RandomSeed()` 的属性选择方式，直接放在新辅助函数声明上：

| 编译环境 | 辅助函数属性 | 约束 |
| --- | --- | --- |
| `_MSC_VER`，包括对应兼容模式 | `__declspec(noinline)` | 优先采用现有 MSVC 分支 |
| GCC 或 Clang 的 GNU 兼容模式 | `__attribute__((noinline))` | 覆盖当前 MinGW、Linux GCC 与 Clang |
| 其他编译器 | 普通 `inline` | 保持可编译性，性能改善需要单独确认 |

该局部声明可以复用现有写法，不需要引入公共配置宏。新辅助函数放在 `detail`，公开 `DefaultEngine()` 的 `[[nodiscard]]`、文档注释和返回类型仍准确附着于原接口。

[GCC 属性文档](https://gcc.gnu.org/onlinedocs/gcc/Common-Attributes.html#Function-Attributes)与 [Clang 属性文档](https://clang.llvm.org/docs/AttributeReference.html#noinline)说明 `noinline` 的作用；[MSVC 文档](https://learn.microsoft.com/en-us/cpp/cpp/noinline?view=msvc-170)也明确指出，把低频函数隔离后，调用者可因体积缩小而更适合内联。具体效果以各工具链生成的代码为准。

### 3.3 共享来源与双头文件

当前发布头文件由 `src/header_sources` 维护来源生成。新增共同片段 `common/engines/create_default_engine_definition.inc`，其中包含完整的 `detail` 命名空间块和辅助函数定义。

两个 `security_and_seeding.inc` 在共同的 `random_seed_definition.inc` 之后、`DefaultEngine()` 的公开文档注释之前插入该片段。这样既保证 `RandomSeed()` 已经定义，也保持公开注释与 `[[nodiscard]]` 的归属。共同的 `default_engine_definition.inc` 只调整线程局部对象的初始化表达式。

使用现有生成器更新 `RandX.hpp` 和 `RandX_Cpp17.hpp`，再运行 `--check`。共享来源、标准模板和两份交付产物属于同一项实现变更，应一并审阅和提交。

### 3.4 对其他默认接口的影响

`RandReal`、分布、洗牌、抽样等默认入口也通过 `DefaultEngine()` 取得状态。变化集中在共同入口的代码生成，因此整数以外的默认接口必须参加性能回归验收。

既有九轮原型结果如下，标量单位为 ns/次，容器操作单位为 ns/整个操作：

| 项目 | 原版中位数 | 原型中位数 | 当前判断 |
| --- | ---: | ---: | --- |
| 均匀浮点 | 0.974 | 0.971 | 变化很小 |
| 正态分布 | 19.888 | 19.645 | 变化很小 |
| 洗牌 | 1266.940 | 1010.900 | 本调用形态中出现改善，需正式复测 |
| 抽样 | 6049.000 | 6064.000 | 波动区间较宽，收益尚未确认 |

这些结果用于识别影响范围，不替代正式门禁。首次调用增加的辅助函数调用属于一次初始化成本，应与稳态吞吐分开记录。

### 容器与稀疏小样本路径

容器入口在零请求和空范围返回后才获取默认引擎，数量转换与位图选择由共同片段装配，后续复用公开迭代器路径。随机访问迭代器及容器适配入口共同使用现有抽样内联策略，使空输入早退、边界检查和策略选择在调用点展开。完整复制和哈希去重保持独立操作边界；稠密索引遍历按引擎输出范围选择调用边界：完整 64 位引擎在调用点展开，使编译器能够在循环中保留引擎状态；其他引擎保持独立内核。稀疏抽样中，一个或两个索引使用容量为二的定长存储，每次重抽至多比较一个已接受索引，省去哈希桶和节点的分配。更大样本沿用现有哈希集合路径。小样本辅助函数保持独立调用边界，限制通用内核的展开规模。

完整复制对可平凡复制的元素和原生指针、标准 `vector` 迭代器使用范围构造，保留标准库的批量复制能力；其他来源沿用预留容量后的索引复制。单元素完整复制在适配层直接完成，分配仍先于元素访问。稠密内核按公开入口校验后的请求数量运行，每步区间由当前索引与总体大小构造。位图路径在调用点展开。共同分布辅助函数在位图和蓄水池路径中，对覆盖分布整数类型完整范围的引擎局部展开标准库调用；分布算法、对象生命周期和随机消耗保持原有契约。默认洗牌由标准专属操作内核承担，沿用各标准的洗牌 API；GCC／Clang 将公开入口与标准库调用展开到调用点，使容器、引擎与循环信息同时可见。空请求先直接返回。

该路径沿用对应入口的分布生命周期、随机抽取消耗、重复重抽和接受顺序；结果容量在首次抽取前准备，接受索引后才访问和复制源元素。共享契约验证碰撞重抽、输出顺序、默认引擎最终状态和复制异常时的进度。性能验收继续覆盖全部抽样用例及现有确认测量策略。

上述采样与洗牌的调用边界描述当前实现，性能依据限于实际测量的工具链和工作负载。引擎输出范围本身不能决定整个稠密函数的最优内联方式；集成门禁通过也不能证明每条强制内联、局部展开或上界假设的独立收益。[性能策略评估](整数生成性能策略评估.md)给出按契约、编译器机制及测量证据区分的判断，并记录普通稠密内联边界的独立对照。稠密调用边界的收敛需保持其他因素一致，经过完整门禁验收后采用。

生产改动围绕默认引擎构造及入口；熵源回退实现、整数映射实现和其他引擎构造函数继续作为现有依赖使用。

## 5. 行为与兼容性验收

### 5.1 序列和状态

- 以现有具名种子构造显式 xoshiro256 引擎，同时对默认引擎执行 `Reseed(seed)`；比较对应整数输出及最终序列化状态。
- 范围覆盖 `[1,6]`、大小为二的幂的区间、单值区间、跨零有符号区间，以及完整有符号和无符号整数范围；端点从具名案例及 `numeric_limits` 推导。
- 检查默认原始输出与同种子局部引擎一致，并复用当前 `RandInt` 参数契约测试。
- 对修复前后的头文件快照运行同一套序列比较程序，逐项比较输出和最终状态。输入、编译器、标准库、构建选项及各 API 调用顺序保持一致。
- 执行现有跨标准序列 parity。标准库分布没有跨不同标准库实现的逐值统一保证，因此各平台分别对自己的修复前基线验收。

正式对比使用结果值与状态数组，不以哈希摘要代替。案例规模采用具名测试参数；比较规模与运行命令记录到验收材料。

### 5.2 线程与翻译单元

- 同一线程在主测试翻译单元和桥接翻译单元取得 `DefaultEngine()`，地址应一致。通过其中一个翻译单元播种，另一个生成的结果与相同种子的局部引擎一致。
- 在新线程中首次获取默认引擎；在该线程存活期间完成跨翻译单元地址和状态观察，线程结束前保持引用使用有效。
- 主线程与工作线程分别播种、推进状态并同步观察。工作线程操作完成后，主线程序列继续与自己的参考引擎一致，以确定性状态检查证明线程隔离。
- 不把“两个随机输出恰好不同”作为线程隔离的判据；地址比较也必须在两个线程都存活时完成。
- 在线程内部连续访问默认引擎，确认已播种状态不会在后续访问中被覆盖。保留 `Reseed`、`ReseedRandom` 与 `ResetThreadLocalEngine` 的现有调用时序，运行现有相关契约。

新鲜线程首次调用的可用性需要单独覆盖。OS 熵 hook 只能观察某条来源路径，硬件 RNG 可能提前成功；因此不能用 OS hook 调用次数来宣称测出了默认引擎的初始化总次数。熵源优先级与失败回退继续由 `RandomSeedWithSources` 的现有可控来源测试验证。

上述跨翻译单元、首次访问及线程隔离契约必须在生产与 hook 两种配置中实际运行。共享套件不依赖故障脚本或 hook 调用计数；故障入口装配时保证熵源脚本在用例边界复位，随机排序仍能通过。验收分别记录四个目标的执行与注册核对结果。

### 5.3 构建和分发

- GCC、Clang、MSVC 的现有 CI 矩阵，包含兼容头的 C++17/C++20 和主头的 C++23；现有 Apple Clang 验收路径一并运行。
- Debug 与 Release、普通排序与固定种子重排测试均通过，新公共套件在两标准、两配置的对应注册清单中出现且一致。
- 共享来源生成检查、来源测试、诊断映射检查和现有覆盖率门禁通过。
- 现有示例及单头消费者构建通过；生产配置的双翻译单元目标和启用熵源测试 hook 的目标均完成编译、链接与运行。

两标准生产默认引擎目标按现有覆盖率选项插桩，并在 CI 的生产覆盖率采集目录中构建、执行和汇总。故障目标继续进入独立故障报告；生产阈值按实际生产报告判断。

## 6. 性能验收设计

### 6.1 补齐调用形态

现有 `BM_EngineRandInt` 使用显式局部引擎，无法观测默认入口的首次构造分支影响。保留它作为原始引擎和映射的参照，新增以下默认接口用例：

| 维度 | 案例 | 要回答的问题 |
| --- | --- | --- |
| 入口 | 直接默认入口、普通业务包装函数 | 冷路径缩小是否解决本次内联问题 |
| 状态访问 | 默认入口、计时前缓存引擎引用、显式局部引擎 | TLS 访问与优化的实际差别 |
| 端点 | 常量骰子、常量二的幂区间、运行时端点 | 内联收益是否依赖端点可见性 |
| 类型 | `int`、`uint32_t`、`uint64_t` | 目标位宽与满范围路径有无回退 |
| 相关 API | 默认均匀浮点、正态、洗牌、抽样 | 共同入口变化是否产生回归 |

运行时端点从 Google Benchmark 的参数输入获取；常量案例使用具名常量，并验证生成代码确实保留了预期的端点可见性差异。

普通业务包装函数的定义在同一翻译单元可见，维持普通函数形式，让编译器自行决定是否内联。跨翻译单元且关闭 LTO 的业务包装函数，本来就可能保留外部调用，应另列适用条件。

计时前完成默认引擎首次访问与固定播种，并执行充分预热。测量内循环累积结果，在批次边界使用 `DoNotOptimize`；保留已有逐值屏障基准，分别解释两种观测方式的成本。基准源码中对热包装函数施加强制属性会改变待测问题，因此正式基准采用普通声明。

迭代数、批次长度、端点和播种值使用具名参数或现有基准配置。初始化延迟由 `benchmark_gbench_initialization_cpp17`、`benchmark_gbench_initialization_cpp23` 独立测量：在新线程已启动并到达同步点后计时首次访问，明确同步开销。观察目标使用手工计时的 `real_time`，独立于四组稳态门禁。

上述默认接口用例及具名参数共同维护在 `benchmarks/common/default_api_benchmarks.hpp`，采用两个标准均支持的接口。C++23 通过独立编译单元装配到 general，C++17 专用入口装配同一正文；共同用例名称使用 `BM_Default` 前缀，语言标准记录在组元数据中。两标准枚举出的共同用例集合须一致，性能数值分别与各自基线比较。

抽样基准逐轮通过可写局部变量观察返回长度和元素存储指针；非空结果在观察指针后执行 `ClobberMemory()`，使元素写入对编译器可见。请求数量在一次测量期间固定，在计时前通过可写变量的 `DoNotOptimize()` 观察；容器析构包含在每轮计时迭代内。双边使用相同基准正文和构建配置，保留空请求及全部正样本用例。屏障语义见 [Google Benchmark v1.8.5 官方指南](https://github.com/google/benchmark/blob/v1.8.5/docs/user_guide.md#preventing-optimization)。

### 6.2 同一基准比较修复前后头文件

首次新增的基准在历史 general 基线中不存在，当前 `compare_benchmark.py` 会将其列为新增项并跳过。历史 CI 通过只能证明已有共同项目未超过回归阈值，无法证明新增默认入口用例已被检查。

实施验收使用当前同一份共同基准正文及对应标准入口，分别编译保存的修复前头文件和修复后头文件。现有 `RANDX_SAMPLING_HEADER_DIR` 虽然名称面向抽样，已通过 CMake 应用于 `benchmark_gbench`；C++17 默认接口目标复用相同的覆盖函数。两个入口采用尖括号包含发布头文件，快照目录只有发布头文件，避免源文件所在目录优先命中其他版本。记录目标全部编译单元的实际编译命令并核对来源覆盖，确认同一标准的双边构建仅在头文件目录及必要输出路径上存在差异。

在同一机器上交错运行两个可执行文件，两标准成对测量的重复数、测量时长和回归容差均读取 `tools/benchmark_policy.json` 的 general 策略，保存完整 JSON 与环境信息。对新增用例执行完整名称配对，沿用现有 25% 回归容差。

新增 `tools/run_integer_benchmark_pair.py` 作为成对验收入口。它接收双边头文件目录、编译器、构建目录、结果目录及策略文件，分别构建 C++17、C++23 两组双边程序，枚举共同用例，按轮次交替双边先后顺序运行，并复用现有比较器输出各标准独立的 JSON 和中文 Markdown 报告。每轮的预期用例、双边实测用例必须完整配对；缺项、同轮重复项、编译失败和测量失败归为数据或执行错误，轮次聚合使用现有工具的结果语义。性能回归、数据或执行错误分别沿用既有退出码契约，报告保留完整原始轮次。

可执行的 PowerShell 路径解析、基线提交重建、候选快照生成及 Miniconda Python 调用步骤见[验收结果的重放说明](整数生成性能修复验收结果.md#重放成对验收)。

入口允许显式选择 CMake 生成器、构建配置及双边一致的额外 CMake 参数，支持平台对应的可执行文件位置。测量参数从策略读取，输出中记录实际编译器、标准库、标准、优化及 LTO 选项、双边头文件来源、CPU 和运行顺序，并保存对应生成器支持的构建命令记录与代码生成证据；支持 `compile_commands.json` 的生成器直接保留该文件。工具测试覆盖参数传递、头文件选择、双标准用例配对、交错顺序、单位与轮次聚合、错误分类和报告输出。研究材料中的产品对照程序继续用于独立产品比较。

双边额外 CMake 参数必须相同。MinGW 响应文件按实际编译工作目录展开以核对头文件优先级；Windows 基准框架的本地编码 JSON 转为 UTF-8 时另存原始字节文件。

### 6.3 两标准持续门禁

C++23 共同默认接口用例进入现有 `general` 组；C++17 新增 `default_cpp17` 组，目标为 `benchmark_gbench_default_cpp17`。新组采用通用比较语义，测量轮数、时长与 25% 容差在 `tools/benchmark_policy.json` 中配置，与现有 general 的测量要求一致。该组只装配共同默认接口用例，覆盖整数调用形态及第 6.1 节的相关默认 API。

C++17 组在同一 runner 上，用当前共同基准正文及当前构建定义分别编译历史基线提交与候选提交的 C++17 发布头文件。基线提交沿用统一运行计划选定的有效基线，历史提交只提供头文件，不要求其已经含有新目标。这样首次接入即可比较新用例，后续也维持同源测量。两边分别记录基准来源提交与头文件来源提交，并校验完整用例集合。

Benchmark 工作流增加独立的 `measure_default_cpp17` job，统一计划、产物、求值和基线发布将其列为必需组；该组回归或未完成时按现有规则阻止正常基线发布。工具及接线测试覆盖新增组，包含历史基线尚无新目标时的同源构建。新增基准正文、入口、成对验收工具及其测试文件纳入工作流路径过滤。

四组分别为 general、default_cpp17、sampling_cpp17、sampling_cpp23，各自在自己的 runner 内比较双边结果。C++23 首次新增项的成对报告是本次修复的必需验收材料，旧 general 组通过不能代替它；正常发布的新 general 基线包含这些用例后，后续运行持续检查。C++17 组从首次接入起检查同源用例。两标准均须通过相应性能比较，数值不跨标准合并。

### 6.4 代码生成证据与通过条件

在已重现问题的 GCC 16.1.0 配置下，普通包装函数热循环应消除逐次 `call Dice`；辅助构造函数的调用位于首次初始化分支。结合编译器内联诊断、反汇编和耗时变化确认机制，不能只凭某个符号在整个汇编文件出现与否判断。

在其他工具链中，先观察修复前是否存在同样的内联问题。已经充分内联的平台以行为保持和性能回归检查为主要验收条件；存在问题的平台还需要确认初始化代码规模及逐次调用成本的改善。分别检查常用优化等级及启用 LTO 的构建，记录实际构建选项。

通过条件为：生产与 hook 两配置的双版本行为、注册清单及线程契约全部通过；两标准成对验收用例完整且比较通过；已重现的普通包装函数性能问题有代码生成与成对测量两类证据证明改善；直接默认、显式引擎和相关默认 API 的回归不超过现有门禁容差；四组持续门禁及新增工具、Actions 接线测试通过。固定的 1.108 ns 或固定倍数属于原型观测值，不作为跨机器验收阈值。
