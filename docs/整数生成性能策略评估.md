# 整数生成性能策略评估

评估日期：2026-10-04。当前生产代码提交为 `52b0ceca6e820c728a0255b5901c3855c8b78796`。本节稠密局部对照以 `81f296708a52e127ea81f1b65cf2fd1e70370dba` 为参考；属性独立贡献测量见[抽样与洗牌属性实测](抽样与洗牌编译器属性实测.md)，组合对照和当前代价见[编译器属性收敛验收](编译器属性收敛验收.md)。正式基准和门禁策略保持既定配置。

## 判断

源码清晰、常规表达与可维护性优先，性能回归同时记录相对增幅和绝对代价。默认引擎的冷构造隔离具有直接因果证据，应保留。稠密抽样保持现有调用边界，请求数量依据公开入口校验，内核采用普通上界表达。默认洗牌直接使用标准库算法，公开入口采用普通 `inline`，函数及其内部调用的内联由编译器自行决定。

输出范围决定分布映射条件，但不能单独决定整个稠密函数的最优内联方式。进一步收敛须同时记录 GCC 14 集成测量与 GCC 16 局部对照的实际结果；性能门禁提供证据，源代码复杂性由可维护性和明确的因果机制共同判断。

抽样与洗牌属性已在参考实现上开展独立配置对照，本轮组合收敛另有完整测量，均记录双标准生成代码、完整输出和最终状态、初测及延长确认。贡献判断限定于实际测量的调用现场；功能兼容性和集成门禁通过不能推导每条属性都有独立收益。

## 逐项判断

| 当前策略 | 判断 | 主要依据与适用条件 |
| --- | --- | --- |
| `CreateDefaultEngine()` 的 `noinline` | 保留 | 完整首次构造从 TLS 热入口隔离，普通业务包装的 GCC 内联拒绝得到复现和消除；[产品研究与正式复测](整数生成性能修复验收结果.md#问题调用形态复测)提供序列和汇编证据。Clang／MSVC 尚无性能收益测量。 |
| 稠密抽样完整 64 位范围分派 | 保持现有边界，继续研究收敛 | 参考边界在 GCC 14 完整门禁中已有对照；GCC 16 局部对照中 Xoshiro128 的普通内联更快，GCC 14 C++17 普通内联集成对照存在回归。输出范围不能作为通用内联收益判据。当前生产结果见收敛验收。 |
| 抽样入口、位图和分布的 `always_inline`／`flatten` | 分别验证贡献 | 提供调用点优化机会，同时扩大展开范围；参考实现上的九组配置分别切换对应策略，另将洗牌组合属性分开测量。循环内调用、代码体积和吞吐见独立实测报告。 |
| 默认洗牌入口 | 普通 `inline` 直接调用标准库 | 保持两标准接口约束及对应标准库算法；GCC 16 反汇编中留下标准分布外调。相对于在调用点内联的参考配置，耗时增加约 79%–95%，属于明显代价。组合对照、绝对耗时和 GCC 14 集成结果见收敛验收。 |
| 完整复制与哈希操作的 `noinline` | 暂保留 | 分配与大段遍历有明确的函数体规模；是否最佳仍取决于调用现场；完整复制与哈希边界尚未进行独立属性对照。 |
| 一两个索引的定长存储 | 保留算法优化 | 查重至多比较一个已选索引，减少哈希桶及节点分配；接受顺序、重抽和普通元素复制异常进度保持一致。辅助函数的 `noinline` 已独立对照；测得的代码生成与吞吐变化不等同于定长存储的算法收益。 |
| 平凡元素及已知连续迭代器的范围复制 | 保留 | 快路径只覆盖原生指针和精确标准 `vector<T>` 迭代器；其他来源维持预留容量后的索引复制，没有发现公开复制行为反例。 |
| 稠密请求数量 | 采用普通循环表达 | 公开入口限制范围宽度，只在 `0 < n < size` 后转换计数并进入稠密路径；内核的每步分布由当前索引与总体大小构造。上界对照的 GCC 14 集成测量有三项小请求／空输入回归，绝对增加约 0.31 ns、0.31 ns 和 8.32 ns，详见收敛验收。 |

小样本数组消除了集合节点分配，故特定分配失败注入下的失败时机和随机消耗可能与集合实现不同；现有公开承诺没有证明包含这一资源故障进度，普通元素复制异常的契约则仍需保持。

## 稠密调用边界对照

环境为 Windows 11、Ryzen 7 5800H、MinGW GCC 16.1.0、libstdc++ 16、Google Benchmark 1.8.5，C++17／C++23 均使用 `-O3 -DNDEBUG -falign-functions=64 -falign-loops=64`。两侧编译选项和观察方式相同。

参考配置为 `81f2967` 的独立快照。总体大小为 256 和 65,536，请求分别为 129 和 32,769，均通过公开容器入口进入稠密路径。覆盖 Xoshiro128StarStar、Xoshiro256StarStar 和 `std::mt19937_64`。对照仅改变稠密正文的内联属性及其调用边界，保留算法、上界假设和其他采样策略。

十个配置的完整输出及最终引擎状态逐字节相同，每个配置的验证输出为 587,619 字节；两标准之间也相同。该验证覆盖上述固定种子和参数，不能代替完整公开契约测试。

五种调用边界与假设配置各初测五轮、每项 0.1 秒；参考实现与普通内联边界再执行六轮、每项 1 秒的交错确认，均读取现有抽样策略。无亲和性约束的 C++23 确认出现显著波动及部分用例增幅，因此另以相同六轮和时长执行单核对照，且两侧先后顺序均衡。仅实验子进程设置 CPU 15 亲和性和高于普通的调度优先级；未改变系统调频、SMT、ASLR 或正式门禁。

下表为单核对照 CPU 时间中位数，单位 ns；变化相对于参考快照。

| 标准 | 引擎 | 总体／请求 | 参考 | 普通内联 | 变化 |
| --- | --- | --- | ---: | ---: | ---: |
| C++17 | Xoshiro128StarStar | 256／129 | 819.35 | 410.33 | -49.92% |
| C++17 | Xoshiro128StarStar | 65,536／32,769 | 215357.29 | 96007.14 | -55.42% |
| C++17 | Xoshiro256StarStar | 256／129 | 423.58 | 421.93 | -0.39% |
| C++17 | Xoshiro256StarStar | 65,536／32,769 | 99193.02 | 98803.01 | -0.39% |
| C++17 | std::mt19937_64 | 256／129 | 587.33 | 587.33 | -0.00% |
| C++17 | std::mt19937_64 | 65,536／32,769 | 147876.17 | 145170.00 | -1.83% |
| C++23 | Xoshiro128StarStar | 256／129 | 793.46 | 412.60 | -48.00% |
| C++23 | Xoshiro128StarStar | 65,536／32,769 | 202462.40 | 94420.91 | -53.36% |
| C++23 | Xoshiro256StarStar | 256／129 | 414.86 | 404.23 | -2.56% |
| C++23 | Xoshiro256StarStar | 65,536／32,769 | 99488.08 | 97289.24 | -2.21% |

单核条件下 Xoshiro128 的四项 CPU 时间均减少约 48%–55%；Xoshiro256 和 `mt19937_64` 的变化约在 −2.6% 至 +2.9%。本结果证明普通内联在上述 GCC 16 调用现场更快。无亲和性约束的原始结果也完整保留，不能只报告单核数据。

反汇编确认：参考 Xoshiro128 基准调用独立 `SampleDenseIndicesOperation`，普通内联版本没有该调用，由编译器将正文展开到调用点。C++23 基准函数从 542 条指令变为 812 条，参考独立稠密函数另有 402 条；这是函数边界和规模变化，不能直接换算成吞吐成本。对应标准分布函数的规范化反汇编相同，不能将收益解释为更换了区间映射算法。具体寄存器保存、分支布局和调用现场各自的贡献尚未被隔离。

## 测量有效性与验收范围

当前正式采样基准通过可写局部变量观察结果长度和元素存储指针，并在非空结果上提交内存写入；这一方式符合 [Google Benchmark 1.8.5 的观察示例](https://github.com/google/benchmark/blob/v1.8.5/docs/user_guide.md#preventing-optimization)。固定请求在计时前观察一次，保持其运行时输入性质。该协议不保证所有表达式运算保留；空输入可能被编译为返回常量或得到循环外优化。

已记录的 GCC 16 空容器用例约 0.256 ns 到 1.256 ns，是该微基准和配置下的真实观察差异，不能直接等同于普通用户每次 API 调用的执行成本，也不能忽略。应独立检查普通消费者的运行时请求、零请求与空范围汇编，保持全部空输入用例。

GCC 14 集成对照以 `ec7cdb8b64dbbe213f23c97e0520a7cac991e53d` 为基线，在同一 runner 重建双边程序。[运行 37145351297](https://github.com/lidaixingchen/RandX/actions/runs/37145351297) 的普通稠密内联配置在 C++17 抽样组有 25 项延长确认后的回归，稠密请求约增加 32%–117%；C++23 抽样、general 和 C++17 默认接口组通过。C++17 候选的默认容器及迭代器函数中留下 `vector::reserve` 调用，基线没有该直接调用；尚未隔离其耗时贡献，也未确认 Xoshiro256 热循环的引擎状态溢出。

参考提交 `7ceeceb` 的[CI](https://github.com/lidaixingchen/RandX/actions/runs/37152235610)、[Docs](https://github.com/lidaixingchen/RandX/actions/runs/37152235596)和[Benchmark](https://github.com/lidaixingchen/RandX/actions/runs/37152235620)均通过。四组完整比较 641 项，新增、缺失和回归项均为零；原始计划及求值记录见[稠密调用边界集成门禁材料](整数生成性能研究材料/稠密调用边界集成门禁原始结果.json)。当前生产提交的实际工作流状态见[集成验收](整数生成性能修复验收结果.md#集成验收)。Clang、MSVC 和 ChaCha20 的性能对照仍未执行。

## 收敛与验证边界

当前稠密正文、分派与完整复制及哈希边界保持现有配置。后续调用边界优化以双标准共享契约、固定重排、注册核对、历史序列及最终状态为行为约束，并在 GCC 14 完整四组门禁和本地成对测量中共同记录收益与代价。功能与序列正确性必须通过；性能变化独立量化。

抽样适配器、分布包装、洗牌边界、小样本辅助函数和稠密上界的实际测量及判断见[独立实测报告](抽样与洗牌编译器属性实测.md)及[组合收敛验收](编译器属性收敛验收.md)。现有位图及分布属性尚未呈现跨标准、跨用例一致的保留收益；完整复制与哈希边界缺少独立属性对照。已有数据限定于实测调用现场，Clang／MSVC 的功能 CI 继续作为兼容性证据。
