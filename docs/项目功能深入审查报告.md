# RandX 项目功能深入审查报告

## 判断与投入顺序

审查基线为提交 `9a56a32c8fca6f1fda9ca93b0f85c7d68578a6ff`。范围包括分布与抽样、并行随机流、安全接口、标准库组合、统计验证和安装发布。本文记录该基线的审查事实与建议；当前实现与验收结果见[项目功能改进方案](项目功能改进方案.md#11-实施结果)。

项目已经具备通用随机库的主要能力。当前最值得投入的是完成有效的质量验证、收紧公开类型契约、降低并行流初始化成本。新增能力中，带权无放回抽样有最明确的语义增量；可复用权重对象的价值在于复用 RandX 的验证和原索引契约；逻辑地址随机数需要具体的并行计算需求支撑。

| 顺序 | 工作 | 判断依据 | 建议行动 |
| --- | --- | --- | --- |
| 1 | PractRand 检验可完成性与结果留存 | 最近五次 nightly 均被取消；最近一次没有完成首个目标检查点 | 优先修复验证设施 |
| 2 | 整数分布返回类型约束 | 泊松、二项分布允许 `bool` 实例化，几何分布也接受 `bool` | 修正准入契约并补编译期检查 |
| 3 | `MakeStreamEngine` 初始化复杂度 | 构造成本与流 ID 高低位数值之和成正比；逐个从种子建流累计成本高 | 保持映射的快速跳跃设计；批量建流复用状态 |
| 4 | 发布渠道与安装消费者验收 | CMake 安装消费通过；官方 xmake 配方与本地版本存在差距 | 更新渠道状态，补安装树验收，推进版本同步 |
| 5 | 带权无放回抽样 | 现有均匀抽样和单次带权选择不能直接提供该联合抽样律 | 优先开展独立功能设计 |
| 6 | 可复用的已验证权重对象 | 现有容器重载每次预处理，标准分布重载不承担 RandX 的完整预处理契约 | 有固定权重重复抽取需求时设计 |
| 7 | 按逻辑地址生成随机数 | 能直接定位对象内第几次随机取值，减少对可变引擎状态的依赖 | 有逻辑地址需求时评估 Philox |

## 一、需要优先改进的功能与设施

### 1. PractRand nightly 的规模和执行组织无法形成预期证据

**确认事实。** [工作流](../.github/workflows/practrand-nightly.yml) 将八个引擎放在一个六小时 job 内串行执行，七个统计 PRNG 的默认目标为 `1TB`，ChaCha20 为 `256GB`。驱动将这些单位按二进制解释，分别为 1 TiB 与 256 GiB。最近五次运行 `37146774066`、`37061472339`、`36925157403`、`36774415752`、`36627679363` 的终态均为 `cancelled`。

[最近一次完整日志](https://github.com/lidaixingchen/RandX/actions/runs/37146774066) 显示：xoshiro256 执行四小时后为 `inconclusive`，已完成检查点字节数和测试数均为零；xoroshiro128 随后开始，job 到六小时上限被取消。这里的零表示没有完成可报告的检查点，不能解释成生成器没有输出。失败通知步骤被跳过。

**原因。** [驱动](../tools/pract_rand/run_practrand.py) 使用目标长度同时作为 `-tlmin` 和 `-tlmax`，首个完整检查点就是大目标；单引擎默认超时四小时。即使改成每引擎一个 job，当前证据仍说明首个引擎无法在四小时内完成该目标。驱动支持结构化报告，但工作流没有传入 `--output-json`，没有上传日志或报告；报告写入还发生在整个引擎循环结束之后。

**建议。** 用当前托管 runner 的实际吞吐选择可按期完成的 nightly 规模，按引擎拆分任务；更长检验放到具备时间预算的周期任务或专用 runner。支持逐级检查点和每引擎完成后的增量报告，上传日志及结构化产物。汇总时区分统计失败、环境失败、证据不足和取消；对计划外超时形成可见告警。取消后的上传只能尽力执行，已经完成的独立 job 应分别保存证据。

**验收。** 八引擎均完成声明的目标；每项记录 RandX 提交、PractRand 版本、seed、输入位宽、目标及已完成字节数、测试数和原始日志。中途失败或取消能保留已完成项目的证据。完整目标未达到时不能判为通过。后续再拓展多个 seed、不同输出位段和流交织检验；这些扩展应在基本检验可完成后进行。

这是验证缺口，不是算法已被证明统计失败。常规 CI、序列对照和有限样本统计检查不能替代上述质量证据。

### 2. 整数分布的类型范围需要统一

**确认事实。** 两版 `RandPoisson`、`RandBinomial` 和 `RandGeometric` 使用 integral 约束，均接受 `bool`。泊松和二项直接实例化标准分布，几何分布使用自有数值算法。位置见 [C++23 来源](../src/header_sources/cpp23/convenience.inc)、[C++17 来源](../src/header_sources/cpp17/convenience.inc)，生成接口见 [RandX.hpp](../RandX.hpp#L3700) 与 [RandX_Cpp17.hpp](../RandX_Cpp17.hpp#L3767)。

Windows MinGW GCC 16.1、C++17/C++23 小实验中，固定种子的 `RandPoisson<bool>` 在 20,000 次调用中全部返回 `false`；`RandBinomial<bool>(3, 0.5)` 的参数先转换成 `true`，传入的试验次数成为 1；`RandGeometric<bool>(0.5)` 有 4,826 次溢出异常。泊松实验只证明该工具链的实际表现，不构成合法分布的概率结论。

C++17/C++23 的标准分布 `IntType` 要求不保证支持 `bool`，也不能把所有 integral 类型都直接当作合法的标准分布参数。C++23 草案列出的类型是 cv 未限定的 `short`、`int`、`long`、`long long` 及对应 unsigned 类型；当前泊松和二项的约束也放行了未在该列表中的字符类型。这是公开约束与标准分布实例化要求的落差。[C++23 N4950，§28.5.3.1](https://www.open-std.org/jtc1/sc22/wg21/docs/papers/2023/n4950.pdf#page=1417)

**建议。** 泊松与二项明确可支持的整数返回类型，或用受支持的内部类型采样并定义范围转换契约；几何分布单独明确自有算法的返回类型政策，并排除 `bool`。共享类型政策时保持两版一致，考虑约束收紧对既有调用的兼容影响。

**验收。** 默认和显式引擎重载均在编译期拒绝 `bool`；保留支持类型的正向实例化检查；实际调用验证合法输出、参数边界与范围异常。不能只检查模板声明可见性，因为标准分布的限制可能在函数体实例化时才出现。生产修改从来源进行，再生成两份头文件。

### 3. 流初始化应改善算法复杂度

**确认事实。** [C++23](../src/header_sources/cpp23/modern_features.inc#L14) 与 [C++17](../src/header_sources/cpp17/engines_implementation.inc#L285) 的 `MakeStreamEngine` 从根种子构造引擎，随后调用：

`(streamId >> 32)` 次 `longJump()`，以及 `(streamId & 0xffffffff)` 次 `jump()`。

固定跳跃自身有界，但重复次数由 ID 数值决定。小规模实验验证了 ID `0、1、3、2^32、2^32+1` 的状态符合规则，两标准一致。最大 uint64 ID 需要 `2 × (2^32−1)` 次跳跃，约 85.9 亿次；本轮没有实际运行该高 ID。不要将任意散列值直接作为当前接口的流编号。

这一问题也影响密集批量：若从相同种子独立构造 ID `0..N−1` 的 N 个流，在低 32 位范围内会累计执行 `N(N−1)/2` 次 jump。

**建议。** 批量分配可从已有流继续 jump；直接定位任意 ID 可评估线性状态转移的跳跃多项式组合或二进制幂表。xoshiro 作者明确说明任意跳跃多项式的可计算性；具体初始化成本、表大小及纯头文件维护成本需项目测量。[算法作者资料](https://prng.di.unimi.it/)

改进必须保持现有 `seed + streamId` 到状态的映射。xoshiro256 的映射为 `high32 × 2^64 + low32` 个 jump 间隔；128 位引擎为连续的第 ID 个 jump 间隔。两者不能未经兼容设计统一成另一种编号规则。`discard(n)` 目前线性执行是正常契约；快速定位可与流构造优化共用底层机制。

**验收。** 小 ID 与旧实现的完整状态及后续序列一致；大 ID 通过独立转移组合和代数性质验证；两标准 parity 通过。分别测量单流随机定位、N 流初始化、冷启动、静态材料大小和稳态抽取。固定 seed 与紧凑逻辑任务 ID 已能提供调度无关的起点；流池的新增价值应是所有权、分配和预算管理。

128 位引擎的周期为 `2^128−1`，jump 间隔为 `2^64`。完整 uint64 ID 域不能同时给每流分配完整 `2^64` 次输出而声称严格无重叠，应明确预算边界。跳跃间隔本身也不证明统计独立性。

### 4. 安装发布的改进集中在版本同步和实际消费

**已验证能力。** 当前 CMake 导出 `RandX::Cpp17` 与 `RandX::Cpp23` 并传播平台链接依赖。本轮将库安装到独立前缀，从该安装树 `find_package`，以 MinGW GCC 16.1 Release 编译并运行现有两标准消费者，均成功。该检查不同于原构建树消费。

**远端事实。** 最新 GitHub release 为 [v1.5.0](https://github.com/lidaixingchen/RandX/releases/tag/v1.5.0)。[打包预演 35954198285](https://github.com/lidaixingchen/RandX/actions/runs/35954198285) 成功。官方 vcpkg 的 `ports/randx` 查询返回 404；[xmake 官方配方](https://github.com/xmake-io/xmake-repo/blob/master/packages/r/randx/xmake.lua) 已存在，最新条目为 1.4.3，本地配方含 1.5.0。因而 xmake 的实际工作是版本同步，发布文档中的“待首发”应更新。

[vcpkg 预演](../.github/workflows/packaging-validation.yml) 安装后仅核对两份头文件存在，尚不能证明安装的 CMake 配置、语言标准和链接依赖可供消费者使用。本地 registry 版本片段仍含 1.3.1 和占位字段，应按模板用途明确标识。发布说明中的旧版本示例也应与当前发布流程对齐。

**建议与验收。** 将安装树 C++17/C++23 消费者编译、链接和运行纳入打包验收；同步 xmake 上游版本，再推进 vcpkg 官方发布。分别记录配方已准备、预演通过、PR 已提交和官方可安装状态。更新渠道说明具有即时用户价值。

### 5. 安全接口优先补齐消费者契约说明

本轮未发现已确认的安全实现缺陷。`SecureRandomBytes` 的 OS 熵失败行为、默认 `ChaCha20()` 的初始化、先取得完整材料再提交重播种状态，以及熵故障测试均有现有实现支撑。[熵故障契约](../tests/common/entropy_failure_contracts.hpp)

现有 `ChaCha20 rng{}; RandString(rng, n, CharSet::Base64UrlSafe)` 和 `RandUUID(rng)` 已能组合安全用途输出。应在 API 文档补齐显式引擎 UUID 与自定义字符集字符串重载，明确 `ChaCha20(seed)` 的确定性模式、64 位 `SecureSeed()` 与默认完整 OS 熵初始化的区别。直接 key/nonce/counter 构造需要说明：同一 key 下不能复用重叠的密钥流位置；重复材料及位置会重复输出。[RFC 8439](https://www.rfc-editor.org/rfc/rfc8439#section-2.3)

## 二、真正值得拓展的功能

### 1. 带权无放回抽样：优先设计

现有 `RandSample` 提供均匀无放回抽样，`RandWeighted` 返回一次带权选择。带权抽取多个不同位置是独立能力，可用于按重要性抽取候选、模拟和推荐集合。重复抽取并移除权重虽可组合，但会重复预处理，流式输入也需要专门算法。

建议首先采用“每轮在剩余项目中按权重比例选择”的顺序抽样律。它与预先指定每项最终包含概率不同；当样本数大于 1 时，不能把包含概率简单写成 `k × w_i / Σw`。Efraimidis–Spirakis 给出这种定义及单遍 reservoir 算法。[作者稿](https://utopia.duth.gr/~pefraimi/research/data/2007EncOfAlg.pdf)

设计需明确按位置唯一还是按值唯一、返回顺序、零权重、有效正权重数不足、空输入、请求零项、异常前随机消耗、浮点端点与极端权重。相同值处于不同输入位置时通常应视作不同项目。数值稳定的键计算、舍入导致的并列和决胜规则须作为算法问题验证。

验收包括小规模联合概率参考、唯一性、等权退化为均匀抽样、零权重排除、极端权重和两标准 parity；性能比较覆盖样本数与输入规模，基线为可读的逐轮按剩余权重实现。先确定目标输入是随机访问容器、单遍范围，还是两者均需要。

### 2. 可复用的已验证权重对象：有契约增量

[现有预处理](../src/header_sources/common/distributions/prepared_weights.inc) 完成有限性、符号和总有效权重检查，以最大权重缩放，移除零权重并保存原索引；[抽取正文](../src/header_sources/common/distributions/rand_weighted_02_body.inc) 恢复原索引。容器重载每次重复该工作。

预构建 `std::discrete_distribution` 已提供重复调用能力。新增对象的价值应是一次完成 RandX 的输入验证、归一化与原索引映射，并在后续抽取中保持这些契约。优先复用标准分布后端，避免为了对象包装引入另一套采样算法。

构造后权重固定的对象更容易定义所有权与线程规则；对象是否持有可变分布状态必须明确，并行共享不能默认安全。权重更新的重建成本、内存规模和随机消耗须公开。实测对比容器重载、完整权重构造的标准分布及新对象，确定在哪些类别数和重复次数下收益成立。

现有预构建重载的 `O(1)` 注释应修正：标准约束平均引擎调用次数，并未规定相对类别数的查找复杂度。Alias 表属于固定权重高频抽取的后续性能设计，须先测量标准后端的瓶颈。[C++23 分布要求](https://www.open-std.org/jtc1/sc22/wg21/docs/papers/2023/n4950.pdf#page=1422)、[Vose 论文](https://doi.org/10.1109/32.92917)

### 3. 按逻辑地址生成随机数：场景明确时评估 Philox

现有任务专属引擎已能让固定任务的起点不受调度影响。Counter-based 生成的进一步能力是根据根 key、对象 ID、对象内抽样序号等逻辑坐标直接取得结果，无需先消费此前输出。它适用于对象局部重算、任务重分块、并行模拟和需要直接随机访问的计算。[Random123 论文](https://www.thesalmons.org/john/random123/papers/random123sc11.pdf)

复现性来自稳定且不重复的逻辑地址映射。若改变对象编号、用物理线程号分配地址，或未定义一次分布抽样内部的多次随机消耗，换成 Philox 也不能自动满足应用复现要求。应先定义原始随机块层的定位契约，再决定如何接入分布。

WG21 的后续工作草案已包含 `std::philox_engine` 和 `set_counter`，项目当前 C++17/C++23 目标存在标准可用性差异。新增引擎的定位应是逻辑地址能力及当前目标标准的可用性，而性能收益仍须本项目验证。[WG21 N4988](https://www.open-std.org/jtc1/sc22/wg21/docs/papers/2024/n4988.pdf)、[采纳记录](https://www.open-std.org/jtc1/sc22/wg21/docs/papers/2024/n4989.html)

验收需要公开参考向量、计数器进位和穷尽边界、地址映射、两标准输出一致性、随机访问与顺序消费对照、统计检验和目标平台成本。本轮未验证各编译器的后续标准库实现状态。

## 三、其他方向的推进条件

| 方向 | 所需证据 |
| --- | --- |
| SIMD 批量生成 | 大批量填充的实际瓶颈、目标硬件、可复现边界、尾部和回退规则、初始化与吞吐测量 |
| 并行流管理对象 | 集中分配、重复任务所有权、预算管理需求；与快速初始化共享机制 |
| 安全用途类型约束 | 已发生或可复现的误用路径、可信初始化条件、迁移成本与编译期拒绝规则 |
| 更多分布 | 具体场景、标准库组合成本，以及新增边界契约或算法价值 |
| 更长质量检验与性能看板 | 先有能完成且可追溯的原始报告，再展示趋势或扩展检验规模 |

分布对象复用和按数量生成继续采用已交付的[标准库组合方案](分布扩展与批量生成改进方案.md)。当前新增工作的着力点应是抽样律、数值与类型契约、定位算法或管理能力。

## 四、本轮证据边界

- 分布方向：Windows MinGW GCC 16.1，C++17/C++23，小型类型实例化与运行实验。
- 并行方向：同工具链优化构建，小 ID 状态映射及初始化测量；没有执行数十亿次 jump。
- 安全方向：两标准消费者探针编译运行，结合现有实现和故障契约检查；未进行独立密码分析。
- 安装方向：安装树两标准 Release 消费者编译、链接及运行通过。
- 远端方向：通过 `gh` 实时读取 release、registry 配方和 Actions 状态及日志；未触发新的长时间统计任务。
- 资料方向：标准草案、算法作者稿、Random123 和 RFC 等一手来源，详见[功能拓展一手资料](功能拓展一手资料.md)。

本轮未运行完整 CTest、MSVC/Clang/macOS 矩阵或完整 PractRand；报告中的功能建议尚未形成生产实现。具体优先修复可以独立交付，扩展功能应先冻结语义与验收条件。
