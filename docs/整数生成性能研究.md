# 整数生成性能研究

研究日期：2026-10-02。

## 结论

前次产品对照基准中的 `RandInt(1, 6)` 慢，主要原因是 GCC 16.1 未将测试包装函数 `Dice()` 内联到热循环；这不是默认 xoshiro 引擎或 64 位整数映射必然更慢的证据。

汇编显示原基准每次抽样执行 `call Dice`，GCC 内联诊断明确给出 `--param max-inline-insns-auto limit reached`。该包装函数展开后包含默认引擎的首次初始化路径；即使初始化在计时前完成，冷路径的代码体积仍参与内联决策。仅把首次引擎构造移到独立的不可内联辅助函数，保持整数映射和默认引擎不变，原基准耗时便从 3.206 ns/次降到 1.108 ns/次，降幅约 65%。对测试包装函数施加内联干预得到 1.108 ns/次，构成另一项相互支持的证据。

库的主要改善方向是隔离首次构造的冷路径、提高热路径内联的稳定性。64 位乘积映射、运行时端点校验和 TLS 访问是后续细化因素，不能用它们替代已确认的主要原因。

## 实验环境与方法

- Windows 11，AMD Ryzen 7 5800H，MinGW GCC 16.1.0 / libstdc++，x86-64。
- 基本选项为 `-O3 -DNDEBUG`；另测 C++17 和 `-march=native`，主要判断使用基本选项结果。
- 对照库为本机 `E:\project\random`，其默认 `random_static` 和 `random_thread_local` 使用 `std::mt19937`。
- 拆分实验每项进行 5,000,000 次抽样，先完整执行一次相同循环热身，再计时；七轮交错运行三个编译变体，取中位数。
- 单因素干预实验保留产品对照基准的调用形态，交错运行九轮，取中位数；所有 RandX 干预变体使用同一份捕获的头文件作为起点。
- 抽样结果累加到可观察的 sink，计时和输出位于热循环外；汇编确认循环和随机生成代码实际保留。
- 拆分实验用固定种子和连续引擎状态；产品基准每个任务计时前重新播种，播种不计时。两类实验有不同的调用形态，因此只在各自组内作单因素因果判断。
- 原始材料见 [整数生成性能研究材料](整数生成性能研究材料/)。完整汇编及头文件快照位于本机临时目录 `C:\Users\LIDAIX~1\AppData\Local\Temp\randx-integer-study-20261002`。

这些结果属于本机吞吐量微基准，计入循环与累加成本，不能直接解释为单条指令延迟，也不是所有编译器、优化选项和应用代码形态的保证。

## 整数生成的实际路径

默认调用路径是：

```text
RandInt(min, max)
  → DefaultEngine()
  → RandInt(engine, min, max)
  → 检查 min > max
  → std::uniform_int_distribution<DistType>
  → 引擎输出 + 无偏区间映射
```

源码见 [RandX.hpp](../RandX.hpp#L1944) 的默认重载、[DefaultEngine](../RandX.hpp#L1624) 和[指定引擎重载](../RandX.hpp#L2595)。C++17 的指定引擎重载执行相同的检查与标准库分布调用。

默认 `Xoshiro256StarStar` 满范围输出 64 位；对照库默认 `mt19937` 满范围输出 32 位。**返回类型是 `int`，不会使 64 位引擎自动进入 32 位映射分支**：libstdc++ 依据引擎结果范围和分布类型的公共类型选择映射路径。

### libstdc++ 已采用 Lemire 映射

本机实际头文件：

```text
C:\hjpz\mingw64\lib\gcc\x86_64-w64-mingw32\16.1.0\include\c++\bits\uniform_int_dist.h
```

第 252–280 行实现 `_S_nd`，第 295–342 行选择缩小区间的分支：

| 引擎满范围输出 | 中间乘积类型 | x86-64 上的主要区别 |
|---|---|---|
| 64 位 | `unsigned __int128` | 计算 64×64 的高低两半；本次汇编使用 `mul` |
| 32 位 | `uint64_t` | 计算 32×32 的 64 位乘积 |

设均匀随机字为 `x`，位宽为 `w`，目标区间大小为 `s`：

```text
p = x × s
候选值 = p 的高 w 位
t = 2^w mod s
若 p 的低 w 位 < t，则重抽
```

拒绝采样消除不能整除时的偏差。该算法和乘积映射有 [Lemire 原论文](https://arxiv.org/abs/1805.10941)支持；GCC 源码直接引用这篇论文。[C++ 工作草案](https://eel.is/c++draft/rand.dist.uni.int)规定均匀概率及有效区间前提，并未指定具体算法。

`[1,6]` 的 `s=6`，`2^32 mod 6` 和 `2^64 mod 6` 都为 4。因此拒绝概率分别为：

- 32 位：`4 / 2^32 ≈ 9.31×10^-10`。
- 64 位：`4 / 2^64 ≈ 2.17×10^-19`。

在本实验规模下，这些概率无法解释每次抽样约 2 ns 的额外开销。常量区间的热路径也没有常规整数除法；运行时区间的阈值计算属于条件路径，并可能被优化器移出循环。

## 主要原因：调用形态影响内联

产品对照基准用普通包装函数统一接口：

```cpp
int Dice() { return RandX::RandInt(DiceMin, DiceMax); }
```

原基准热循环中保留了：

```asm
.L517:
    call _Z4Dicev
    add  rsi, rax
    sub  rdi, 1
    jne  .L517
```

同一个基准的对照库包装函数被内联，热循环没有 `call Dice`。这使两边承担不同的代码生成成本；即使接口任务相同，该结果也不能直接判定区间算法的固有快慢。[汇编与编译器诊断摘录](整数生成性能研究材料/汇编与内联证据.txt)保留了证据。

GCC 给出的最终拒绝内联理由是：

```text
comparison.cpp:73:93: missed: not inlinable:
Measure.constprop -> int Dice(), --param max-inline-insns-auto limit reached
```

[GCC 优化选项文档](https://gcc.gnu.org/onlinedocs/gcc-16.1.0/gcc/Optimize-Options.html)说明了自动内联的大小限制。源代码中的 `inline` 也不能被理解为机器码一定内联的保证。

原 `Dice()` 的汇编入口有六个保存寄存器的 `push`，随后分配栈空间、查询 TLS、检查首次初始化标志；每次调用读取和写回引擎状态，再恢复寄存器并返回。这些成本以及阻断跨抽样优化的影响，被一同计入原来的约 3.2 ns。

`DefaultEngine()` 的初始化表达式构造 xoshiro 状态，包含 SplitMix64 的四字种子展开。`RandomSeed()` 已不可内联，但返回种子后的状态构造仍可能展开进调用链。计时前播种可排除实际首次播种耗时，却排除不了冷路径对编译器成本模型的影响。

### 单因素干预结果

| 变体 | 中位数 ns/次 | 九轮最小–最大 | 变化范围 |
|---|---:|---:|---|
| 原产品基准，保持普通包装函数 | 3.206 | 3.128–3.369 | 基线 |
| 对测试包装函数施加内联干预 | 1.108 | 1.096–1.125 | 只改变包装函数的内联属性 |
| 将首次引擎构造隔离到辅助函数 | 1.108 | 1.091–1.179 | 只改变默认引擎初始化的代码组织 |
| 对照库默认静态版本 | 1.903 | 1.879–2.004 | 对照 |

第三个变体只在临时头文件快照中进行：独立的 `CreateDefaultEngine()` 返回 `Xoshiro256StarStar{RandomSeed()}`，标记为不可内联；`DefaultEngine()` 的线程局部对象通过该函数初始化。该变体的产品基准汇编中不再出现 `call Dice`。这项干预没有替换默认引擎，也没有改变 `uniform_int_distribution`。

固定种子下，原版与冷路径隔离变体的前 20,000 个 `[1,6]` 抽样结果和最终序列化引擎状态完全相同。此检查验证本次原型的序列保持；不替代未来正式修改需要的跨编译器、双版本和熵源测试。

## 次要因素的拆分证据

以下为独立热循环的 C++23 基本选项结果，单位 ns/次，七轮中位数。

| 路径 | 中位数 | 支持的判断 |
|---|---:|---|
| 局部 xoshiro256 原始输出 | 0.771 | 默认引擎的原始生成较快 |
| 局部 mt19937 原始输出 | 1.440 | 原始引擎速度不能解释原来的排名 |
| `RandInt(1,6)` 默认入口 | 1.126 | 内联后的默认入口没有固有的约 3.2 ns 成本 |
| 局部 xoshiro256 + `RandInt(1,6)` | 1.167 | 显式引擎结果与默认入口接近 |
| 局部 xoshiro256 + 直接标准库分布 | 1.196 | RandX 的常量合法区间包装没有显著额外成本 |
| 局部 xoshiro256 + 等价手写 Lemire | 1.137 | 本案例重新实现映射没有明显收益 |
| xoshiro256 取高 32 位 + 标准库分布 | 1.228 | 缩小输入位宽没有解决主要问题 |
| 复用常量区间的分布对象 | 1.515 | 复用对象不能自动带来收益 |
| 默认 mt19937 静态入口 `[1,6]` | 1.856 | 此调用形态下 RandX 更快 |
| 默认 mt19937 线程局部入口 `[1,6]` | 2.101 | TLS 版本仍未达到原 RandX 基准的约 3.2 ns |
| 默认 RandX，运行时输入上界 6 | 1.712 | 常量区间与运行时区间应分别测量 |
| 局部 RandX，运行时输入上界 6 | 1.790 | 动态合法性判断和代码生成可能产生额外成本 |
| 直接标准库，运行时输入上界 6 | 1.517 | 该差值不能直接当作所有场景的固定检查成本 |
| 默认 RandX 常量区间 `[1,8]` | 1.179 | 2 的幂大小区间同样没有原基准的差距 |
| 局部 mt19937 常量区间 `[1,8]` | 1.777 | 对照 |
| 局部 xoshiro256 生成满范围 `uint64_t` | 0.757 | 64 位目标范围利用默认引擎的输出宽度 |
| 局部 mt19937 生成满范围 `uint64_t` | 4.732 | 32 位引擎必须组合输出并执行上扩路径 |

对象复用案例中，分布的端点经引用传入独立循环函数；优化器不能像局部常量表达式那样充分折叠参数。这说明“每次构造 `dist` 必然慢”不成立，不代表所有分布对象复用都更慢。

原始 TLS 输出的默认访问为 0.993 ns，缓存引擎引用为 0.762 ns，存在小幅差异；但 `[1,6]` 内联循环的默认入口和缓存入口接近，说明 TLS 成本也依赖优化后的调用形态。应把 TLS 作为可测的次要因素，而不是把原基准的全部差距归给它。

C++17 的默认 `[1,6]` 独立热循环为 1.131 ns，与 C++23 的 1.126 ns 接近。`-march=native` 又改变部分排名，进一步说明结论需绑定编译配置。

## 优化优先级

1. **优先隔离默认引擎首次构造的冷路径。** 本机单因素实验已确认收益，并且可以保持当前默认引擎、抽样算法和序列。正式实现时同步两个头文件，确认首次调用、重播种、线程隔离及不同编译器的代码生成。
2. **建立覆盖调用形态的整数性能基准。** 至少区分直接默认调用、普通业务包装函数、显式局部引擎、运行时端点和不同整数位宽；检验是否存在逐次调用，而不是只看一张 ns 表。
3. **之后再评估运行时区间内核。** 标准库已经有 Lemire 专用分支，重复实现只有在证明具体平台或调用形态收益后才值得引入；需保持无偏分布、完整类型范围和预期输出契约。
4. **位宽适配依据目标区间单独评估。** 高 32 位映射会改变输出序列和引擎消费策略；范围接近 32 位可表示空间时，还可能显著增加拒绝概率。本次常量 `[1,6]` 基本配置未证明其优于现有 64 位路径。
