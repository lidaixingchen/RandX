# 性能门禁策略集中方案

日期：2026 年 10 月 2 日

代码基点：`628ee59`（双头文件共同实现来源已落地）

状态：设计方案，供后续实施与验收使用。

## 1. 目标与明确判断

将基线选择、比较模式、结果分类、回归通知资格和基线发布资格集中到可直接测试的 Python 门禁模块。GitHub Actions 负责查询、下载、checkout、构建、测量和上传，通过结构化输入与输出调用该模块。

当前的主要问题是门禁决策由多处工作流条件、Shell 分支和比较脚本共同持有。比较器已经区分性能回归与输入错误，工作流却只读取步骤是否失败；强制更新的发布条件也没有表达测量完成这一前提。因此，继续增加比较器单测无法验证整条门禁的行为，必须把“这些结果意味着什么、接下来允许什么”纳入同一个测试入口。

门禁模块接收运行上下文、基线查询结果、执行状态和测量结果，集中决定这些事实对应的门禁结论。Actions 平台适配层和本地文件适配层调用相同的决策函数。未来调整发布规则或比较组时，可通过这一入口验证完整行为。

实施范围包括比较器的可调用接口、策略配置、门禁模块、工具测试、工作流接入及说明文档。工作流采用统一计划、三个独立 runner 测量组和统一求值发布；每组在自己的 runner 上测量新旧版本，保留全部用例、轮数、容差和抽样固定延长确认流程。生产头文件、共同 C++ 来源、随机输出序列和消费方式不在本次改动范围内。

## 2. 当前结构与证据

| 当前事实 | 位置 | 对门禁的影响 |
| --- | --- | --- |
| 历史数量查询与有效基线筛选分开执行，有效基线只搜索前 30 个 artifact | `benchmark.yml` 的 `Find Baseline Run` | 较早但仍有效的基线可能被漏选；查询与筛选没有统一的测试入口 |
| 首次初始化、显式更新、历史基线不可用由 Shell 分支判断 | `Check Baseline Availability` | 相同输入对应的比较与发布模式难以在本地重放 |
| 通用性能使用当前 runner 重新构建、测量历史提交 | `Configure & Build Baseline`、`Run Baseline Benchmark` | 下载的历史 `result.json` 不直接作为本次耗时比较值 |
| 抽样使用当前 `benchmark_gbench.cpp`，分别编译历史与当前头文件，覆盖 C++17、C++23 | 同源抽样构建与运行步骤 | 两边应具有相同的完整测量项集合 |
| 初测疑点与邻接项执行一次固定、双边顺序均衡的延长确认 | `confirm_sampling_benchmark.py` | 最终门禁应使用确认后的完整结果，保留其测量语义 |
| C++17、C++23 比较步骤各自嵌入一份测量项集合检查 | 两个 `Compare Same-Source Sampling` 步骤 | 检查规则重复，并将集合差异作为普通步骤失败返回 |
| 比较 CLI 已用退出码 1 表示回归、2 表示输入错误 | `compare_benchmark.py` | 工作流按步骤失败创建回归 issue，丢失了分类信息 |
| 强制更新分支以 `hashFiles('result.json')` 判断发布条件 | `Upload Current Result as Baseline` | 文件存在没有证明全部必需测量成功；发布分支未限定 master |
| 比较器已有单测，Python CI 已运行聚合与确认单测，但未运行比较器单测 | `test_compare_benchmark.py`、`ci.yml` 的 `python-tests` | 需要补齐现有比较器覆盖与新增策略覆盖 |
| 性能 workflow 的路径过滤未包含比较器测试文件 | `benchmark.yml` 的 push、PR paths | 门禁测试变更与性能 workflow 的触发范围不完整 |

这些证据支持集中策略，并以比较组为边界并行测量。现有工具已提供部分噪声控制；其存在并不证明当前轮数和容差已经完成可靠性校准。策略正确性与测量可靠性分别验收。

### 2.1 耗时证据与优化优先级

2026 年 10 月 2 日的[成功 PR 性能运行](https://github.com/lidaixingchen/RandX/actions/runs/36967935663)从创建到完成耗时 26 分 50 秒，测量 job 本身耗时 26 分 48 秒。通过 `gh run view` 的步骤时间和日志核对如下：

| 环节 | 耗时 | 占总墙钟时间约比 |
| --- | --- | --- |
| 通用基准：候选 | 4 分 16 秒 | 16% |
| 通用基准：历史基线 | 4 分 14 秒 | 16% |
| C++17、C++23 抽样初测与确认 | 17 分 01 秒 | 63% |
| 全部配置与构建 | 1 分 01 秒 | 4% |
| 检出、查询、上传及其他操作 | 18 秒 | 1% |

基准测量合计 25 分 31 秒，约占 95%。头文件生成检查约 1 秒。主要耗时来源是测量矩阵与串行调度，编译缓存的收益受构建占比限制。

该次日志包含每个标准 243 个抽样用例，初测执行次数为 `243 × 2 个标准 × 2 个版本 × 5 轮 = 4,860`。以每次 `0.1s` 的计时目标粗算为 8 分 06 秒，这不是完整运行时间：每次独立进程还需要校准、准备输入与输出结果。C++17 初测与确认约 7 分 41 秒，C++23 约 9 分 20 秒；C++17 没有选中确认项，C++23 确认了 4 项。这些数量属于该次运行的观察值，后续用例清单由程序枚举。

Google Benchmark v1.8.5 的[校准实现](https://github.com/google/benchmark/blob/v1.8.5/src/benchmark_runner.cc#L292)以目标时间约 1.4 倍估算下一次迭代数，并有小样本扩展和最大迭代数约束；不能将 1.4 当作总墙钟时间的固定倍率。当前抽样每轮启动新进程并设置 `repetitions=1`，会重新校准；同一框架运行内的后续重复可以沿用已确定的迭代数。

该次通用套件包含 67 项，新旧版本各重复 5 次。当前命令未指定 `min_time`，使用 v1.8.5 [默认的 `0.5s`](https://github.com/google/benchmark/blob/v1.8.5/include/benchmark/benchmark.h#L276)。[`report_aggregates_only`](https://github.com/google/benchmark/blob/v1.8.5/src/benchmark.cc#L90)控制输出，不减少测量次数。

优先将通用、C++17 抽样、C++23 抽样拆到三个独立 runner，使测量关键路径从三组耗时之和变为最长一组。校准复用和统计参数调整进入独立实验；PR 与目标分支 push 继续分别验证其实际提交。

## 3. 模块与配置归属

| 路径 | 最终职责 |
| --- | --- |
| `tools/benchmark_policy.json` | CI 使用的基线名称、目标分支、来源 workflow、允许的发布事件、抽样初始化提交、比较组、容差、测量与确认参数 |
| `tools/benchmark_gate.py` | 配置读取、基线选择、运行计划、比较组求值、最终决策，以及命令行适配层 |
| `tools/compare_benchmark.py` | Google Benchmark 数据读取、单位换算、逐项比较、结构化比较结果和现有 CLI 输出 |
| `tools/confirm_sampling_benchmark.py` | 保持疑点选择、固定延长确认及完整结果替换；适配比较器的可调用接口 |
| `tools/merge_benchmark_repetitions.py` | 保持现有轮次合并与聚合职责 |
| `tools/test_benchmark_gate.py` | 验证基线来源、模式、预期清单、跨 job 状态、分类、通知、发布与 Actions 接线 |
| `tools/test_compare_benchmark.py` | 继续验证现有 CLI，并覆盖可调用比较接口的主要数据契约 |
| `.github/workflows/benchmark.yml` | Actions 适配层：统一计划、三组并行测量、状态与产物传递、统一求值发布及最终退出 |
| `.github/workflows/ci.yml` | 运行比较、聚合、确认和门禁测试 |
| `docs/性能门禁策略集中验收结果.md` | 实施后记录基点、实际检查命令和验收证据 |

门禁模块内部采用显式类型、枚举和数据类表达输入与结果。基线选择与决策函数不访问网络，不读取 GitHub 环境变量，不执行基准进程。命令行适配层负责文件读写；Actions 适配层负责平台 I/O。

配置保存当前测量参数：通用基准 5 次聚合测量，显式指定与当前默认值等价的 `0.5s`；抽样初测 5 轮、每项最低计时目标 `0.1s`；确认 6 轮、每项最低计时目标 `1s`；容差 `0.25`。抽样初始化提交沿用当前 workflow 的 `e0ce50a6c0dd5e3b5158efb1cbe17a68bd93edec`。CI 参数从配置解析后显式传给测量和比较工具，避免 workflow 与工具各自决定门禁阈值。

配置里的参数均使用有业务含义的键名。已配置的 master 分支、artifact 名称与 Git 提交引用属于项目策略数据。CPU 编号根据 runner 的可用 CPU 集合选取，并写入测量记录。

抽样组从绑定 CPU 的 sysfs 缓存信息读取一级指令缓存行字节数，记录为 `loop_alignment`。历史头文件和当前头文件使用同一份基准正文，均以 `-O3 -DNDEBUG` 及相同的 `-falign-functions`、`-falign-loops` 参数构建，为函数入口和循环提供共同的缓存行对齐条件。对齐参数的作用见 [GCC 优化选项](https://gcc.gnu.org/onlinedocs/gcc-14.1.0/gcc/Optimize-Options.html)。常规组沿用 CMake Release 配置。

每次配置成功后立即保留 `compile_commands.json`，链接成功后保留程序的 `objdump -d -C` 输出，分别存入 `compiler/baseline`、`compiler/candidate`。构建步骤结束后单独上传已有诊断产物；完整组产物也保留这些文件，以支持测量结果与实际指令布局的联合分析。

## 4. 输入、输出与调用顺序

### 4.1 两阶段门禁入口

采用 `plan` 和 `evaluate` 两个命令，两者复用同一模块的类型与策略。

| 阶段 | 输入 | 输出 |
| --- | --- | --- |
| `plan` | 策略配置、运行上下文、完整基线列表与所属运行元数据，或查询失败状态 | `benchmark-plan.json`，以及供 Actions 使用的固定名称输出 |
| `evaluate` | 运行计划、准备与测量 job 状态、必需步骤 outcome、预期用例清单、通用结果、抽样确认后的双边结果 | `benchmark-gate.json`、中文 Markdown 摘要、发布与通知资格 |

`plan` 对已识别的查询、元数据或上下文错误写出错误计划，明确禁止测量与发布；`evaluate` 将该错误带入最终报告。计划文件无法生成时，工作流保留原始失败状态，跳过依赖有效计划的操作。

运行上下文包含仓库身份、事件类型、ref、当前 run ID 与 run attempt、候选提交、fork PR 标识和规范化后的强制更新布尔值。候选提交是本次实际 checkout 的提交；PR 默认 checkout 的合并提交与 PR head 提交分别记录。计划包含格式版本、冻结的生效配置、模式、选定 artifact ID、所属 run ID、基线提交、抽样基点、预期比较组和必需操作清单。所有测量 job 使用这一计划，不各自重新选基线；求值使用计划内的配置。

各组产物包含组标识、当前 run ID 与 run attempt、实际候选与基线提交、预期用例清单、必需步骤 outcome、原始 JSON、确认状态和该组测量环境。来源、组标识或提交与计划不一致时报告数据错误。最终报告包含模式、实际生效配置、基线来源、各组状态、逐项比较结果、执行失败原因、豁免的回归项、`publish_baseline` 和 `notify_regression`。环境按组记录，不合成一个共享 runner 环境；文件就绪通过读取与内容解析确认。

结构化报告使用命名的格式版本常量。现有 artifact 名称及 `result.json` 保持兼容，新发布的基线 artifact 同时包含本次门禁报告。历史基线的来源与完成状态使用 GitHub 官方运行元数据判定，兼容只有 `result.json` 的历史 artifact；门禁报告用于补充本次决策的来源与豁免记录。

### 4.2 Actions 接入顺序

1. `benchmark_plan` 检查已提交头文件与共同来源一致，使用 `gh` 分页查询基线及所属运行元数据，调用 `plan` 并上传计划。有效计划才允许启动测量。
2. `measure_general`、`measure_sampling_cpp17`、`measure_sampling_cpp23` 依赖计划，并分别分配独立 runner。每组下载同一计划、checkout 指定提交，只构建自己使用的目标；测量前枚举用例，随后在本组 runner 上顺序执行双边测量与必要确认。
3. 各组在运行未取消时记录必需步骤 outcome，上传独立命名的测量产物与日志。原始步骤失败仍使该测量 job 失败；产物记录已有结果和未完成操作。
4. 最终 `benchmark` job 直接依赖计划 job 和三个测量 job，以 `if: ${{ always() && !cancelled() }}` 在上游失败或跳过后仍执行。通过 `needs.<job_id>.result` 获取 job 事实，下载各组可用产物，调用 `evaluate`；单组下载失败要记录并继续收集其他组，不能使求值直接跳过。
5. 求值先写完整报告并上传诊断产物，按报告执行基线发布，同时暴露报告就绪与通知资格输出。最终退出：通过返回 0，性能回归返回 1，数据或执行错误返回 2。保留现有最终检查名称 `benchmark`，避免接入时改变分支规则引用的检查身份。
6. 独立 `notify_regression` job 直接依赖 `benchmark`，以 `always() && !cancelled()` 和通知资格输出决定执行，因此门禁因有效回归失败时仍能通知。该 job 下载对应 run ID 与 run attempt 的报告，在共享并发组内完成 issue 查询与创建。

三个测量 job 不互相依赖，任一组失败不取消其他组。原有按 ref 的 workflow 并发取消规则继续作用于整次运行。取消时停止测量与发布；即使已上传基线产物，该运行也必须满足第 5 节的成功完成条件才能成为后续基线。

### 4.3 Actions 执行与输出契约

- 必需步骤都有稳定的 `id`，采集 `steps.<id>.outcome`。`continue-on-error` 之后的 `conclusion` 不作为测量成功证据；job 状态与步骤状态都传入求值。
- 求值、诊断上传和最终退出使用包含状态函数的条件，在前序失败后仍可执行；依赖构建的测量步骤按实际成功依赖执行。必需操作的意外跳过归为执行错误。
- `publish_baseline`、`notify_regression` 等 Actions 输出明确写为字符串 `'true'` 或 `'false'`，消费时用 `== 'true'`。空值不授予资格。计划中的布尔值保持 JSON 布尔类型。
- 求值程序在成功写出完整报告后才输出 `report_ready='true'`。报告缺失、版本不可解析、资格输出缺失或求值进程异常时，发布和通知不执行，最终退出返回 2；不得把缺失退出码当作 0。
- 基线发布同时要求报告就绪、求值步骤成功、发布资格为真、运行未取消，以及全部必需测量 job 成功；上传步骤还保留当前 job 的 `success()` 条件，前序诊断上传失败时不发布。通知 job 独立执行；后续基线选择仍要求整次来源运行成功完成。上传失败保留其原始失败，使最终 job 和 workflow 失败。
- 查询、计划传输、用例枚举、测量产物上传与下载都属于可失败的平台操作。缺失必需产物是执行错误，不按无回归处理。

[`steps` 与 `needs` 官方契约](https://docs.github.com/en/actions/reference/workflows-and-actions/contexts)、[表达式及状态函数](https://docs.github.com/en/actions/reference/workflows-and-actions/expressions)作为接线依据。workflow 负责依赖和 I/O，模块负责基线模式、完整性、回归、通知及发布策略；不从日志文本重新推断状态。

## 5. 基线选择与运行模式

### 5.1 选择规则

先确认基线候选的来源与完成状态，再按创建时间选择最新项。可用候选必须同时满足：

1. 名称匹配配置，未过期，属于本仓库和配置目标分支，head 仓库为本仓库。
2. 来源为配置指定的性能 workflow；所属运行事件是目标分支 push，或允许发布的目标分支手动运行。
3. 所属运行已完成且结论为 `success`；失败、取消、进行中的运行均不提供可接受基线。
4. 所属 run ID 与当前 run 不同。相同提交的另一成功 run 可以被选中。

创建时间相同时使用 artifact ID 作确定性排序依据。Actions 适配层通过 `gh` 获取 artifact 和所属运行的官方元数据，按 run ID 复用查询结果，将完整事实交给策略函数；不能只凭分支名和 artifact 名称认定来源。[Artifact API](https://docs.github.com/en/rest/actions/artifacts)、[Workflow run API](https://docs.github.com/en/rest/actions/workflow-runs)提供相应字段。

选中项需提供后续下载和 checkout 所需的 run ID 与提交引用。字段不足时报告基线元数据错误，避免悄悄采用更旧记录改变比较基点。列表查询失败必须作为执行错误传入，不能转成空列表或历史数量为零。

查询成功但列表为空，只能说明当前没有基线记录，不自动授权跳过历史通用比较。GitHub 自 [2026 年 9 月 24 日](https://github.blog/changelog/2026-09-24-expired-github-actions-artifacts-no-longer-shown-in-ui-and-api/)起不在相关 REST API 返回过期 artifact；记录为空也可能是正常过期或删除的结果。首次建立与重新建立基线统一通过目标分支的显式手动刷新进行。

| 条件 | 模式或结果 | 通用比较 | 抽样基点与比较 |
| --- | --- | --- | --- |
| 正常运行，找到可用历史基线 | `COMPARE` | 同机重新测量选中历史提交并比较 | 选中历史头文件；两标准都比较 |
| 正常运行，查询成功且记录为空 | 基线错误 | 门禁失败 | 提示目标分支显式手动刷新 |
| 正常运行，记录存在但均不可用 | 基线错误 | 门禁失败 | 记录基线不可用原因 |
| 目标分支手动运行且显式强制更新 | `REFRESH` | 校验当前结果，历史通用比较按计划跳过 | 有可用基线时使用该提交，否则使用初始化提交；完成测量、求值并记录回归豁免 |
| 任意模式下查询失败或选中项元数据错误 | 执行或数据错误 | 门禁失败 | 阻止发布 |
| 其他事件或分支提供强制更新请求 | 上下文错误 | 门禁失败 | 阻止发布 |

`REFRESH` 可以有意重建过期基线，但仍要求查询成功、初始化抽样引用可取得、必需构建与测量成功。历史查询之后的下载或 checkout 失败按执行错误处理，记录失败的具体阶段。

长期基线身份可由持久的已接受提交引用承载，使测量文件保留期与基线生命周期分离。该存储机制作为独立后续任务；当前交付以显式刷新处理空记录，不引入额外自动仓库写入。

### 5.2 强制更新的最终语义

强制更新表示接受本次测量作为新的目标分支基线，允许豁免有效比较产生的性能回归；构建失败、进程失败、结果缺失和数据错误仍阻止发布。

刷新限定为 `workflow_dispatch` 且 ref 为配置目标分支，当前配置为 master。强制更新仍运行两标准抽样确认与结果完整性检查，将观察到的回归项写入报告，并标明已豁免。通用候选结果必须完成预期项目和测量有效性校验。

## 6. 比较与结果分类

### 6.1 比较器接口

将 `compare_benchmark.py` 的数据读取与比较逻辑改为可调用函数，返回逐项耗时、变化率、回归项、新增项与缺失项。数据错误使用明确的异常类型，CLI 在最外层转换成现有退出码与错误输出。

`load_results` 的调用方包括确认工具，必须在同一阶段适配，使加载错误进入确认工具的失败报告并继续保存已有原始日志。现有命令行参数、表格内容含义和 0／1／2 退出码保留。CI 调用时显式传入策略配置的容差。

比较仍使用 `cpu_time` 的 median，单位换算与零基线行为沿用当前比较器；严格大于容差才判定回归，恰好等于容差通过。本次不调整计算公式与测量统计方法。

### 6.2 各组的完整性契约

| 比较组 | 测量来源 | 完整性与新增项规则 |
| --- | --- | --- |
| `general` | 本组 runner 上的当前通用结果与历史提交重测结果 | 两边各自实测集合等于自己的预期清单；基线项必须全部存在于候选中；允许候选新增项 |
| `sampling_cpp17` | 本组 runner 上的当前基准源码、两套头文件、确认后结果 | 双边预期清单相同且非空；双边完整实测集合等于预期清单 |
| `sampling_cpp23` | 本组 runner 上的当前基准源码、两套头文件、确认后结果 | 双边预期清单相同且非空；双边完整实测集合等于预期清单 |

每组在完整测量前对计划要求测量的每个二进制调用 `--benchmark_list_tests=true`，使用约定的完整套件选择参数生成预期清单；刷新模式的通用组只枚举和测量候选。完整套件不设置临时子集过滤；测量命令与清单命令的选择参数一同记录并由接线检查验证。清单解析与实测记录使用相同的规范化用例身份，明确区分运行名称和 median 后缀，拒绝空清单、重复用例和重复 median 条目。

抽样要求 `基线预期集合 = 候选预期集合 = 基线完整实测集合 = 候选完整实测集合`，不能用双边实测相等替代完整性。初测每轮都须符合预期清单，聚合与确认后仍须满足完整清单。用例枚举失败归为执行错误；清单或结果结构不符合契约归为数据错误。用例名称来自程序枚举，不在配置中硬编码 243、67 等历史数量。

初测与确认的每条原始记录在聚合前校验 `cpu_time`、`real_time` 为非负有限数，并显式拒绝布尔值。原始轮次无效时报告数据错误，正常的聚合中位数不能替代原始记录有效性。

通用组的两边基准源码可能不同，先分别验证各自测量完整性，再执行基线项包含关系检查；新增项目没有可比历史值，报告新增项。名称相同只证明比较身份相同，基准工作负载语义的变化仍需在相关基准变更中审查。

抽样确认工具继续选择超容差项和既有邻接项，只执行固定的一轮延长确认。确认子集实测集合必须等于已选确认清单；确认结果覆盖被选项，其余初测项保留。门禁读取完整确认结果、确认清单与完成状态；确认中断时不能把局部结果当成通过。没有疑点时仍记录确认阶段已完成，其完整输出就是初测结果。workflow 内重复的集合检查迁入门禁组求值。

CI 保持基线项完整性要求。比较器现有 `--allow-missing` 可用于显式本地操作，门禁不自动开启该选项。

### 6.3 状态及汇总规则

| 组状态 | 含义 | 对普通门禁的影响 |
| --- | --- | --- |
| `PASS` | 有效测量满足完整性契约，比较未超容差 | 本组通过 |
| `REGRESSION` | 有效比较得到超容差项 | 阻断普通门禁；显式刷新时记录豁免 |
| `DATA_ERROR` | JSON、测量值或测量项集合不符合输入契约 | 阻断全部模式 |
| `EXECUTION_ERROR` | 查询、下载、构建、测量或确认失败，或必需步骤意外跳过 | 阻断全部模式 |
| `SKIPPED` | 计划明确允许跳过的历史通用比较 | 仅在刷新模式有效 |

最终门禁先判定执行与数据错误，再判断未豁免回归，最后判定通过。所有组的已知结果都保留，避免先出现的一个回归掩盖另一组的数据错误。取消运行具有独立取消状态，发布和通知资格均为 false。

刷新模式中，通用历史比较虽然跳过，当前 `result.json` 的读取、完整用例清单及测量有效性检查仍为必需条件。跨 job 汇总同时检查平台 job 结论与产物中的必需步骤状态；job 失败且已有有效比较时保留该比较证据，但最终仍按执行错误失败。

## 7. 通知与基线发布

### 7.1 回归通知

只有有效比较产生未豁免的 `REGRESSION`、该组计划中的全部必需步骤 outcome 均为 success，且运行上下文允许写 issue 时，`notify_regression` 才为 true。失败步骤留下的完整 JSON 可用于比较诊断，该组不进入通知证据列表；job 失败但必需证据生成步骤成功时仍保留有效回归通知。fork PR 保留门禁失败及报告，通知资格为 false。

单纯的数据或执行错误不会触发回归 issue。若另一组已经确认回归，报告同时保留回归证据与错误信息；通知可说明实际回归项，最终门禁仍按错误失败。刷新模式的豁免回归不触发通知。

issue 查重与创建由 Actions 适配层的独立通知 job 执行。查询完整分页中的未关闭 benchmark 标签 issue，标题匹配回归前缀时复用已有记录。仓库内各 PR 与目标分支使用同一并发组，串行执行查询与创建，`cancel-in-progress` 为 false。issue 正文只使用报告通知证据列表中的比较组、回归项、实际容差和运行链接；基线、构建或数据错误通过 job 摘要与 artifact 说明。

### 7.2 发布条件

`publish_baseline` 为 true 必须同时满足：

1. 当前 ref 为配置目标分支，运行未取消。
2. 事件是目标分支 push，或该分支的显式手动刷新。
3. 生成检查、计划传输、必需构建、用例枚举、当前通用测量、双标准抽样测量及确认全部成功；三个测量 job 均成功且必需产物完整到达求值 job。
4. 当前结果有效；每个必需比较组均满足本模式的通过或豁免规则。
5. 最终门禁报告完整，并明确给出可发布结论。

PR、普通手动运行和其他分支运行不发布基线。普通 push 的回归阻止发布；显式刷新可以发布带回归豁免记录的有效结果。文件存在只是读取结果的前提，发布资格由完整决策产生。

只有最终 `benchmark` job 执行基线发布，测量 job 只上传各自的诊断和测量产物。上传动作仍负责实际发布；上传失败使 job 失败，并记录平台错误。后续选择还要求整次来源运行成功完成，不能仅凭本次报告的发布资格使用失败运行的产物。用于排查的结果与日志继续在失败运行中上传，它们与 `benchmark-baseline` 的发布资格分别判断。

## 8. 测量并行与可靠性边界

### 8.1 组内同机、组间独立

三个测量 job 各自完成双边 checkout、构建、枚举与测量。通用组沿用当前双边顺序；抽样组保留固定 CPU 绑定、初测交替顺序及确认双边顺序均衡。新旧版本不能分配到不同 runner 后直接比较。各组分别计算变化率，最终汇总状态，不跨 runner 比较绝对耗时或汇总成一个耗时比值。

通用组只构建通用目标；各抽样组只构建自己标准的双边目标。重复准备、依赖获取、计划与结果传输会增加部分 runner 用量。方案主要减少墙钟等待，不承诺总 runner 分钟不变。

墙钟时间模型为 `准备计划 + max(三个组各自的排队、准备与测量耗时) + 汇总发布`。该次最长测量组约 9 分 20 秒，支持将等待时间降至最长一组附近的判断；实际收益受账户并发额度、排队、runner 环境和确认项数量影响，不把单次估算作为固定 SLA。

### 8.2 性能验收

记录并行后每个 job 的排队、准备、构建、初测、确认、传输及总耗时，同时记录整次墙钟时间与 runner 分钟。比较改造前后的相同候选、基线和策略配置，重复观察正常通过及需要确认的运行，报告样本和实际收益。

性能改善成立的前提是预期清单、实测完整性、轮数、计时目标、容差和固定确认规则均保持约定。不能用缺失用例或未完成确认解释提速。三组即使分配不同型号 runner，也只在各组内部进行同机比较；环境差异作为报告事实保留。

### 8.3 后续测量实验

校准复用单独设计和验证。简单把抽样改为单边连续 5 次，会改变双边交替顺序；固定迭代数也可能使更快的一边达不到既有计时目标。实验必须分别校准双边、记录每项迭代数与实际计时，保留双边顺序控制，并量化收益和测量影响后再接入。

采用同一提交的双边重复测量估计误报率，评估频率变化、调度竞争、缓存和 runner 差异，再决定轮数与阈值。CPU 绑定和 median 已减少部分噪声，但不构成当前 25% 阈值充分性的证明。[Google Benchmark 方差说明](https://google.github.io/benchmark/reducing_variance.html)提供噪声控制依据。

滚动基线用于检测相邻已接受版本间的明显退化，不能约束长期累计退化；长期性能参照与持久基线身份另行建设。当前 PR 与目标分支 push 各自测量实际 checkout 提交，保留合并后验证。

## 9. 实施顺序

### 阶段一：建立可调用比较结果

提取比较函数与明确的数据错误类型，保留既有 CLI 契约，同步适配抽样确认工具。补齐比较器 CI 执行。通过既有比较、聚合和确认测试，证明比较公式、确认轮数和结果替换规则维持现有契约。

### 阶段二：实现集中策略

新增配置与门禁模块，通过 `plan`、`evaluate` 接口实现完整决策表。测试输入包括合成运行上下文、分页后的 artifact 列表，以及小型 Google Benchmark JSON 样本。测试执行本地文件适配层，与 Actions 使用相同的门禁入口。

这一阶段验证查询失败、来源与运行状态、空记录显式刷新、意外跳过、预期清单、跨 job 状态、回归豁免和发布资格。完整测试通过后再切换 workflow。

### 阶段三：接入 Actions

建立计划 job、三个独立测量 job、最终 `benchmark` job 和独立通知 job，替换工作流内的基线选择分支、重复集合检查和决策表达式。测量工具、同源构建与确认顺序沿用现有实现；清单与状态传输满足第 4、6 节契约。采集真实步骤 outcome 与 job 结论，让求值、诊断上传和最终退出在失败场景下保持可执行。

将配置、门禁模块及其测试、比较器测试加入性能 workflow 的 paths；在普通 Python CI 中执行全部相关工具测试。接线检查验证三个组独立执行、最终 job 直接依赖全部组、完整套件选择参数、步骤 id、状态传递、布尔输出比较及失败后的求值与退出条件。工作流静态检查和真实故障演练分别验证接线结构与平台执行语义。

### 阶段四：远程演练与交付

在实施任务的已授权远程验证范围内，使用普通 PR 和目标分支手动运行检查真实查询、计划传输、三组同机重测、确认、报告与发布路径。演练单组失败、产物下载失败、求值异常及取消，验证其他组的结果保留和发布阻断。按第 8 节记录耗时、并发与 runner 用量。强制刷新演练是实际更新基线的操作，单独记录其运行链接与产物；方案阶段的证据来自已有运行，远程验证与刷新在实施阶段执行。

提交分为可调用比较接口、策略模块与测试、工作流接入及验收文档，描述使用中文约定式提交。各提交包含对应调用方与测试，使中间状态可验证。

## 10. 必须覆盖的验收场景

| 场景 | 预期结果 |
| --- | --- |
| 有效基线位于候选列表后续页 | 能选中，不误判为历史基线不可用 |
| 多个分支、过期记录和当前 run 混在列表中 | 仅从符合策略的记录中选择最新基线 |
| 同名产物来自其他 workflow、其他 head 仓库或 PR 事件 | 不作为可接受基线 |
| 最新同名产物来自失败、取消或进行中的 run | 排除；按完整规则选择最新可接受项 |
| 同提交的另一 run 提供基线 | 可以选中；当前 run 被排除 |
| 查询失败，或选中基线缺少必要元数据 | 门禁错误，不初始化、不发布 |
| 普通运行当前记录为空，即使抽样通过 | 基线错误，阻止发布；需显式手动刷新 |
| 目标分支显式刷新且当前记录为空 | 使用初始化抽样提交，全部必需操作与结果有效后可发布 |
| 历史记录存在但均不可用 | 正常运行失败；有效的显式刷新使用初始化抽样基点 |
| 耗时变化恰好等于容差，以及略大于容差 | 分别通过、回归，维持严格大于语义 |
| 通用候选新增项、通用基线项缺失 | 分别报告新增、数据错误 |
| 任一标准的抽样项集合不完整 | 数据错误，阻止发布，单独不创建回归 issue |
| 双边实测集合相同但同时漏掉预期用例 | 数据错误，阻止发布 |
| 空清单、重复枚举名称或重复 median 名称 | 数据错误，不能用覆盖记录获得通过 |
| 初测或确认原始轮次的 cpu_time、real_time 为布尔值、非有限数或负数 | 聚合前判定数据错误，即使中位数正常也阻止发布 |
| 完整套件误传子集过滤参数 | 接线检查失败；不得作为完整测量结果交付 |
| 通用组两边清单不同，但各自实测完整且候选包含基线项 | 正常比较公共项并报告新增项 |
| 初测疑点确认后通过，或确认后仍超容差 | 分别通过、回归；报告采用确认后的完整结果 |
| 一个组回归，另一个组数据错误 | 同时报告；最终按错误失败；通知只引用有效回归证据 |
| 必需测量、聚合或确认步骤失败，但留下完整比较 JSON | 比较诊断保留；该组不进入通知证据列表，阻止发布 |
| job 失败但该组必需证据生成步骤全部成功 | 有效回归仍可通知；最终执行错误，阻止发布 |
| 已有回归 issue 位于后续分页，或不同 PR 同时完成回归求值 | 完整分页查询并串行查重创建，复用已有未关闭回归 issue |
| 确认进程失败，或必需步骤意外跳过 | 执行错误，保留已有日志，阻止发布 |
| 确认子集缺项或完整替换结果漏项 | 数据错误，阻止发布 |
| 一个测量 job 失败，其他两个完成 | 其他组继续执行并保留结果；最终执行错误，阻止发布 |
| 必需产物缺失、下载失败，或传入其他 run attempt 的产物 | 分别按执行错误或来源数据错误失败，保留其他组证据 |
| 求值程序异常、报告缺失或退出码输出缺失 | 最终失败，禁止通知与发布 |
| 输出值为字符串 `'false'` 或为空 | 发布、通知条件不成立 |
| 步骤 outcome 为 failure，conclusion 因容错为 success | 必需步骤仍按执行错误处理 |
| 当前 JSON 存在但含错误记录，且请求刷新 | 数据错误，阻止发布 |
| master 显式刷新，全部必需步骤成功但抽样存在回归 | 通过并记录豁免，可发布，回归通知为 false |
| PR、其他分支请求刷新或运行被取消 | 按上下文错误或取消处理，阻止发布 |
| fork PR 确认回归 | 门禁失败，报告保留，回归通知为 false |
| 历史 artifact 只有 `result.json` | 能按既有 run 与提交元数据取得基线，不要求新增摘要 |
| 发布上传失败，或上传后整次运行取消 | 本次运行失败或取消，产物不进入后续可接受基线 |
| 三组在独立 runner 上完成完整测量 | 每组各自在同机比较，最终统一求值；记录墙钟和 runner 分钟 |

本地使用 Miniconda 提供 Python 运行环境，按以下命令分别运行比较、聚合、确认及门禁测试：

```powershell
$env:PYTHONUTF8 = '1'
```

workflow 接线检查纳入门禁测试命令。Python 决策测试不启动完整性能测量；真实 Linux runner 验证 CPU 绑定、双边运行顺序、跨 job 产物操作与故障处理。生产 C++ 来源未改动时，以生成检查及既有 CI 为约束，不额外复制整套算法测试。

## 11. 完成标准

交付应同时具备以下证据：同一输入通过本地与 Actions 适配层得到相同决策；基线完整列表与所属运行元数据可重放；空记录通过显式刷新处理；预期用例清单证明完整测量；三组在独立 runner 上各自完成同机比较并在一个报告中解释；数据或执行错误与性能回归正确区分；显式刷新只豁免有效回归；基线发布依赖全部必需 job、步骤和有效结果；失败、取消及报告缺失正确阻断发布；比较器与门禁单测进入 CI；并行后的耗时和 runner 用量有真实运行证据。

校准复用、测量统计方法与阈值调整、持久基线存储和生产算法优化属于后续独立任务。本项完成的判断依据是策略归属集中、完整性与错误因果明确、工作流按报告执行，以及完整测量下的等待时间改善。
