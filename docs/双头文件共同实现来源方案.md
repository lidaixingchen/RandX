# 双头文件共同实现来源方案

日期：2026 年 10 月 2 日

行为比较基点：`85b7de2`

状态：生成流程与共同来源迁移已落地；验收范围见第 11 节及迁移清单。

## 1. 目标与明确判断

采用共享 C++ 源码片段、标准专属声明和确定性拼装流程，为 `RandX.hpp` 与 `RandX_Cpp17.hpp` 建立共同实现来源。生成后的两个头文件继续提交到仓库，并作为现有安装、直接包含、基准和文档生成的输入。

主要问题是相同算法知识仍由两个生产头文件分别持有：抽样内核收拢后，每个版本内部只有一份选择循环，但跨版本仍需人工同步。共同来源将相同算法正文集中到一个维护位置；标准专属声明显式保留各版本的能力契约。

共享契约测试和抽样前后行为比较已经落地，能够验证两个生成结果。它们降低了本次迁移的验证成本，但不会自动证明生成来源唯一。因此实施需要同时建立源码归属清单和生成结果一致性门禁。

本方案改变维护方式和构建前的开发流程。生产公开接口、算法、输出序列、调用与异常时序、独立头文件交付形态保持现有契约。消费者直接构建已提交的头文件；Python 仅用于维护者和生成检查。

本项目长期支持两个标准版本、共同算法较多，并要求两份头文件各自独立分发。在这些条件下，共同维护源码与单文件交付产物分离是推荐实践。收益来自一次算法修改同时更新两个交付结果；主要维护成本来自片段边界、来源定位和生成流程，需要通过小范围试点验证。

该架构有一手实践依据：[nlohmann/json 的贡献规范](https://json.nlohmann.me/community/contribution_guidelines/#amalgamate-the-source-code)要求从维护源码生成单头文件，并通过 CI 检查产物是否过期；[SQLite 的 amalgamation 说明](https://www.sqlite.org/amalgamation.html)也采用维护源码与单文件交付分离。这些实践支持源码归属和交付方式的选择，片段粒度与标准适配仍以本项目的试点结果为准。

## 2. 当前结构与具体证据

| 事实 | 当前位置 | 设计含义 |
| --- | --- | --- |
| 两头文件分别持有相同抽样内核及分布生命周期策略 | `SampleRandomAccess`、`SampleReservoir`、`SampleFixedIndexDistribution` | 可作为共同源码的完整模块迁移 |
| 几何分布正文相同，模板声明采用不同约束 | 主头文件 `RandGeometric` 与兼容头文件对应重载 | 声明按版本保留，算法正文共享 |
| Beta 辅助采样和数值处理分别维护 | `SampleGammaLogScale`、`ComputeBetaSampleFromLogScale`、`RandBeta` | 公共数值知识可以集中，而不改浮点运算次序 |
| C++17 拥有特征检测、SFINAE 和条件属性宏 | `is_random_engine`、`is_seed_sequence`、`RANDX_NODISCARD_CXX20` | 这些是实际标准差异，需要专属来源 |
| C++23 提供 Concepts、ranges 与 constexpr 随机 | 主头文件的概念、ranges 和编译期部分 | 保留完整标准专属实现及其位置 |
| 两标准的声明与定义顺序存在差异 | 引擎特征、序列化和 `MakeStreamEngine` 等区域 | 生成顺序需要分别声明，不能自动按名称重排 |
| 安装与包配方仅消费两份头文件 | `CMakeLists.txt`、vcpkg port、xmake 配方 | 继续以生成头文件为消费入口 |
| Doxygen 当前直接读取两个头文件 | `Doxyfile` 的 `INPUT` | 文档仍从实际交付接口生成 |

源码基点包含共享契约测试和抽样内核收拢。抽样实现中的 `Selection`/`Draw` 分布生命周期、局部迭代器引用、静态引擎获取器、空请求快路径及 `RANDX_DETAIL_SAMPLE_INLINE` 属性都纳入共同来源，保持现有展开和调用方式。

源码基点的生产头文件未使用 `__FILE__`、`__LINE__`、`__COUNTER__`、`__DATE__` 或 `__TIME__`。生成器本身也不把日期、绝对路径、运行主机或 Git 提交号写入交付头文件。

## 3. 目标源码组织

### 3.1 文件职责

| 路径 | 职责 |
| --- | --- |
| `src/header_sources/targets.json` | 目标名称、输出文件名、对应根模板的显式映射 |
| `src/header_sources/cpp23/header.inc` | 主头文件的装配顺序、命名空间及标准专属片段引用 |
| `src/header_sources/cpp17/header.inc` | 兼容头文件的装配顺序、命名空间及标准专属片段引用 |
| `src/header_sources/common/engines/` | 公共引擎转移、跳跃与种子扩展实现 |
| `src/header_sources/common/sampling/` | 已收拢抽样内核、分布生命周期策略、位图及公共阈值 |
| `src/header_sources/common/distributions/` | 区间、权重、Beta、几何分布等公共数值正文 |
| `src/header_sources/common/security/` | ChaCha20、OS 熵源、擦除和播种的公共部分 |
| `src/header_sources/common/serialization/` | 公共状态与流格式处理实现 |
| `src/header_sources/common/convenience/` | 其他公共便捷行为及常量 |
| `src/header_sources/cpp23/`、`cpp17/` 下的领域片段 | 各标准的声明、约束、类型提取、必要实现差异 |
| `tools/generate_headers.py` | 按目标映射展开片段、检查产物并输出定位信息 |
| `tools/test_generate_headers.py` | 生成规则与命令行为的标准库单元测试 |
| `tools/test_header_sources.py` | 真实逐行映射、两版声明与完整正文定位、来源归属检查 |
| `tools/check_header_maintenance.py` | 在隔离副本中进行双标准编译诊断与恢复演练 |
| `docs/共同源码迁移清单.md` | 原有符号、共同片段、专属片段和验证契约的归属表 |
| `RandX.hpp`、`RandX_Cpp17.hpp` | 已提交、可独立分发的生成结果 |

`.inc` 文件是生成输入，内容仍为直接可阅读的 C++。优先以完整类、完整函数定义或一组相关定义作为维护单元；声明确有标准差异且正文相同时，共享完整函数体，由标准专属片段持有声明。

片段按业务行为和标准差异分组。相邻且整体相同的定义可以放在一个片段中；需要单独共享的函数体保持完整，避免为共享标点、类型名或个别语句继续拆分。函数体片段依赖的命名空间或类作用域、模板参数、参数名和前置声明，在迁移清单中随定义组登记，维护者可以从正文直接找到对应声明上下文。

### 3.2 源码所有权

- 公共算法正文在 `common/` 中只有一个维护来源，两个目标直接引用它。
- 标准专属片段拥有各自的 Concepts/SFINAE、声明、属性、类型提取与特有能力。
- 根模板拥有声明顺序、命名空间组织及标准库包含关系。
- 生成器只解释装配规则，不承担 C++ 约束推导或算法知识。
- 开发者编辑来源片段，并在同一提交中更新受到影响的生成头文件；代码审查优先阅读来源改动，再核对产物差异。

共同来源负责算法维护，标准专属来源负责接口适配，生成头文件负责独立交付。源码归属、装配顺序和来源定位共同构成维护入口。

## 4. 生成协议

### 4.1 明确的片段展开语法

模板中仅增加一种整行生成指令，例如：

```cpp
// @randx-include ../common/sampling/kernels.inc
```

路径相对于当前模板解析。生成器以被引用片段的原文替换该指令行，并支持片段继续引用片段；输入关系是一张显式的有向无环图。

普通 C++ 代码、注释和预处理器指令原样输出。片段本身携带输出所需的缩进和空行，生成器不重新排版，也不推导或改写函数声明。不存在目标需要的片段不会出现在该目标的装配图中。

`targets.json` 显式列出两目标的根模板与输出文件，生成器从这个配置读取文件名。装配顺序由模板文本确定，文件系统枚举顺序不参与生成。

生成指令只存在于维护源文件；产物保留现有业务注释、Doxygen 说明、版权与原算法署名。维护说明放在开发文档中。

### 4.2 命令接口

生成器使用项目现有 Python 3.12 可用的标准库。Windows 维护者使用 Miniconda 环境，CI 沿用现有 Python 运行环境。

| 命令模式 | 行为 |
| --- | --- |
| `--write` | 在内存中完成两个目标后，逐一写入内容发生变化的生成头文件 |
| `--check` | 在内存中生成两目标，直接比较已提交文件的正文，差异时报告目标与首处差异并返回失败；工作区文件保持不变 |
| `--output-dir <目录>` | 将两个生成结果写到指定目录，供独立包含及临时消费验证 |
| `--map-dir <目录>` | 在指定目录输出来源定位表，用于开发者从产物行号找到来源片段 |

`--write`、`--check` 与 `--output-dir` 互斥；`--map-dir` 可单独使用或与任一模式组合。模式与输出目录由参数明确选择；`--check` 配合来源映射输出时，只有显式指定的映射目录允许写入。诊断采用中文，报告目标文件、来源路径与行号。

配置目标名称对应的映射位置与规范化输出位置必须唯一，统一检测 Windows 大小写及路径别名碰撞。模板、输出与引用路径使用 POSIX 相对路径和 `/`，反斜杠在解析时报告错误并给出配置位置或引用链。输入语法错误、缺失片段和循环引用作为生成失败报告。两个目标都成功展开后才进入写入步骤，正常情况下仅更新改变的文件，避免重触发无关编译。

### 4.3 确定性与换行

输入与输出采用 UTF-8、LF、文件末尾换行。为两个根头文件与新增来源文件配置精确的 `.gitattributes` 规则，使 Windows 与 Linux 使用相同文本；保留当前打包目录的 `export-ignore` 规则。

若现有头文件需要规范化，先以独立准备提交完成编码、换行和文件末尾换行处理，逐项核对差异，并以该提交建立文本基线。纯提取与拼装保留完整产物字节；共同正文的排版和等价类型拼写统一，需另做基点与候选的行为比较及受影响领域性能验收。

两份生成头文件使用精确路径的 `linguist-generated` 属性，使 GitHub 审查默认聚焦维护来源；需要核对交付变化时展开产物差异。来源文件保持正常展示。属性仅影响审查展示与语言统计，生成检查仍读取完整文件。参见 [GitHub 生成文件展示说明](https://docs.github.com/en/repositories/working-with-files/managing-files/customizing-how-changed-files-appear-on-github)。

`--check` 直接比较按规定编码生成的文件字节。这里验证的是已提交产物是否来自当前来源，使用明文差异，不引入哈希校验或额外完整性标记。

生成结果与操作系统、工作目录、时区、Git 状态和配置文件外的环境变量无关。平台条件继续作为 C++ 预处理器条件保留，编译器在消费时选择实际平台路径。

## 5. 标准差异管理

| 差异 | 来源职责 | 验证方式 |
| --- | --- | --- |
| Concepts 与 SFINAE | 专属声明、特征与构造条件 | 现有标准专属约束测试及公共调用契约 |
| 现代与传统迭代器类型提取 | 专属公开适配；公共内核接收明确类型 | 单遍输入、只移动迭代器、哨兵和宽差值测试 |
| C++23 ranges 与 constexpr 能力 | C++23 专属完整实现 | ranges、编译期随机与洗牌专属测试 |
| `std::bit`、旋转及标准特征表达差异 | 专属实现或声明，按实际可共享内容拆分 | 引擎 KAT、位宽契约、编译矩阵 |
| C++17 条件属性与相等运算表达 | C++17 专属属性与声明 | C++17/C++20 兼容矩阵和类型检查 |
| 定义与前置声明顺序 | 各根模板显式排列 | 单头文件包含、完整测试与消费者构建 |
| OS 熵源与架构分支 | 公共片段保留既有条件编译 | Windows/MinGW 和既有跨平台编译、CSPRNG 测试 |

迁移前逐项判定正文是否相同。文字相似不是共享依据；表达不同但行为一致的代码，先按各自专属片段保留，后续如需改变表达方式则按独立重构验证。

公共来源可以包含 C++17 可用的模板和平台条件；C++23 特有表达只进入对应目标。生成器不会把 Concepts 自动翻译成 SFINAE。

已存在的 `RANDX_NODISCARD_CXX20` 与 `RANDX_DETAIL_SAMPLE_INLINE` 保留定义、使用和解除位置。抽样 `Selection`/`Draw` 策略保持在公共算法模块内，标准专属入口继续选择当前策略。

## 6. 开发、诊断与覆盖率

### 6.1 正常开发流程

1. 通过 CodeGraph 查看交付头文件中的符号、调用与影响面。
2. 用来源定位表或生成器的装配追踪，将相关产物行号对应到来源片段。
3. 修改共同片段或对应标准专属片段，执行 `--write`。
4. 执行 `--check`，运行受影响的契约，再执行规定的整体验收。
5. 同一提交包含来源、受影响产物与相应测试。

CodeGraph 继续以完整生成头文件作为结构查询入口；函数体片段可能缺少独立声明上下文，结构查找与来源编辑分别通过完整产物、定位表和迁移清单完成。定位表包含目标行区间、来源文件与来源行区间，支持从产物定位来源，也支持从来源查找全部目标中的展开位置。定位表开发时即时生成，不作为交付头文件依赖。

批次 A 必须完成一次维护演练：通过一个已共享算法的符号定位来源，确认声明上下文，在共同正文中进行一次局部修改，重新生成并核对两个目标对应位置的变化，最后从一次编译诊断定位回来源及其声明。演练完成后恢复来源并重新生成，使交付产物仍与文本基线一致。演练验证定位和编辑流程，不形成产品行为改动；结果只记录通过状态和必要的定位能力证据。

### 6.2 编译位置与文档

生成头文件不插入 `#line`，编译诊断和覆盖率继续定位到实际消费的 `RandX.hpp` 与 `RandX_Cpp17.hpp`。Doxygen 继续读取这两个头文件，公共说明与声明专属说明分别从其来源片段输出。

片段拼装不引入新的函数调用、命名空间、作用域或类型别名。特别保留局部 lambda 所在的公开函数、模板参数与属性位置，降低已验收抽样优化行为变化的风险。

### 6.3 迁移文本与覆盖率验收

每个源码提取批次以最近已验收提交为比较基点，直接比较两份完整生成头文件的字节，要求与该基点完全一致。比较读取已提交基点的文件内容及候选文件内容，不再做换行、空白或格式归一化，也不使用哈希。连续的纯搬移批次保持同一文本基线；若其间合入独立生产代码变更，以该变更验收通过后的提交更新文本基线。

`--check` 验证当前来源能否准确生成已提交产物；迁移前后文本比较验证源码搬移是否保持原交付代码；归属清单验证共同算法是否集中维护。三个条件分别验收，行为测试继续检查现有调用契约。

沿用现有生产头文件覆盖范围和 80% 行覆盖率门禁，并保留编译矩阵、parity、注册清单、基准和消费检查。产物字节完全一致的搬移批次，人工核对重点是来源归属、生成规则和维护流程；不额外重复建立同一生产代码的性能或覆盖率证据。源码片段不进入额外的覆盖率分母。

需要调整声明表达、函数作用域、算法、属性或产物排版时，以独立变更推进。此类变更按实际影响执行迁移前后行为、同机性能和覆盖率比较；行号变化时通过来源映射核对已覆盖语句及关键分支。验收通过后，为后续搬移建立新的文本基线。

## 7. CI、发布与包消费

### 7.1 生成结果门禁

生成检查在批次 A 的首个生成源码提交中接入，在该批次合入前成为必要合并检查，并在后续批次持续执行。在 `.github/workflows/ci.yml` 增加生成检查任务：运行生成器标准库单元测试和 `--check`；源码提取批次另须直接比较已验收基点与候选的两份完整产物，并提交文本一致的验收结果。编译矩阵、parity、注册清单核对与覆盖率任务依赖生成检查成功，继续消费已提交产物。

生成检查的触发范围覆盖 `src/header_sources/**`（含目标配置）、生成器及其测试、两份产物、`.gitattributes` 和相关工作流。基准与文档工作流在批次 A 同步接入相关触发规则，并在编译或生成文档前执行 `--check`，保证独立工作流也消费与来源一致的产物。

生成检查直接执行一致性验证，不自动回写仓库或提交。变更来源但遗漏产物会得到明确失败，维护者在本地重新生成并提交。

### 7.2 CMake 与独立使用

普通 CMake configure、build、install 继续读取已提交头文件。增加默认关闭的维护选项 `RANDX_ENABLE_HEADER_TOOLS`；仅在选项开启的分支内执行 `find_package(Python3 3.12 REQUIRED COMPONENTS Interpreter)`，并注册显式生成与检查目标。两个目标只在主动调用时运行，不加入默认构建或安装依赖。该接入不改变现有测试工具的 Python 探测规则；普通消费者和包管理器安装过程不增加 Python 依赖。

消费验收在临时目录分别复制一份生成头文件，并仅以该目录作为项目头文件包含路径编译示例。标准库和平台链接依赖沿用现有规则，验证产物不会包含 `src/header_sources` 或本仓库路径。

同一程序使用哪一种头文件继续遵守现有约定；两个目标分别构建，不增加同时包含两个同命名空间实现的要求。

### 7.3 发布与归档

发布前执行生成检查及既有测试，Git tag 中同时包含共同来源和正确的生成头文件。源码归档保留维护源文件，包安装继续只安装当前两份头文件与 CMake 配置。

vcpkg 与 xmake 当前消费路径保持不变。更新发布指南，明确来源编辑、产物生成和发布检查顺序；包版本、归档引用与配方校验字段按既有发布流程在实际发布时处理。

先建立比较基点，再按 A 至 D 组织共同来源；纯提取与拼装保持完整产物字节，排版和等价表达统一独立验证行为。批次 A 验收同时证明产物文本一致、首批生成门禁有效和维护流程可用，之后继续迁移抽样与其他领域。新算法、语义调整和性能策略变化以独立任务推进。共同算法使用两标准均支持的等价表达；标准能力边界保留明确适配。

源清单记录每个已迁移符号或相关定义组的来源、目标使用位置、声明上下文和对应契约；保留的标准专属正文登记实际标准能力。完成标准是算法维护知识集中、片段边界可理解和维护流程可用，不以共享行数百分比作为门禁。

每批提交同时更新来源和对应产物，使用中文 Conventional Commits，例如 `build(headers): 接入双版本头文件生成`、`refactor(distribution): 共享数值分布实现来源`。

## 9. 验证与完成标准

### 9.1 生成工具

- 同一输入连续生成结果相同；从不同工作目录运行结果相同；Windows 与 Linux 输出相同字节。
- `--check` 对正常产物成功，对遗漏、正文差异和错误展开返回失败，保持工作区文件不变。
- 相同的 `--write` 第二次运行不重写文件，避免无关 mtime 更新。
- 目标映射顺序、递归片段、空行、缩进、UTF-8 中文、末尾换行和引用诊断有标准库单元测试。
- 来源定位覆盖声明和正文，支持产物到来源及来源到全部展开位置的查询，并正确处理同一片段在同一目标中多次引用及在不同目标中的位置。
- 临时输出可独立包含，不需要维护来源目录。
- 批次 A 的维护演练通过，演练完成后的来源与产物恢复至已验收文本基线。

### 9.2 生产行为

- 每个纯搬移批次的两份完整产物与已验收文本基线逐字节一致；该比较独立于 `--check` 和跨标准 parity。
- 所有原有符号及重载归属清单完整，声明顺序、公开类型、默认参数、属性和标准专属能力保持契约。
- 共享公共测试在两个标准目标中完整注册，标准专属测试、随机执行顺序、debug/release 与既有三编译器矩阵通过。
- 七种 PRNG KAT、ChaCha20 RFC KAT、编译期契约与现有完整 parity 通过。
- 发生生产代码变更的独立重构，在同一工具链下比较基点与候选产物的确定性输出和引擎状态；涉及抽样时执行现有 `tools/compare_sampling.py` 的完整观察。
- 对随机播种和 OS 熵源行为执行现有可观察契约，保持安全熵源失败与通用播种的各自语义。
- 生产覆盖率满足现有门禁，原已命中算法语句与关键分支继续得到验证。

### 9.3 性能和消费

- 既有基准工作流及门禁持续执行。发生生产代码变更的独立重构，按受影响领域进行同机基线比较，保持编译选项与标准库一致；抽样参数化基准和现有引擎、分布基准满足当前门禁。
- 常规 CMake、直接编译、消费者示例、安装与包配方继续可用。
- Doxygen 对生成头文件解析成功，公开说明与标准专属接口完整。
- 普通消费者构建和安装过程中无需运行生成器。
- 维护选项关闭时，头文件生成工具不探测 Python，也不注册生成目标；开启后仅显式目标运行生成器，默认构建和安装继续消费已提交产物。

既有跨标准 parity 不能替代迁移前后文本比较：两个目标从同一来源生成，也可能同时出现同一种错误。纯搬移通过完整产物文本比较证明交付代码保持原样，生产代码重构通过前后行为比较验证变化。生成一致性、来源归属、维护演练和跨标准行为各自验收。

## 10. 主要风险与实施条件

| 主要风险 | 因果机制 | 控制 |
| --- | --- | --- |
| 标准专属声明改变调用契约 | 约束、类型提取或前置声明顺序改变，影响可调用性或重载决议 | 纯搬移保持完整产物字节一致；声明调整单独评审并执行专属编译测试 |
| 来源共同化但仍重复持有算法知识 | 在两个专属片段中保留相同算法正文，生成只替代了复制文件 | 用符号归属清单评审公共算法来源唯一性 |
| 抽样性能或异常时序变化 | 移动 lambda、属性、作用域或分布对象位置，改变优化和求值关系 | 纯搬移保持完整产物字节一致；生产代码变更单独执行完整观察与同机基准 |
| 修改来源后产物遗漏 | 开发者只提交片段，消费者仍读取旧头文件 | 批次 A 首个生成源码提交接入 `--check` 及触发规则，成为必要合并检查 |
| 片段缺少声明上下文 | 函数体依赖外部作用域、模板参数和前置声明，增加理解及定位成本 | 优先完整定义组，登记必要上下文，批次 A 完成维护演练 |
| 覆盖率表面变化掩盖遗漏 | 生产代码重构改变行号或编译器记录位置 | 通过来源映射核对已覆盖语句与分支，保持既有覆盖率门禁 |

生成工具的长期维护成本主要来自装配规则的复杂度。规则保持为目标映射和整行片段引用，把标准差异交给明确的 C++ 专属来源，使维护者能够直接阅读和修改算法。
