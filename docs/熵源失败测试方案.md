# 熵源失败测试方案

日期：2026 年 10 月 2 日

代码基点：`81fbe99`（性能门禁策略集中已完成）

状态：实现已完成，本地验收通过；跨平台与覆盖率验收由 CI 执行。实际命令与结果见[熵源失败测试验收结果](熵源失败测试验收结果.md)。

## 1. 目标与明确判断

为 OS 熵读取建立内部 seam，使测试可以稳定制造读取失败、短读、中断和部分填充后失败，并通过真实填充实现及公开安全接口验证结果。为普通播种的回退链提供显式依赖入口，验证安全随机与普通播种各自的失败契约。

主要问题是失败条件由机器环境决定。当前代码已经规定安全接口失败抛异常、普通播种继续回退，但现有测试主要覆盖真实 OS 熵成功、输出统计特征和正常重播种。正常机器上的成功测试不能证明熵源失败时没有返回结果、没有提交半份新密钥，也不能证明回退顺序。

推荐将平台调用 adapter 与熵填充策略分离。生产 adapter 读取真实 OS，脚本 adapter 返回固定字节、短读、中断或错误，两者执行相同的填充 implementation。安全接口继续使用现有签名。用于公开调用路径的注入仅在独立故障测试目标中编译启用。

熵填充模块集中管理完整填充、零长度、中断重试与失败终止，平台 adapter 负责解释原生返回值。脚本 adapter 与生产 adapter 复用同一填充算法，公开安全接口的故障测试覆盖真实调用路径。这种边界同时满足确定性测试、生产静态调用和独立头文件交付要求。

本项改变内部组织与测试能力。生产调用继续使用原生 OS 密码学熵源；公开类型、函数签名、异常类型、ChaCha20 运算、重播种阈值、显式种子输出与独立头文件交付契约保持现有行为。

## 2. 当前实现与测试缺口

| 当前事实 | 共同来源或测试位置 | 需要验证的契约 |
| --- | --- | --- |
| OS 读取在一个函数中直接调用平台接口 | `common/security/get_os_entropy_bytes_definition.inc` | 成功仅在全部字节填满后返回；错误返回 false |
| Windows 根据 `ULONG` 上限分块 | 同一来源中的 Windows 分支 | 请求长度转换正确，后续块失败立即终止 |
| Linux 循环处理短读与 `EINTR`，零返回视为失败 | 同一来源中的 Linux 分支 | 指针与剩余长度推进正确，中断不推进，永久错误不重试 |
| macOS 按状态码判断一次调用结果 | 同一来源中的 Apple 分支 | 只有成功状态可报告完整填充 |
| `SecureRandomBytes` 对零长度直接返回，OS 失败抛 `std::runtime_error` | `secure_random_bytes_definition.inc` | 零长度不调用熵源；失败没有正常返回 |
| `SecureSeed` 通过 `SecureRandomBytes` 填充一个种子 | `secure_seed_definition.inc` | 失败不能返回未完整填充的种子 |
| 默认 ChaCha20 构造调用 `reseed()` | `cha_cha20_cha_cha20_04_definition.inc` | 默认构造失败必须传播异常 |
| 重播种先读取局部种子，成功后才写状态；局部种子受 `ScopedWiper` 管理 | `cha_cha20_reseed_definition.inc` | 失败前后状态不发生部分提交；异常展开时擦除局部敏感数据 |
| `operator()` 在读取缓存前检查自动重播种 | `cha_cha20_next_definition.inc` | 到阈值后的重播种失败不能返回旧流数据 |
| `discard()` 循环调用 `operator()` | `cha_cha20_discard_definition.inc` | 在跨越阈值时传播失败；此前已丢弃的结果不回滚 |
| `RandomSeed()` 依次尝试硬件、OS、`random_device`、最终兜底 | `random_seed_definition.inc` | 顺序、短路与异常回退可确定性验证 |
| 公共安全测试共用正文 | `tests/common/security_contracts.hpp` | 继续保留真实 OS 成功与 RFC 测试，新增故障用例另设目标 |

`IsOsCryptoEntropyAvailable()` 与 `HasCryptoGradeOsEntropy()` 检测编译环境中的平台能力。运行时故障注入不能改变其编译期结果，也不能将其解释为“当前熵服务正常”。

平台契约有直接文档依据：[Microsoft 的 BCryptGenRandom 文档](https://learn.microsoft.com/en-us/windows/win32/api/bcrypt/nf-bcrypt-bcryptgenrandom)声明长度参数为 `ULONG`，系统首选 RNG 配合空算法句柄使用；[Linux getrandom 文档](https://man7.org/linux/man-pages/man2/getrandom.2.html)说明返回实际写入长度，大请求可能短读或遇到 `EINTR`；[Apple 的 SecRandomCopyBytes 文档](https://developer.apple.com/documentation/security/secrandomcopybytes(_:_:_:))要求检查成功状态后使用结果。本方案保留现有调用参数与处理语义。

## 4. OS 读取 seam

### 4.1 reader interface

一次读取返回状态和实际写入字节数。状态采用有名字的枚举，包含 `Progress`、`Interrupted` 和 `Failure`。reader 同时提供单次请求上限，填充 implementation 据此计算本次请求长度。

| 返回结果 | 契约 | 填充行为 |
| --- | --- | --- |
| `Progress` | 写入长度为正，且不大于本次请求长度 | 推进目标指针与已填长度，直到全部完成 |
| `Interrupted` | 本次没有写入 | 使用同一指针与剩余长度重试 |
| `Failure` | 本次不能继续填充 | 立即返回 false |

reader 的读取函数及请求上限访问均为 `noexcept`。平台 adapter 负责把原生结果转换成上述契约；生产填充策略信任 adapter 的契约。测试脚本记录违反 fixture 契约的情况，由测试断言报告，不增加生产路径的哈希、冗余校验或补偿性分支。

`FillOsEntropy` 接受 reader 引用、目标指针与长度。零长度立即成功，不调用 reader；非零长度仅在全部填满时成功。中断重试保留当前行为，不增加重试上限、超时或非安全备用熵源。

### 4.2 原生 adapter

Windows 的单次请求上限由 `std::numeric_limits<ULONG>::max()` 推导，继续使用 `BCRYPT_USE_SYSTEM_PREFERRED_RNG` 和现有成功判定。成功报告本次请求长度，失败返回 `Failure`。

Linux 继续使用 `getrandom(..., 0)`。正返回值报告实际字节数；负返回值只在对应 `errno` 为 `EINTR` 时返回 `Interrupted`；零返回值与其他错误返回 `Failure`。adapter 在失败调用后立即读取对应错误值，不使用上一次调用遗留的错误解释成功返回。

Apple 继续使用 `kSecRandomDefault`，成功报告请求长度，其他状态返回 `Failure`。编译环境缺少 OS 密码学接口时，原生 adapter 返回失败，零长度仍由填充快路径完成。

原生返回值转换可直接用固定状态码测试。实际系统调用的成功路径在对应平台上验证；脚本测试负责错误处理策略，不能替代真实平台调用与链接验证。

### 4.3 脚本 adapter

脚本包含固定输出字节及读取事件，如“写入前缀”“中断”“写入剩余数据”“失败”。记录每次调用的目标偏移、请求长度、实际写入和事件顺序。fixture 使用预先准备的存储，使 `noexcept` 读取期间无需分配或抛异常。

脚本耗尽时返回失败并记录意外调用，测试结束核对全部事件与调用记录。Windows 分块推进用小型、有名字的测试请求上限执行同一填充循环；实际 `ULONG` 上限推导另行核对，避免为长度边界分配超大缓冲区。

成功脚本允许全零输出。全零是有效随机字节取值，失败测试不能通过“结果非零”或“两次结果不同”判断来源是否成功。

## 5. 公开调用路径的故障注入

独立目标通过私有编译定义 `RANDX_ENABLE_ENTROPY_TEST_HOOKS` 启用内部 hook。hook 保存一个 `noexcept` 填充回调及其上下文指针；回调以脚本 reader 调用真实 `FillOsEntropy`。`GetOsEntropyBytes` 在该构建中使用当前 hook；未安装 hook 时连接原生 reader。

普通生产构建直接连接原生 reader，测试槽位、函数指针分派和作用域注入设施不参与编译。注入定义不进入已安装 CMake INTERFACE 目标，不通过环境变量、运行时设置或默认引擎激活。

fixture 的作用域守卫保存旧 hook，安装当前上下文，析构时恢复。槽位为线程局部，允许嵌套守卫，异常展开同样恢复。脚本上下文的生命周期覆盖守卫作用域。测试覆盖顺序重排、嵌套、异常恢复与两线程隔离。

槽位采用 `inline thread_local` 变量，或具有外部链接的 inline 访问函数中的局部 `thread_local` 变量，使同一可执行程序内同一线程的所有翻译单元共享一个槽位。作用域守卫禁止复制与移动，安装与恢复均在创建守卫的线程完成。

Header-only 的 inline 定义必须在一个可执行程序中保持一致。故障目标的所有翻译单元统一启用该定义，普通目标统一关闭；两种目标分别链接，禁止把不同配置的 RandX 定义混入同一程序。两个头文件分别在各自目标中包含。

两个故障目标均编译 `entropy_cross_translation_unit.cpp`。C++17 目标通过私有定义 `RANDX_ENTROPY_TEST_CPP17` 选择兼容头文件，C++23 目标选择主头文件；目标内所有翻译单元使用相同配置。共享测试在入口翻译单元安装脚本，调用另一翻译单元的 `SecureRandomBytes` 与 `SecureSeed`，核对固定材料、失败传播和脚本记录；嵌套守卫与异常展开恢复后再次跨翻译单元调用，验证槽位恢复。两线程隔离测试同时通过该入口调用，验证跨翻译单元共享与线程隔离两个约束。

故障目标只加载故障契约及必要内部测试，普通 `test_randx` 与 `test_randx_cpp17` 继续运行真实来源测试。这样两种 adapter 都有实际使用者，seam 能同时验证受控失败和真实集成。

## 6. 安全接口与 ChaCha20 失败契约

### 6.1 安全字节与种子

`SecureRandomBytes(nullptr, 0)` 正常返回，来源调用次数为零。非零请求在任一读取失败时抛现有 `std::runtime_error`，不能返回成功或转入普通播种回退。

部分读取后失败时，调用方缓冲区可以保留已写入前缀；本次不新增整缓冲区回滚或擦除承诺。测试记录前缀写入和失败传播，区分缓冲区更新与“获得完整安全结果”。

`SecureSeed()` 必须请求完整种子长度。读取失败时传播异常，不返回局部种子；读取成功时返回脚本填充后按当前表示得到的值，不引入字节序转换。

### 6.2 构造与手动重播种

默认 ChaCha20 构造在获取密钥与 nonce 失败时抛异常。显式 seed 或 key/nonce 构造继续使用确定性输入，不调用 OS 熵源。

手动 `reseed()` 的状态提交顺序保持现有实现：完整取得局部种子后才更新密钥、nonce、counter、缓存位置、重播种计数、计数器耗尽标志与移出状态；随后擦除旧缓存。首次失败和部分填充后失败均不得提前提交状态。

使用两个显式种子相同的引擎，先消费相同数量输出，再令其中一个重播种失败；后续输出必须与未重播种的控制引擎连续一致。分别在缓存部分消费与缓存耗尽的位置触发失败，对照输出跨越下一块边界。恢复成功来源后，固定种子材料生成的输出与显式 key/nonce、counter 为零的控制引擎一致，验证成功提交与缓存失效。

通过公开 key/nonce/counter 构造函数，将 counter 设置为 `std::numeric_limits<std::uint32_t>::max()`，消费完整末块后建立计数器耗尽状态。末块调用数由块大小与 `sizeof(ChaCha20::result_type)` 推导。首次读取失败与部分填充后失败均须保留耗尽状态：`reseed()` 抛现有 `std::runtime_error`，后续取值及正次数 `discard()` 仍抛 `std::overflow_error`，不能重新输出末块。恢复成功来源后，输出与新材料、counter 为零的控制引擎一致。

通过公开移动构造建立移出对象。首次读取失败与部分填充后失败均须保留移出状态：`reseed()` 抛现有 `std::runtime_error`，后续取值及 `discard()` 仍抛 `std::logic_error`。恢复成功来源并完成重播种后，对象恢复可用，取值与 `discard()` 后的输出均与新材料控制引擎一致。这两类用例分别验证生命周期标志，正常流连续性用例验证密钥流位置与缓存。

局部种子保持 `ScopedWiper` 的异常展开擦除。擦除测试使用仍存活的自有数组，在守卫结束后检查内容；结合真实重播种路径中守卫覆盖读取调用的来源检查。不得保存并读取 `reseed()` 返回或展开后已失效的栈指针，也不把测试结果扩大为对所有内存副本的证明。

### 6.3 自动重播种与 discard

按实际 `ChaCha20ReseedThreshold` 和 `sizeof(ChaCha20::result_type)` 推导边界调用数，不修改生产阈值或私有计数器。默认构造用固定材料成功播种，输出达到阈值前不再次请求熵；到达阈值后，下一次取值先尝试重播种。

若重播种失败，该次 `operator()` 抛异常，不能返回旧缓存或旧密钥生成的数据。连续失败调用继续尝试熵读取并抛异常，不推进流位置与重播种计数。来源恢复后，与新材料对应的控制引擎输出一致。

跨阈值的 `discard()` 传播相同失败；此前成功丢弃的输出属于已完成操作，不承诺整次 discard 回滚。显式确定性构造跨越阈值不触发自动重播种，维持既有输出序列。

## 7. 普通播种的回退 seam

将回退编排提取为 `RandomSeedWithSources`，接收来源对象。生产来源对象提供硬件尝试、OS 尝试、`random_device` 种子读取和最终兜底；`RandomSeed()` 固定连接该对象，保持公开签名。

来源 adapter 保留原来的 `random_device` 构造与两次取值表达式，以及最终时间、线程、地址、计数和 SplitMix64 混合方式。回退 implementation 持有优先级、短路和捕获异常的规则。测试来源对象给出固定返回值、失败或异常，并记录实际顺序。

| 来源状态 | 预期执行路径 |
| --- | --- |
| 硬件成功 | 返回硬件值，后续来源不调用 |
| 硬件失败、OS 成功 | 返回 OS 值，后续来源不调用 |
| 硬件与 OS 失败、`random_device` 成功 | 返回其种子，最终兜底不调用 |
| 硬件与 OS 失败、`random_device` 构造或取值抛异常 | 调用最终兜底并正常返回 |

最终兜底来源按当前使用约束正常返回，测试同时验证 `RandomSeedWithSources` 不传播中间来源的异常。安全接口不调用该回退 implementation。

回退失败测试通过内部依赖入口执行，公开 `RandomSeed()` 的原生连接由普通测试和来源归属检查验证。无需为测试更换整个进程的硬件或标准库随机设备，也不扩大安全字节 hook 的职责。

## 8. 测试组织与 CI

### 8.1 共享契约与目标

新增 `test_entropy_cpp17`、`test_entropy_cpp23` 两个独立 doctest 目标，并注册到 CTest。两个入口仅选择头文件，加载相同 fixture、公开故障契约和内部测试正文；另一翻译单元的调用入口按第 5 节连接到相同交付头文件。

公开故障用例使用 `公共/基础/安全熵源故障` 套件；填充、平台返回值转换、普通来源编排和擦除用例使用 `内部/熵源` 套件。扩展已有注册清单工具，为本地双目标比较与 CI 矩阵比较增加可选套件范围；故障目标显式选择上述两个套件，每个指定套件必须非空，每个套件/用例注册项必须恰好出现一次。普通目标沿用工具默认的公共契约核对规则。

故障注册清单使用独立目录与 artifact，按相同编译器、平台及构建模式比较 C++17、C++20 与 C++23，覆盖公共故障契约与内部熵源用例；macOS 核对 C++17 与 C++23 目标对。原生状态转换用例按当前平台编译，同平台跨标准清单及全部预期平台构建组的指定注册项必须一致。清单工具的单元测试覆盖公共用例一致但内部用例缺失、两个目标同时缺少指定套件、内部用例重复和完整一致的输入。

所有 fixture 数据、请求上限、预期调用数和输出材料使用命名常量。长度从数组大小、类型大小或已有生产常量推导；固定数据是测试材料，不代表实际熵质量。

### 8.2 平台与标准覆盖

Linux GCC、Clang 与 Windows MSVC 的现有标准矩阵增加故障目标运行：C++17 编译兼容头文件，C++20 同样编译兼容头文件，C++23 编译主头文件。覆盖现有调试和发布模式，使用项目已有排序种子运行重排验证。

增加 macOS 的轻量熵源 job，编译并运行两标准故障目标，同时编译普通目标，筛选真实安全字节、种子与默认构造用例。`run-selected` 从实际执行 XML 核对每个指定用例恰好运行一次且成功，并核验汇总计数及退出码；零匹配、跳过、缺失、重复或失败均使步骤失败。该 job 验证 Apple 分支及 Security framework 链接，不复制整个统计与性能矩阵。

Linux 覆盖率 job 使用独立构建目录分别编译、运行和捕获普通目标与故障目标，保留各自的覆盖率报告及配置标识。普通目标关闭注入，生产配置报告继续执行现有 80% 总体门槛；故障配置报告单独列出熵填充、异常、回退和测试注入分支的实际覆盖，必需场景逐项验收。

合并报告作为补充诊断，在核对条件编译导致的函数与分支结构差异、确认数据兼容后生成，并保留两份原始报告。合并比例不承担生产覆盖率门槛；合并兼容性错误应修正采集或报告范围后解决。未在 Linux 编译的平台分支以对应平台测试结果为证据。

新增入口位于 `tests/**`，现有 CI 路径过滤已覆盖；共同来源改动继续触发生成检查与性能门禁。性能目标保持生产配置，通过既有门禁检查性能回归。生产配置的预处理结果须确认 hook 槽位、回调分派与注入 TLS 访问均未编译，`GetOsEntropyBytes` 直接连接原生 reader；该结构检查独立于基准结果，编译命令及预处理证据写入验收记录。

## 10. 实施与交付顺序

1. 建立 reader 结果类型与完整填充函数，迁移平台调用 adapter；首先用脚本覆盖读取与进度契约，生成两头文件并验证真实 OS 成功路径。
2. 建立独立故障目标、跨翻译单元入口及作用域 hook；验证槽位共享、线程隔离和恢复，通过公开安全接口验证字节、种子、构造及正常、计数器耗尽、移出状态的重播种失败与恢复。维持 ChaCha20 当前状态提交顺序与擦除守卫位置。
3. 提取普通播种来源编排，验证回退顺序和异常处理；扩展清单工具的可选套件范围与单元测试，对接公共及内部熵源跨标准注册清单与重排测试。
4. 接入现有编译器矩阵、分配置覆盖率报告与轻量 macOS job，核对补充合并报告的数据兼容性和生产预处理结果，更新源码归属清单，完成生产配置与故障配置的分别验收。
5. 记录本地和远程验收结果，说明实际通过的平台、标准、构建模式及各失败场景；交付共同来源和同次生成的两个头文件。

实施后在 Windows 使用 Miniconda 提供生成器 Python，使用已有 CMake 编译器配置构建测试：

```powershell
conda run --no-capture-output python -X utf8 tools/generate_headers.py --check
cmake -S . -B build/entropy-tests -DRANDX_BUILD_TESTS=ON
cmake --build build/entropy-tests --config Debug
ctest --test-dir build/entropy-tests -C Debug --output-on-failure
cmake --build build/entropy-tests --config Release
ctest --test-dir build/entropy-tests -C Release --output-on-failure
```

单配置生成器分别配置调试与发布构建目录，确保两种模式真正生效。Linux、macOS 按对应 job 编译，保留平台库链接；原有 RFC KAT、跨标准输出一致性、来源生成与生产性能门禁继续运行。

完成标准是：失败场景可以本地确定性重放；公开安全接口在失败时遵守现有契约；正常流、计数器耗尽与移出状态的重播种失败及恢复、敏感数组擦除具有明确证据；普通播种回退顺序可验证；三平台 adapter 有真实集成验证；跨翻译单元共享与线程隔离通过；公共及内部熵源跨标准注册清单一致；生产配置通过既有覆盖率与性能门禁，故障配置保留必需分支证据；普通生产构建保持原生静态调用与交付形态。
