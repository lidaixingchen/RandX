## 基线问题与修复

### B01：大形状 Gamma 在 MSVC 上无法完成采样

**位置：** [默认引擎实现](../src/header_sources/common/distributions/rand_gamma_body.inc)、[显式引擎实现，第 2—5 行](../src/header_sources/common/distributions/rand_gamma_02_body.inc)。

**触发：** 使用正常的 `Xoshiro256StarStar` 引擎，调用 `RandX::RandGamma(engine, 1e308, 1.0)`。两个参数均为正有限数，通过公开接口的参数校验；理论均值为 `1e308`，仍在 `double` 有限范围内。

**实测：** MSVC `/O2`、`/std:c++17` 和 `/std:c++23preview` 均编译成功，两个程序都在 3 秒超时后被探针终止。MinGW 的对应案例可以返回。

**原因：** RandX 直接委托 `std::gamma_distribution<double>`。本机 MSVC 实现在参数初始化中计算 `sqrt(2 * alpha - 1)`；当 `alpha=1e308` 时，乘法先溢出为正无穷。拒绝采样随后得到非有限候选值；正候选的接受概率表达式出现无穷减无穷，成为 NaN，比较无法成立，循环持续取随机数。直接缺陷位于该版本 MSVC 标准库，RandX 的公开参数范围暴露了这一兼容性问题。

**影响：** 极端但合法的参数可让调用持续占用线程。3 秒是复现程序的超时预算；无法接受候选值的判断来自上述数值路径，不是仅凭运行时间推断。

**修复：** 当形状超过返回类型最大有限值的一半时，利用同尺度 Gamma 的可加性，顺序取得两个半形状样本后相加。常规形状沿用原有标准分布路径。共享回归覆盖 float／double／long double 的最大形状与有限缩放、有调用预算的完成性、常规参数输出和完整引擎状态。

### B02：Poisson 的 64 位最大均值检查失效

**位置：** [默认引擎实现，第 4—5 行](../src/header_sources/common/distributions/rand_poisson_01_body.inc)、[显式引擎实现，第 4—5 行](../src/header_sources/common/distributions/rand_poisson_02_body.inc)。

**触发：** 返回类型为 `unsigned long long` 时传入 `mean=0x1p64`，返回类型为 `long long` 时传入 `mean=0x1p63`。例如：

```cpp
RandX::Xoshiro256StarStar engine(42);
auto value = RandX::RandPoisson<RandX::Xoshiro256StarStar,
                              unsigned long long>(engine, 0x1p64);
```

**原因：** 检查使用 `mean > static_cast<double>(numeric_limits<T>::max())`。64 位无符号上限 `2^64-1` 转成 `double` 后向上舍入为 `2^64`，有符号上限 `2^63-1` 同样舍入为 `2^63`；严格大于比较因而漏过这两个已经超过整数上限的输入。

**实测：** 两标准均未抛出参数异常。固定种子探针依次得到：

```text
poisson_unsigned=accepted:18446744068236783616
poisson_signed=accepted:9223372035078219776
```

**影响：** 接口明确实现的“均值超过返回类型最大值则拒绝”保护失效。该复现没有证明返回值发生越界，也不意味着修正均值检查就能解决 Poisson 无限理论支撑集的所有表示问题。

**修复：** 共同 `ValidatePoissonMean<T>` 按整数有效位数和 double 精度选择准确边界：可精确表示的整数上限采用闭区间比较；更宽类型使用 `2^digits` 排他上限。共享回归覆盖 32／64 位有符号和无符号类型、边界相邻浮点数、默认与显式引擎，拒绝路径不消耗随机数。

### B03：输入迭代器抽样按请求量提前分配

**位置：** [sample_reservoir_body.inc，第 5—14 行](../src/header_sources/common/sampling/sample_reservoir_body.inc)。现有短输入契约见 [sampling_contracts.hpp，第 564 行附近](../tests/common/sampling_contracts.hpp)。

**触发：** 输入只有两个整数，请求数量为 `ptrdiff_t` 最大值：

```cpp
std::istringstream input("17 23");
auto result = RandX::RandSample(
    std::istream_iterator<int>(input), std::istream_iterator<int>(),
    (std::numeric_limits<std::ptrdiff_t>::max)());
```

**原因：** 水库在读取输入前调用 `reserve(n)`。接口原本在输入耗尽时返回全部已读元素，但申请容量取决于请求上限，而非实际输入数量。

**实测：** 两标准均抛出 `std::length_error`，内容为 `vector::reserve`。同样的两元素输入在较小请求量下正常返回全部元素。

**影响：** 很短甚至空的输入也可能因大请求量产生异常或过大的内存需求。这不是为实际结果分配内存失败：实际结果至多含两个整数。

**修复：** 水库通过实际读入元素逐步增长，取消按请求上限提前预留容量。共享回归覆盖最大请求量下的空输入与短输入，保留单遍进度、抽样输出、引擎消耗和异常传播检查。vector 扩容可能复制已有元素，测试只约束公开异常与遍历语义。

### B04：RandInt 的字符整数类型在 MSVC 上编译失败

**位置：** [rand_int_03_body.inc，第 4—6 行](../src/header_sources/common/distributions/rand_int_03_body.inc)；公开约束见 [C++23 convenience.inc，第 399—403 行](../src/header_sources/cpp23/convenience.inc) 与 [C++17 convenience.inc，第 444 行附近](../src/header_sources/cpp17/convenience.inc)。

**触发：**

```cpp
RandX::Xoshiro256StarStar engine(42);
auto value = RandX::RandInt<char16_t>(engine, 0, 100);
```

**原因：** RandInt 接受除 `bool` 外的整数类型，却只将比 `short` 更窄的类型提升为标准分布整数类型。`char16_t` 不满足该窄类型条件，于是原样成为 `std::uniform_int_distribution<char16_t>`。MSVC 的标准库明确拒绝此类型。

**实测：** MSVC 两标准均报 `C2338`，诊断为 `invalid template argument for uniform_int_distribution`。MinGW 允许这一实例化，因而仅靠 GCC 验证无法发现问题。

**影响：** 满足 RandX 声明约束的调用无法在受支持的 MSVC 工具链编译。`wchar_t`、`char32_t` 应纳入同类类型矩阵，但本次确认实例为 `char16_t`。

**修复：** 字符整数类型按符号和宽度映射到标准整数分布类型；既有窄类型仍采用原先的 int／unsigned int 提升。共享回归覆盖 char、signed／unsigned char、wchar_t、char16_t、char32_t，以及 C++20 起的 char8_t，另核对标准整数类型的原有输出与引擎状态。MSVC 双标准完整测试通过。

### B05：容器抽样的约束与 const 参数不一致

**位置：** [C++23 convenience.inc，第 552—563 行](../src/header_sources/cpp23/convenience.inc)、[C++17 convenience.inc，第 598—609 行](../src/header_sources/cpp17/convenience.inc)。

**触发：** 自定义随机访问 range 具有可变 `begin/end`、`size` 和索引访问，但没有 const `begin/end`。C++23 中带可变转换函数的 `transform_view` 也可形成同类场景。

**原因：** 模板检查的是可变 `Container` 的能力，参数却绑定为 `const Container&`。函数体随后要求 `range_difference_t<const Container>` 或 `std::begin(c)`，超出了被检查的能力。

**实测：** 主 Agent 的同一自定义 range 在两标准均被选入容器重载，随后在函数体中失败；C++17 报找不到 `begin(const MutableRange&)`，C++23 无法取得 const range 的差值类型。

**修复：** 容器入口保留 `const Container&` 语义，概念／trait 改为验证 const 限定后的随机访问能力；C++23 的元素关联类型也从 const range 获取。编译期矩阵确认 const 可遍历容器可调用，仅可变遍历类型在约束层被拒绝。

### B06：RandElement 额外依赖未声明的 empty 成员

**位置：** [rand_element_body.inc，第 2 行](../src/header_sources/common/convenience/rand_element_body.inc)。文档及约束见 [C++23 convenience.inc，第 131—149 行](../src/header_sources/cpp23/convenience.inc)。

**触发：** 自定义随机访问容器具有 `begin/end/size/operator[]`，没有 `empty()`，调用 `RandX::RandElement(container)`。

**原因：** 文档要求索引访问和 `size()`，模板检查随机访问能力，函数体却调用 `std::empty(c)`。这个标准函数对普通自定义容器依赖 `.empty()` 成员，不会自动回退到 `.size()==0`。

**实测：** 两标准均在 `std::empty(c)` 实例化时编译失败，容器本身满足所声明的遍历、大小与索引条件。

**修复：** 共同函数体使用 `std::size(c) == 0` 判断空输入，与公开大小能力一致。共享回归使用有 size／索引而没有 empty 成员的容器，并验证空容器异常与数组调用。

### B07：输入迭代器抽样额外要求元素可复制赋值

**位置：** [sample_reservoir_body.inc，第 24 行](../src/header_sources/common/sampling/sample_reservoir_body.inc)。C++23 ranges 包装器见 [modern_features.inc，第 203—209 行](../src/header_sources/cpp23/modern_features.inc)。

**触发：** 元素类型可以复制构造，但删除复制赋值：

```cpp
struct CopyOnly {
    CopyOnly() = default;
    CopyOnly(const CopyOnly&) = default;
    CopyOnly& operator=(const CopyOnly&) = delete;
};
std::list<CopyOnly> values(3);
auto sample = RandX::RandSample(values.begin(), values.end(),
                               std::ptrdiff_t{1});
```

**原因：** 填充水库通过构造元素完成，替换却执行 `reservoir[j] = *first`。C++23 ranges 接口只要求 `copy_constructible`，迭代器入口也没有表达对应赋值要求。

**实测：** 两标准均在水库替换处报告调用已删除的 `CopyOnly::operator=`；子 Agent 另验证了 C++23 `RandX::ranges::RandSample(values, 1)` 的相同故障。

**修复：** 水库入口明确要求元素可复制构造、可复制赋值；C++23 ranges 包装器只在输入迭代器路径追加复制赋值要求。编译期矩阵确认 CopyOnly 元素的随机访问路径继续可用，水库路径在约束层被拒绝。文档同步表达两条路径的能力要求。

### B08：MakeStreamEngine 的约束遗漏种子构造能力

**位置：** [C++23 infrastructure.inc，第 106—121 行](../src/header_sources/cpp23/infrastructure.inc)、[C++17 engines_implementation.inc，第 78—81 行](../src/header_sources/cpp17/engines_implementation.inc)、[stream_jump_apply.inc，第 92 行](../src/header_sources/common/engines/stream_jump_apply.inc)。

**触发：** 一个有效自定义 URBG 可以默认构造，具有 `void jump()`，但不能从 `uint64_t` 构造。它满足当前 jump／stream 约束；调用 `MakeStreamEngine<E>(0, 42)` 时进入函数体后失败。

**原因：** 约束只验证 `jump()`，实际建流却执行 `Engine engine{seed}`。用于表达“可以创建流”的能力检查没有覆盖实际构造步骤。

**实测：** 两标准均在种子构造处编译失败。内置流引擎都具备该构造函数，未受此问题影响。

**修复：** C++23 StreamEngine 与 C++17 HasStreamEngine 检查 `Engine{uint64_t_seed}` 表达式，与实际列表构造一致；JumpableEngine 继续只描述跳跃能力。共享编译期矩阵覆盖有效内置／自定义引擎、缺少种子构造以及发生窄化的种子构造。

### B09：MakeStreamEngine 对 jump 返回类型的两标准契约不同

**位置：** [C++23 infrastructure.inc，第 106—108 行](../src/header_sources/cpp23/infrastructure.inc)、[C++17 engines_implementation.inc，第 78—81 行](../src/header_sources/cpp17/engines_implementation.inc)。

**触发：** 自定义引擎具有 `uint64_t` 种子构造函数，但 `jump()` 返回 `int`。

**原因：** C++23 要求 `jump()` 精确返回 `void`；C++17 的 `HasJump` 仅验证表达式存在。

**实测：** 同一调用在 C++17 编译成功，在 C++23 被约束拒绝。差异发生在类型接受范围，未发现内置引擎运行结果差异。

**修复：** C++17 HasJump 统一为精确 void 返回要求，与 C++23 一致。共享编译期矩阵覆盖 void jump、其他返回类型和缺少 jump 的类型。内置流映射及引擎递推保持原有契约。

## 维护边界与待验证线索

以下内容不计入上述 9 项缺陷：

- **空目标配置的单独检查语义。** 在隔离项目中将 `targets.json` 设为 `{"targets":[]}`，`generate_headers.run_cli(["--check"], config)` 返回 0 并输出“生成头文件与来源一致”。该工具按配置列表逐个比较，空列表不会检查产物；当前真实配置包含两个目标，`test_header_sources.py` 另核对目标集合。此项描述独立命令的检查边界，不据此宣称当前 CI 漏检，也不建议重复增加相同的目标集合检查。
- **预存在的 min／max 宏。** 子 Agent 在 MinGW 中显式定义与 Windows 同形的函数式宏后，复现了标准库包含失败；主 Agent 对真实的“先包含 windows.h，再包含 RandX”场景执行 MSVC 双标准编译，均通过。本轮未确认标准 Windows 包含流程存在故障。若要扩展任意预定义宏的兼容性，应增加精确场景验证。
- **外部命名空间的流运算符查找。** 自定义引擎使用 RandX 的自由运算符时，需要符合 C++ 名称查找规则，例如显式导入 `RandX::operator<<` 和 `RandX::operator>>`。未发现内置引擎的 ADL 故障；不能仅凭没有导入外部运算符就判定序列化实现错误。

### 性能验证

性能比较采用同机 MinGW GCC 16.1.0、Google Benchmark 1.8.5，双方均编译当前 `benchmark_gbench.cpp`，使用 `-O3 -DNDEBUG` 和对应的 `-std=c++17`／`-std=c++23`。基线仅替换为 `490ca19fcd563a9861e848e3eb1faf27d9a900d8` 的公开头文件；候选使用本轮生成头文件，头文件目录在包含路径中优先。两边共享同一基准静态库、PMR 链表夹具、输入规模和固定种子。

定向运行全部 Reservoir 用例：每标准 69 项，覆盖默认引擎及显式 32／64 位引擎、空输入、短输入、小规模与百万规模。按 `tools/benchmark_policy.json` 交替进行 5 轮、每项至少 0.1 秒；再由现有确认工具固定选择超容差项及相邻请求量，先后顺序均衡地运行 6 轮、每项至少 1 秒。原始 Windows 基准 JSON 按系统 GBK 编码读取，UTF-8 副本供现有合并工具使用，测量值与原始文件均保留。

### 兼容性与验收边界

- 普通形状 Gamma、标准整数 RandInt 与有效 Poisson 参数沿用原有算法路径；极大形状 Gamma 使用新的两个半形状样本，输出序列和随机消耗随该路径改变。
- C++17 自定义建流引擎的 `jump()` 现在与 C++23 一样必须返回 void。已有返回其他类型的调用方需调整签名；这一类型接受范围的收紧应按破坏性变更管理，发布需遵守主版本与迁移要求。
- 仅可变遍历容器、缺少种子列表构造的流类型、不可复制赋值的水库元素在约束层拒绝；此前公开约束未完整表达函数体的类型要求。
- 本轮验证限于上述 Windows 本机工具链。Linux／macOS、远端 CI、完整性能门禁和真实 PractRand 统计流验收仍由对应工作流执行；推送与发布按各自验收流程执行。
