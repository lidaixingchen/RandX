## 1. 目标与交付顺序

先使质量检验按期完成并形成可追溯证据，再修正类型契约、改善流初始化、补齐安装发布与使用说明。带权无放回抽样进入独立设计；可复用权重对象和逻辑地址随机数按目标场景进入后续阶段。

各批次单独审阅、提交和验收。阶段完成依据实际结果登记，方案中的预期行为不作为已完成能力。

| 批次 | 交付目标 | 前置条件 | 发布影响 |
| --- | --- | --- | --- |
| A | 可完成的 PractRand 检验、检查点、报告与异常汇总 | 当前 runner 小规模测量 | 维护设施，生产序列保持一致 |
| B | 泊松、二项与几何分布的明确类型约束 | 类型矩阵与迁移说明 | 模板候选集收紧，按破坏性变更管理 |
| C | 内置流引擎按 ID 快速定位 | 独立数学参考、生成材料与成本测量 | 保持签名、映射、状态和后续序列 |

## 2. 共同契约与维护边界

1. 生产实现维护在 `src/header_sources/`，共同算法与类型政策放入 `common/`，Concepts、SFINAE 和标准声明放入各标准来源。来源与受影响的两份生成头文件同一提交交付。
2. 同一工具链及标准库配置下，两标准共同 API 保持参数、随机消耗、状态与输出一致。使用标准分布的接口只承诺文档规定的复现范围；跨标准库逐值一致性须有独立算法契约支持。
3. 固定 seed、跳跃距离、流 ID 映射、序列化格式、默认引擎 TLS 所有权和安全熵源失败语义保持既有契约。
4. 新功能的空请求、非法参数和退化情况单独规定是否取得默认引擎、是否消耗随机数。分配失败和采样中途异常不承诺回滚显式引擎，除非接口明确实现事务式状态提交。
5. 所有计时、长度、轮数和预算来自有名称的策略配置或算法定义。新基准与现有性能门禁分别登记；既有门禁遵循 [benchmark_policy.json](../tools/benchmark_policy.json)。
6. 消费者保持纯头文件安装形态；维护工具、测试依赖和离线生成器不进入消费者构建。

维护前阅读[共同源码归属](共同源码迁移清单.md)、[测试归属](共享契约测试迁移清单.md)及[开发与验证](开发与验证.md)。

### 3.2 执行计划与规模

工作流按“生成计划 → 引擎矩阵 → 汇总”组织。计划输出不可变的预期项目清单，每项包含引擎、RandX 提交、PractRand commit、profile、输入位宽、seed 策略及固定值、起始检查点、目标字节数、工具超时和实际测试参数。长度单位解析为字节数，等价的参数写法按解析后的语义比较。矩阵设置 `fail-fast: false`，一个引擎失败后其他引擎继续形成证据。手动指定单引擎时，预期清单相应缩小。

驱动新增 `--profile`、`--checkpoint-min` 和 `--timeout`，继续支持既有 `--engine`、`--length`、`--keep-going` 与 `--output-json`。显式 CLI 值优先于 profile；计划 job 解析后输出最终值，矩阵不得重新隐式选择默认值。长度或预算不合法时在启动生成器前退出并报告参数错误。

先用既有快速验证规模 `4GB`（驱动解释为 4 GiB）完成全部引擎的 runner 试运行，记录启动成本和完整检查耗时。将它作为初始 profile 参数，正式 nightly 目标依据测量冻结。若该规模无法按预算完成，试运行必须登记为证据不足，再以明确提交调整 profile。

单引擎工具超时须小于 Actions job 超时，差额覆盖编译、缓存、清理和上传。时间预留依据试运行步骤耗时确定并写入策略，CLI 参数不得突破 job 可用预算。长时间检验使用独立 profile，在单引擎目标已测得可完成的运行环境启用；配置目标降低必须在报告中体现。

`-tlmin` 对应起始检查点，`-tlmax` 对应最终目标，逐级完成的检查点均解析和保存。一次 PractRand 进程持续检验，不为每个检查点重启随机序列。固定统计 PRNG seed 继续沿用既有基准；ChaCha20 报告记录 OS 熵初始化，不收集密钥或敏感状态。多个 seed、位段及流交织属于后续 profile 扩展。

### 3.3 报告、分类与失败行为

- 保留现有 `TestResult` 字段和执行轴／统计轴分类。`--output-json` 继续输出项目数组，以兼容扩展记录 profile、输入位宽、起始检查点、工具超时、实际测试参数、各检查点及 `phase`；独立汇总报告记录预期项目和实际项目。工作流产生的报告必须包含计划核对所需字段，缺失字段按证据不足处理。运行中项目以 `inconclusive` 和运行阶段表达，只有结束分类后才能成为 `pass`。
- 启动项目时写入运行状态，完成检查点后更新证据，结束项目后写入最终分类。沿用现有临时文件加原子替换的写入方式。
- CLI `--output-json` 保持可用；多引擎执行时每项结束即保存。单引擎矩阵使用独立产物名，避免互相覆盖。
- `pass` 必须同时满足执行成功、完成目标检查点、有效测试数为正且没有已定义的统计失败标记。可疑标记的通过／失败阈值沿用既有政策。
- 每个检查点保存完成状态、测试数、可疑计数及可疑项目的测试名称、检查点字节数和日志位置；未完成尾部中已观察到的标记也保留。现有 `suspicious_count` 继续表示最大完整检查点的计数，新增 `run_suspicious_count` 表示整个运行中已观察到的可疑标记出现次数，Summary 使用全程计数和位置清单。增量读取按检查点更新同一记录，重复读取不增加计数。`reported_tested_bytes` 和 `test_count` 仍取最大完整检查点，跨检查点的测试数分别展示。
- 未达目标保留已完成字节数，并判为 `inconclusive`；生成器或测试器异常按现有规则判定环境错误；缺报告项目不得当作通过。
- 正常结束、工具超时和可处理的终止请求均执行既有子进程清理，并尽力写入证据。runner 被强制终止后不承诺继续上传。
- 引擎 job 用 `always()` 上传已有日志和报告；独立汇总 job 用 `always()` 检查预期清单。整个 workflow 被取消时，汇总也可能无法执行，验收记录必须保留 Actions 终态。
- 计划任务通知由汇总结果决定，区分统计失败、环境异常和证据不足。沿用既有同类 issue 去重方式，提供 run 链接、缺席项目及证据位置；实施本批次时更新现有已授权的工作流通知逻辑。

汇总不依赖日志中的“成功”字样，读取结构化报告、矩阵结果及目标完成情况。逐项核对计划与实际报告的引擎、RandX／PractRand 提交、profile、输入位宽、seed 策略及固定值、起始检查点、目标字节数、工具超时和实际测试参数；任一不一致均按数据不匹配处理，并使总体结果失败。ChaCha20 仅核对 OS 熵初始化策略，报告保持敏感材料隔离。计划生成失败、预期清单为空或汇总读取失败时，总体结果为环境异常并返回失败退出码。

### 3.4 验收

工具测试覆盖：多个完整检查点、尾部未完成检查点、早期可疑而最终正常、多个检查点出现同名可疑测试、尾部可疑标记、增量重复读取、目标未达、统计失败后结束、进程崩溃、工具超时、一次项目结束后的报告、缺席项目、损坏报告及报告身份不匹配。身份核对分别覆盖提交相同而 seed、输入位宽、检查点、目标或实际测试参数不同，以及必需字段缺失；接线检查覆盖计划失败、空预期清单和汇总失败。已有清理与分类用例继续通过。

远端验收先跑全引擎快速 profile，再跑冻结后的正式 nightly profile。每个预期项目均有原始日志和结构化结果，完整目标未达时总体结果失败。实测至少一次受控的工具超时，确认已完成检查点留存和汇总分类；不通过故意耗满 Actions 硬上限验证。

## 4. 批次 B：整数分布类型契约

### 4.1 选定政策

| 接口 | 支持类型 | 契约保持 |
| --- | --- | --- |
| `RandPoisson`、`RandBinomial` | cv 未限定的 `short/int/long/long long` 及对应 unsigned 类型 | 保持标准分布类型、参数、算法与随机消耗 |
| `RandGeometric` | cv 未限定的 integral 类型，排除 `bool`，且有效数值位数不超过 `std::uint64_t`；字符族在该边界内按当前语言能力保留 | 保持自有算法、范围检查与溢出异常 |

这两种政策分别对应标准分布要求和自有算法能力。泊松与二项直接约束受支持的标准类型；几何分布使用 `std::numeric_limits<T>::digits <= std::numeric_limits<std::uint64_t>::digits` 表达数值位宽上限，匹配现有正文的结果组装类型，并在该边界内保留字符类型。扩展整数也遵循该上限。固定宽度 typedef 以实际底层类型归属判断，不能仅凭名称保证 `int8_t/uint8_t` 可用于标准分布包装器。

新增共同类型 trait，放入 `src/header_sources/common/distributions/integer_distribution_traits.inc`，分别表达标准整数分布类型政策和几何分布类型政策，在两标准约束定义可见的位置引入。C++23 使用 concept/requires，C++17 使用对应共同 trait 的 SFINAE；默认与显式引擎重载采用相同政策。

### 4.2 修改位置与验证

修改两标准 `convenience.inc` 的声明约束及 API 说明，保留 `common/distributions/rand_poisson_*`、`rand_binomial_*` 和 `geometric_body.inc` 的生产采样正文。新增 trait 的 include 接入两标准来源，并运行头文件生成器。

共享公开测试在 `tests/common/distribution_contracts.hpp` 或新的同目录类型契约正文中装配；内部 trait 测试属于 `tests/implementation/`。覆盖八种标准整数类型、字符族、`bool`、cv 限定、枚举与浮点类型，检查默认和显式重载是否参与调用；正向用例实际实例化并运行函数体。几何分布覆盖有效位数上限附近的有符号与无符号类型。工具链提供 `__int128` 时检查其准入结果；GNU 扩展模式中确认该类型满足 integral 后，验证超出上限的有符号与无符号扩展整数在默认和显式重载中均被拒绝。该探针按编译器能力独立接线，两标准常规目标继续采用项目既定语言配置。

对既有支持类型比较固定 seed 的输出及调用后的引擎状态。保留非法参数、泊松零均值、二项边界概率和几何返回范围测试，不借本批次改变数值行为或默认引擎获取顺序。

### 4.3 兼容与发布

模板候选集收紧按破坏性变更登记，提交使用 `!` 或 `BREAKING CHANGE:`，对外发布遵循主版本政策。迁移材料说明：标准包装器调用选择支持的整型，字符值转换由调用方承担明确范围检查；几何分布调用选择有效位数满足上限的类型，更宽整数分布需求进入独立数值设计；布尔随机用途使用 `RandBool`／`RandBernoulli`，其概率模型与原计数分布不同，迁移须由调用方确认语义。

验收必须列出被拒绝类型和保留类型；开发分支通过不代表可以直接沿用旧次版本号发布。

## 5. 批次 C：保持映射的流快速定位

### 5.1 算法与适配边界

针对 `Xoshiro256StarStar`、`Xoroshiro128StarStar` 和 `Xoshiro128StarStar` 提供共同的跳跃多项式幂表与应用内核。令 `J` 为当前 jump 的状态转移，`L` 为当前 longJump 的状态转移，保持：

`state(streamId) = L^high32 · J^low32 · state(seed)`。

为每种内置引擎离线生成 `J^(2^b)` 和 `L^(2^b)`，`b` 覆盖 ID 半段的位宽。运行时按高低位的置位应用相应多项式，成本与位数及状态宽度有关，脱离 ID 数值大小。每次多项式应用使用现有线性状态递推语义，最终恢复累加后的完整状态。

幂表采用模特征多项式的紧凑表示；系数来自引擎线性转移与现有跳跃定义，有生成脚本、推导说明和独立矩阵参考。三种引擎、两组各 32 个多项式的原始系数总量为 `64 × (256+128+128) / 8` 字节，即 4 KiB；它是数据布局估算，编译产物大小和编译时间另行测量。

幂表作为共同 constexpr 材料进入生成头文件，消费者直接使用；保持 `constexpr` 能力，不依赖运行时全局缓存、堆分配或 Python。对自定义引擎保持现有 jump／longJump 适配与映射；快速内核通过专用 trait 只接入已验证的内置引擎，自定义引擎的成本由其能力决定。

### 5.3 正确性与性能验收

1. 小 ID 与旧循环实现对照完整状态和后续输出；覆盖多个 seed、不同合法状态以及高低位组合。
2. 最高位、半段边界和最大 uint64 ID 用独立 GF(2) 矩阵幂参考验证；不能调用新幂表作为唯一正确性参考。
3. 验证幂组合性质、jump 与 longJump 的对应关系，以及三类引擎各自的 ID 映射。所有状态基向量参加转移一致性验证。
4. 使用两个发布头文件分别编译；在 GCC、Clang 和 MSVC 支持矩阵的默认 `constexpr` 求值预算下，检查零 ID、单次跳跃、最高位、半段边界、最大 uint64 ID 及置位数较多的 ID，编译期结果与独立参考核对。记录实际编译器版本、标准模式和编译时间；消费者默认配置下通过是验收条件。
5. 自定义测试引擎分别覆盖只有 jump、同时具备 longJump 两种现有适配。输入状态、构造次数和转移顺序保持契约。
6. 基准单独报告 ID 位数／置位数、流数量、播种成本、冷启动、编译时间及最终产物大小。旧实现只测可在时间预算内完成的 ID，大 ID 比较用操作数量与新实现实测，不伪造旧实现耗时。

本批次的正确性结论来自独立线性转移参考、所有基向量验证以及完整状态和后续序列的等价性检查。PractRand 结果作为补充统计证据单独登记，流之间的统计关系按独立检验范围说明。

小 ID 采用现有单次跳跃快路径，维持常见调用成本；任何基于阈值的路径选择需有基准证据及具名政策。现有性能门禁照常执行，快速定位数据建立独立首轮基线。

连续建流示例维护当前高 32 位段的起点；低段递增时从上一流起点执行一次 jump，低段进位时从保存的高段起点执行一次 longJump 并重置低段。调用方使用流的独立副本，避免采样消耗改变后续建流起点。这保持 xoshiro256 的分层映射，也适用于两类 128 位流引擎。

本批次完成快速定位和连续建流示例。流池、任意 `advance` 公共接口及集中预算管理另行设计。文档明确 128 位周期引擎的完整 ID 域与每流 `2^64` 输出预算不能同时构成严格无重叠保证。

## 7. 批次 E：带权无放回抽样的设计入口

### 7.1 建议的首期边界

先设计“有限权重容器 → 原位置索引集合”的接口，候选名 `RandWeightedSampleIndices`，提供默认和显式引擎重载。按输入位置唯一，同值不同位置是不同项目；输出建议按原索引排序，表达样本集合。若需要有顺序的抽取结果，应在规格中另行规定概率和顺序契约。

抽样律采用每轮按剩余权重比例选择。样本数大于一时，最终包含概率不等于简单的 `k × w_i / Σw`。基准参考为直接逐轮按剩余权重抽取；高效实现评估 Efraimidis–Spirakis 的随机键与大小为 k 的堆，数值上优先评估对数形式。

推荐零请求直接返回空结果，不读取权重、不获取默认引擎；正请求先完成整个权重序列的验证，再采样。负数、非有限、空输入、全零及请求数超过正权重项数抛参数异常；零权重不入选。请求恰等于正权重项数时返回全部有效原索引，不消耗随机数。

这些是新增接口的拟定规则，不改变现有 `RandSample` 或 `RandWeighted`。

### 7.2 进入实施的条件

独立规格必须冻结：权重可表示范围、随机变量端点、对数键的稳定计算、舍入并列决胜、输入所有权、内存与复杂度、输出顺序、合法输入的消耗规则及异常后的引擎状态。必须说明有限精度算法与理想抽样律的误差范围。

共享契约正文拟放 `tests/common/weighted_sampling_contracts.hpp`，共同内核放 `common/sampling/weighted_sample_indices.inc`；接口约束由两标准声明装配。独立参考覆盖小规模子集概率、等权退化、零权重、重复值位置、极端权重、唯一性及 parity。统计门槛在运行前按检验方法冻结，不能根据测试结果反向调整。

只有数值契约和独立参考通过、目标输入规模的基准有依据后，才实施公共接口。流式 reservoir 输入与值提取层可在该规格基础上独立扩展。

## 8. 批次 F：可复用已验证权重对象

独立设计候选 `WeightedIndexDistribution`，构造后持有归一化权重对应的标准分布和原索引映射，后续由显式引擎抽取索引。一次复用当前 `PrepareWeights` 的输入验证、零项压缩及正权重下溢契约；构造不访问默认引擎，也不持有调用方容器或引擎引用。

对象拥有自身材料，源容器修改和销毁不影响已构造对象。首期按固定权重设计，采样成员采用标准分布需要的可变访问语义；并行调用为每个任务持有独立对象和引擎。副本拥有独立分布状态与映射，不引入共享可变缓存。

输入异常种类和原索引语义与现有容器重载一致；更换权重通过完整构造新对象后替换，失败时现有对象保持可用。不要为抽取速度预先增加 alias 后端。

先以现有容器重载、完整权重的预构建标准分布和候选对象进行同机测量，覆盖类别数、稀疏度及抽取次数。若主要诉求只是重复调用标准分布，继续使用现有重载；只有需要长期保留 RandX 的验证和映射契约时推进对象 API。

拟维护在 `common/distributions/weighted_index_distribution.inc`、两标准声明及 `tests/common/weighted_index_distribution_contracts.hpp`。冻结名称、返回类型、复制／移动、异常、线程、随机消耗与序列复现范围后形成独立规格。

## 9. 批次 G：逻辑地址随机数的准入条件

收集至少一个实际工作负载，说明为什么需要直接定位对象内的随机取值，以及对象局部重算或任务分块变化怎样影响当前有状态方案。确定根 key、对象 ID、样本序号、块内分量等字段的位宽、分配和复用规则。

以原始随机块定位作为首期边界，评估 Philox。分布的拒绝采样可能取得不定数量的随机块，必须有样本内部子序号空间与穷尽规则，再讨论分布接口的调度复现。应用逻辑地址映射是复现契约的一部分。

独立规格覆盖算法参数、公开参考向量、计数器进位与穷尽、seed/key 派生、顺序与随机访问对照、跨标准 parity、状态大小、统计检验和 CPU 平台成本。C++17/C++23 可用性与后续标准 `std::philox_engine` 的关系单独说明；编译器实现状态在进入该批次时查询一手资料。

该方向与批次 C 的职责分别为逻辑地址能力和现有流定位优化，各自按需求验收。
